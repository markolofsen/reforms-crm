# 08. Stack of the local admin app

Status: in use (`app/`). Node 22.20 or newer (`engines` of `app/package.json` and `apps/installer`), pnpm from `packageManager`. Pairs with `06`.

## Language: TypeScript only
The app is local, so there is no reason to keep a second language. One toolchain (Node + pnpm), one set of types from the database to the screen.
- UI: Next.js 16 (App Router, Turbopack) + React 19 + Tailwind v4 + coss ui (skills `coss`, `coss-particles`). Routing: real paths with the framework's typed routes under our own typed layer (`src/routes`, `src/hooks`, `AppLink`; decisions 0014 and 0015). Server and client: route files are thin server components, every screen is a client component, and the browser reaches the API through a same-origin rewrite of `/api`; no Server Actions, no database in the Next app. `hub up` serves a production build (`next build`, replayed from the turbo cache when nothing changed, then `next start -H 127.0.0.1`) on the instance's admin port (`admin_port` in `config/config.json`, else `HUB_ADMIN_PORT`, default 5173; the API port is `api_port`, else `HUB_PORT`, default 4317), so two instances run side by side with different ports; `hub up` refuses a port that is already in use and says so; the hot-reload loop is `pnpm live` (`next dev` in a worktree); e2e serves its own production build from its own directory.
- Server: small local API (Hono, decided in 0001) on 127.0.0.1. It serves the admin (drafts, send, overview, activity, connections, the instance's brand), runs the Sent detection loop (an `osascript` read of each project's Sent mailbox in Apple Mail, only while drafts wait, never launching Mail) and the optional Telegram poller. The agent does not talk to it: a session records a draft with `hub record-draft`, which writes the database directly.
- Storage: SQLite 3, one file `data/app.db` under the instance root, WAL, `foreign_keys=ON`. Every table has three `live_*` triggers that record each write in `live_seq` and `live_versions` (migration 0019); the server tails them for the admin's live stream (`06`, Live updates).

## Where files live (`HUB_HOME`)

Every location comes from one function, `hubPaths()` in `@hub/config/paths`. Nothing else joins a repo root onto `projects`, `state`, `config`, `.claude/skills` or `data` (a gate test fails on new direct joins).

- The instance is found in this order: `HUB_HOME`, else the nearest folder at or above the current one that holds `core.version`. So `hub agent <project>` works from anywhere inside an instance without `./run.sh`; started that way, the optional `hub` shortcut (`hub link`; an instance runs without it, with `./run.sh`) hands over to that instance's own pinned `core/` (an explicit `HUB_HOME` is never overridden). A command needs one of the two exactly when it resolves a data path through `hubPaths()` (the projects, the database, `state/`, `config/`). With neither, it exits 2: "no instance: run hub inside an instance folder (one with core.version), or export HUB_HOME". Commands that resolve no data path (`--help`, `docs`, `test`, `link`, `guide`, `init`, `status`) work without it. It must be an existing folder other than the core checkout: `<home>/projects`, `<home>/data/app.db`.
- Nothing lives in the user's home except the optional `hub` shortcut (`hub link`): an instance owns its data, config, secrets, backups and skills.
- Always under the home: `state/` (evidence, `guard.log`, `secrets/`, `projects/<slug>/` with the send policy and the session files, `codex/<slug>/` the Codex homes: [24-terminal.md](24-terminal.md)), `config/`, `.mcp.json`, `.claude/skills`. Always under the core: `skills/`, the project template, the `hub` binary, MCP defaults.
- Precedence: `HUB_PROJECTS`, `HUB_DB`, `HUB_CONFIG_DIR`, `HUB_CONFIG_FILE` beat the home-derived default; `HUB_LEDGER_ROOT` still overrides the ledger root; an explicit `home`/`core` option beats the environment. With only `HUB_PROJECTS` set, state sits under `<home>/state`.
- An instance states the core version it runs on in ONE file, `<home>/core.version` (first non-comment line: a core commit or tag). `hub doctor` (step `instance.core`, read-only, only when `HUB_HOME` is set) fails when the file is missing, when the core in use is not that commit or has uncommitted changes, when a core file (`app/apps`, `app/packages`, `skills`, `@docs/core`, `install.sh`, ...) is inside the instance, when the core tracks an instance file (a project folder other than the template, `@dev`, `@docs/custom`, `@refs`), or when a generated skill link dangles. While the core is still a folder inside another repository the pin check is a warning. It also WARNs "core is behind: N newer tag(s)" when the core checkout holds `vX.Y.Z` tags newer than the pin (local tags only; `hub core update` fetches), so an instance cannot sit on an old core unnoticed.
- A new instance is made with `hub init <dir> [--core-url <url>] [--pin <tag|main>] [--name <n>] [--dry-run]` (no `HUB_HOME` needed, plan P35): it refuses a folder that is not empty, runs `git init`, adds the core as the `core/` submodule at the pin (newest `vX.Y.Z` tag, else `main`; any other tag is never pinned, and `--pin` accepts only a version tag or `main`; the file carries one managed comment, `# tag: vX.Y.Z` or `# follows: main`), copies `app/apps/installer/templates/instance/` with `{{NAME}}` filled in (`run.sh`, README, `.gitignore`, AGENTS/CLAUDE stubs, the `@dev` kanban skeleton, `@docs/custom`, `@refs`), writes `core.version`, links the core skills into `.claude/skills`, installs the core's dependencies, runs `install --only Files` and `doctor` with `HUB_HOME` set to the new folder, and makes one commit (a commit that fails, for want of `git user.name`, is an error that says how to finish, not a success). It never pushes and creates no remote. The files it writes are plain files in the core, not an archive; a test pins the list.
- `hub status [--root <dir...>] [--json]` (no `HUB_HOME`): one read-only table over the instances next to the core in use (or the roots given, plus the instance the current folder is in): the core each one runs and whether it differs from its pin, the pin and `follows main`, projects with their status, drafts waiting (`ready`, read from the database opened read-only), the admin port and whether it is up.
- An instance moves to another core version with `hub core update` (HUB_HOME set): no argument lists the `vX.Y.Z` tags of the core and the one in use; `hub core update <tag>` shows the plan; `--apply` checks the tag out in `core/`, rewrites the pin in `core.version` (exactly one managed `# tag: vX.Y.Z` comment; a hand-written comment that names a version is dropped, so the file cannot state a stale one), runs the `instance.core` check and puts everything back when that check fails, then runs `pnpm install --frozen-lockfile --prefer-offline` in `core/app` when the lockfile differs between the two commits, `node_modules` is missing, or a workspace member's dependency is not installed at the version the checkout names (when pnpm fails, it prints the exact command to run). On an instance with its own workspace files (decision 0018) it regenerates them from the new core (`hub workspace init --apply`: versions, the pnpm catalog, turbo tasks). Already on the tag, it still installs when `node_modules` is behind the checkout (a pin moved by a pull). It never commits: commit `core/`, `core.version` and any regenerated workspace file together, in one commit. Going to an older tag is a rollback and is reported as one. Instances update independently of each other. A test instance may follow the core's `main` instead of a tag: `hub core update --branch main --apply` checks out the tip of `origin/main`, pins that commit in `core.version` and marks it with a `# follows: main` comment; the next tag pin replaces the mark with `# tag:`. A real-business instance stays on tags.
- `core/` is the submodule by default (`hub core install`: submodule at the pin). For core development inside a real instance, `hub core dev <path>` (dry run; `--apply` to do it) deinitialises the submodule checkout and symlinks `core/` to your core checkout, with `skip-worktree` set on `core` first so `git status`, `add -A` and `commit -a` ignore the link (the gitlink, `.gitmodules` and `core.version` stay). `hub core install` removes the link and checks the pinned commit out again. While linked: `hub core update` refuses and `instance.core` warns; never deploy in that state.
- In an instance `hub agent` runs Claude Code or Codex in `<home>`, sets `HUB_HOME` in the child, links the core skills into `<home>/.claude/skills` (relative symlinks, git-ignored, regenerated on every start and by `install --only skills.runtime`; Claude Code loads project skills from `.claude/skills/` of the folder it starts in and follows symlinked skill folders, so nothing is written to `~/.claude/skills`; `hub uninstall` removes only these links, and step `skills.legacy` reports old links an earlier `hub setup` left in `~/.claude/skills` with the one `rm` command to remove them), and gives stdio MCP servers absolute core paths plus `HUB_HOME`.
- Start-up: before the CLI is loaded, `bin/hub.mjs` checks that every workspace member of `core/app` has its dependencies installed at the versions the checkout names (`apps/installer/src/deps.ts`, Node built-ins only); when not, it runs the same `pnpm install` first (output on stderr), so a core whose checkout moved ahead of its `node_modules` never crashes on an import.
- ORM: Drizzle ORM over `better-sqlite3`, behind an async repository layer (decision 0001; libsql is the fallback).
- MCP: the knowledge tools (`knowledge_search`, `knowledge_get`) are a stdio MCP server in `app/packages/knowledge`, built on the official `@modelcontextprotocol/server`. Mail is reached only through Apple Mail (decision 0026): the agent through the installed `mail-mcp`, the hub through `osascript` (the send door, the open draft's text, Sent detection). The hub holds no mail login.
- Tests: Vitest (unit, and the rules test of `app/@rules`); Playwright with axe for the screens, in light and dark.

## What lives in SQLite (working state only)
The schema is `app/packages/db/src/schema.ts`; every table has a `project` column. Client keys (`clients`, `client_identifiers`), `marks`, drafts (status `ready hold done sent skipped`; Checked is a flag, not a status), `batches`, `send_log` and `send_control`, `safety_rules`, `inbox_rows`, `enrollments` (follow-up sequences, `23`), the project index (`projects`, `project_addresses`, `project_questions`), the knowledge index (`knowledge_docs`, `knowledge_fts`), the messenger tables, and the action log `agent_runs` and `agent_events`. Mail is read live and Notion stays the CRM; the Notion side has a dump and a dry-run restore (`app/packages/notion/README.md`).

## Monorepo
Turborepo + pnpm workspaces, best practices. Domains are packages, so each can be tested and replaced alone:
- `apps/admin` (Next.js + React + coss), `apps/server` (Hono API), `apps/installer` (the `hub` CLI).
- `packages/db` (Drizzle schema, migrations, repositories; includes the agent log), `packages/notion` (read-only dump and restore dry-run), `packages/messengers` (Telegram long polling; see its README), `packages/send` (the Mailer and the send checks, `16` section 3B), `packages/connections` (the Notion token and the Telegram bot derived from `state/secrets`: inspect, probe, write-only store; used by the server, the CLI and the installer), `packages/contract` (the API's request and response schemas, shared with the admin), `packages/projects` (`project.md` schema and registry), `packages/sequences` (follow-up sequences: definition parser, transitions, due dates, stop rule; `23`), `packages/knowledge`, `packages/mail-filters`, `packages/config` (paths, settings, shared constants, the lint size caps, the instance switches `terminal.enabled`, `agent.default`, `agent.unattended`), `packages/agent` (what a Claude Code or Codex session gets: deny lists, the unattended sandbox, the generated session config, the Agent tools checks; `24`), `packages/terminal` (the embedded terminal's sessions on `node-pty`, Node only, imported by `apps/server` alone; `24`), `packages/ui` (`@hub/ui`: the coss copies, the product primitives (`ActionButton`, `Field`, the page shell, list-detail, the data table, the brand header, the theme provider and switcher on `next-themes`), `cn` and the tokens in `styles.css`; subpath exports, no barrel; the admin and any instance app import it, it imports no app and no other `@hub/*` package; decision 0024 in the owner's plan repo).
- Rules: packages never import from apps; one public entry per package (`contract` and `ui` export by subpath instead); the UI talks only to the server; internal packages use TypeScript project references; Turbo pipeline `build`, `test`, `lint`, `typecheck` cached.
