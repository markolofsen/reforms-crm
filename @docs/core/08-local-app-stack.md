# 08. Stack of the local admin app

Status: in use (`app/`). Node 22.20 or newer (`engines` of `app/package.json` and `apps/installer`), pnpm from `packageManager`, TypeScript 6.0.3 (the `typescript` line of the `app/pnpm-workspace.yaml` catalog and the root `devDependencies`; 7.x waits until typescript-eslint admits it and `next build`'s type check is measured on it, P69). Pairs with `06`.

## Language: TypeScript only
The app is local, so there is no reason to keep a second language. One toolchain (Node + pnpm), one set of types from the database to the screen.
- UI: Next.js 16 (App Router, Turbopack) + React 19 + Tailwind v4 + coss ui (skills `coss`, `coss-particles`). Routing: real paths with the framework's typed routes under our own typed layer (`src/routes`, `src/hooks`, `AppLink`; decisions 0014 and 0015). Server and client: route files are thin server components, every screen is a client component, and the browser reaches the API through a same-origin rewrite of `/api`; no Server Actions, no database in the Next app. `hub up` serves a production build (`next build`, replayed from the turbo cache when nothing changed, then `next start -H 127.0.0.1`) on the instance's admin port (`admin_port` in `config/config.json`, else `HUB_ADMIN_PORT`, default 5173; the API port is `api_port`, else `HUB_PORT`, default 4317), so two instances run side by side with different ports; `hub up` refuses a port that is already in use and says so; after a restart of the Mac the server is started by the instance's LaunchAgent (P67, decision 0033: `~/Library/LaunchAgents/com.reforms.hub.<instance>.plist` runs `./run.sh up --service`, written by the installer step `autostart.agent`, on by default, switched in Settings ▸ This Mac or `hub autostart on|off`; an autostarted instance needs explicit ports that are not the default pair, which `hub up --demo` and `pnpm live` use), and `hub up` by hand then opens that server instead of starting a second (`--foreground` runs in the terminal as before; `hub stop`, `hub restart`); `--service` never loops launchd: switched off (`state/autostart/off`), ports held by a hand-run, a forwarded SIGTERM and the fifth failed start in 15 minutes are exit 0, and its log `state/autostart/launchd.log` rotates at 5 MB; the hot-reload loop is `pnpm live` (`next dev` in a worktree); e2e serves its own production build from its own directory.
- Server: small local API (Hono, decided in 0001) on 127.0.0.1. It serves the admin (drafts, send, overview, activity, connections, the instance's brand), runs the Sent detection loop (an `osascript` read of each project's Sent mailbox in Apple Mail, only while drafts wait, never launching Mail), the optional Telegram bot poller, the two user-account supervisors (`apps/server/src/telegram-user.ts` for the owner's Telegram account, `whatsapp.ts` for his WhatsApp number as a linked device: one connection per session under `state/secrets/sessions/`, a parked account never reconnected by itself, the sender handed only to the send door; `packages/messengers/README.md`), the autolink's client directory (P84: the Notion Clients read into memory at start and every 6 h), the messenger pre-analysis pass after a poll that stored messages (P71 M-P, through `@hub/llm`; `27`), the hourly purge of expired messenger messages, and writes the ops log (`28`). The agent does not talk to it: a session records a draft with `hub record-draft`, which writes the database directly.
- Storage: SQLite 3, one file `data/app.db` under the instance root, WAL, `foreign_keys=ON`. Every table has three `live_*` triggers that record each write in `live_seq` and `live_versions` (migration 0019); the server tails them for the admin's live stream (`06`, Live updates).

## Where files live (`HUB_HOME`)

Every location comes from one function, `hubPaths()` in `@hub/config/paths`. Nothing else joins a repo root onto `projects`, `state`, `config`, `.claude/skills` or `data` (a gate test fails on new direct joins).

- The instance is found in this order: `HUB_HOME`, else the nearest folder at or above the current one that holds `core.version`. So `hub agent <project>` works from anywhere inside an instance without `./run.sh`; started that way, the optional `hub` shortcut (`hub link`; an instance runs without it, with `./run.sh`) hands over to that instance's own pinned `core/` (an explicit `HUB_HOME` is never overridden). A command needs one of the two exactly when it resolves a data path through `hubPaths()` (the projects, the database, `state/`, `config/`). With neither, it exits 2: "no instance: run hub inside an instance folder (one with core.version), or export HUB_HOME". Commands that resolve no data path (`--help`, `docs`, `test`, `link`, `guide`, `init`, `status`) work without it. It must be an existing folder other than the core checkout: `<home>/projects`, `<home>/data/app.db`.
- Nothing lives in the user's home except the optional `hub` shortcut (`hub link`): an instance owns its data, config, secrets, backups and skills.
- Always under the home: `state/` (evidence, `log/` the agent session log ([25-agent-log.md](25-agent-log.md)) and beside its project folders the ops log `log/ops-<day>.jsonl`, what failed or happened in the server and every package ([28-ops-log.md](28-ops-log.md), `hub logs`; the server's stderr still goes to `state/autostart/launchd.log`, now one human line per ops line), `secrets/`, `projects/<slug>/` with the send policy and the session files, `codex/<slug>/` the Codex homes (`codex/_unbound/` for a session bound to no project): [24-terminal.md](24-terminal.md), `drops/<slug or _shell>/<session>/` the files dropped on a terminal tab (P76, decision 0041: removed when the tab closes, emptied at server start, never backed up)), `config/`, `.mcp.json`, `.claude/skills`. Always under the core: `skills/`, the project template, the `hub` binary, MCP defaults.
- Precedence: `HUB_PROJECTS`, `HUB_DB`, `HUB_CONFIG_DIR`, `HUB_CONFIG_FILE` beat the home-derived default; `HUB_LEDGER_ROOT` still overrides the ledger root; an explicit `home`/`core` option beats the environment. With only `HUB_PROJECTS` set, state sits under `<home>/state`.
- An instance states the core version it runs on in ONE file, `<home>/core.version` (first non-comment line: a core commit or tag). `hub doctor` (step `instance.core`, read-only, only when `HUB_HOME` is set) fails when the file is missing, when the core in use is not that commit or has uncommitted changes, when a core file (`app/apps`, `app/packages`, `skills`, `@docs/core`, `install.sh`, ...) is inside the instance, when the core tracks an instance file (a project folder other than the template, `@dev`, `@docs/custom`, `@refs`), or when a generated skill link dangles. While the core is still a folder inside another repository the pin check is a warning. For newer cores it reads the server's last update check (below) when that answer is about this pin: WARN for an update recommended or required, PASS with a note for a patch or a followed branch, never FAIL for an origin that did not answer; with no such answer it WARNs "core is behind: N newer tag(s)" when the core checkout holds `vX.Y.Z` tags newer than the pin (local tags only). The doctor reads no network, so an instance cannot sit on an old core unnoticed and a doctor run stays offline.
- A new instance is made with `hub new-instance <name> [--kind <kind> [--project <slug>]] [--core-url <url>] [--pin <tag|main>] [--no-install] [--dry-run]` (no `HUB_HOME` needed, plans P35 and P89; a bare name makes the folder `hub-<name>`): it refuses a folder that is not empty, runs `git init`, adds the core as the `core/` submodule at the pin (newest `vX.Y.Z` tag, else `main`; any other tag is never pinned, and `--pin` accepts only a version tag or `main`; the file carries one managed comment, `# tag: vX.Y.Z` or `# follows: main`), copies `app/apps/installer/templates/instance/` with `{{NAME}}` filled in (`run.sh`, README, `.gitignore`, AGENTS/CLAUDE stubs, the `@dev` kanban skeleton, `@docs/custom`, `@refs`), writes `core.version`, links the core skills into `.claude/skills`, installs the core's dependencies, runs `install --only Files` and `doctor` with `HUB_HOME` set to the new folder, and makes one commit (a commit that fails, for want of `git user.name`, is an error that says how to finish, not a success). With `--kind` it also writes the first project (`project.md` with schema, kind, name and status draft, the template's workflows, sequences and `@dev`, the kind's taxonomy, an empty `knowledge/files/`). Under 5 GB free it skips the dependency install and says so; `--no-install` skips install and doctor on purpose. It never pushes and creates no remote: it prints the one `gh repo create <owner>/hub-<name> --private --source … --remote origin --push` line. `hub starters build <out>` generates the PUBLIC starter repositories (one per kind, `hub-starter-saas`, `hub-starter-realty`, `hub-starter-generic`) the same way with no install, a README preamble and the leak guard (`app/apps/installer/src/leak-guard.ts`); the team workflow is `@docs/setup/team.md`. The files it writes are plain files in the core, not an archive; a test pins the list.
- `hub status [--root <dir...>] [--json]` (no `HUB_HOME`): one read-only table over the instances next to the core in use (or the roots given, plus the instance the current folder is in): the core each one runs and whether it differs from its pin, the pin and `follows main`, projects with their status, drafts waiting (`ready`, read from the database opened read-only), the admin port and whether it is up.
- An instance moves to another core version with `hub core update` (HUB_HOME set): no argument lists the `vX.Y.Z` tags of the core and the one in use; `hub core update <tag>` shows the plan; `--apply` checks the tag out in `core/`, rewrites the pin in `core.version` (exactly one managed `# tag: vX.Y.Z` comment; a hand-written comment that names a version is dropped, so the file cannot state a stale one), runs the `instance.core` check and puts everything back when that check fails, then runs `pnpm install --frozen-lockfile --prefer-offline` in `core/app` when the lockfile differs between the two commits, `node_modules` is missing, or a workspace member's dependency is not installed at the version the checkout names (when pnpm fails, it prints the exact command to run). On an instance with its own workspace files (decision 0018) it regenerates them from the new core (`hub workspace init --apply`: versions, the pnpm catalog, turbo tasks). Already on the tag, it still installs when `node_modules` is behind the checkout (a pin moved by a pull). It never commits: commit `core/`, `core.version` and any regenerated workspace file together, in one commit. Going to an older tag is a rollback and is reported as one. Instances update independently of each other. A test instance may follow the core's `main` instead of a tag: `hub core update --branch main --apply` checks out the tip of `origin/main`, pins that commit in `core.version` and marks it with a `# follows: main` comment; the next tag pin replaces the mark with `# tag:`. A real-business instance stays on tags.
- The instance learns of a newer core from its origin's tags (P68, decision 0034). The server checks 2 minutes after it starts, then every 6 hours, and when the owner presses Check now on Settings ▸ This Mac (at most once a minute, else 429): `git ls-remote --refs origin` in the core (no prompt, 15 s; it writes nothing), and only when origin has a `vX.Y.Z` tag newer than the pin that the core does not hold, one `git fetch --tags origin` (no `--force`, so a moved tag is reported and never taken; a fetch that meets a lock is skipped until the next run; a fetch changes no working-tree file, so `instance.core`'s clean check is unaffected). The answer, `@hub/config/core-version` (`judgeCoreUpdate`), is cached in `state/core-update.json` (`hubPaths().coreUpdate`) and served by `GET /api/instance/core`, which never runs git. Levels: current; update available (patch releases only, fewer than 5 behind, and the newest tag less than 14 days newer than the pin's); update recommended (a new minor or major, 5 or more patches behind, or 14 days newer); update required (a tag in the range carries `[update: required]` in its first line); an instance that follows a branch shows how many commits it is behind, no level. With it come the newer tags' subject lines, whether dependencies change (the lockfile differs) and whether the database migrates (a new file under `app/packages/db/drizzle/`), and the instance's own three lines: `cd <home> && ./run.sh core update vX.Y.Z --apply`, the commit of `core core.version` (plus the workspace files when the instance has them), `./run.sh restart`. A check that does not reach the origin keeps the last good answer and adds when and why. There is no switch to turn it off, and no Update button: the server would have to replace the code it runs (a later track, after P67's service).
- **Releasing a core version** (the rule the check reads). A release is an annotated tag on `main`, `git tag -a vX.Y.Z -m "core: vX.Y.Z (<what>)"`, pushed with `git push origin vX.Y.Z`: the subject line is what every instance's admin shows for that release, so it says what changed in the owner's words (track numbers in parentheses). When every instance must take it (a security or data fix), the subject ends with `[update: required]`. A tag is never moved or deleted once pushed (instances fetch without `--force` and report a moved tag); a mistake is the next patch. Lightweight tags still count (their commit subject is shown), but the release rule is annotated. There is no CHANGELOG or release-notes file: the tag is the one statement of a release (decision 0009).
- `core/` is the submodule by default (`hub core install`: submodule at the pin). For core development inside a real instance, `hub core dev <path>` (dry run; `--apply` to do it) deinitialises the submodule checkout and symlinks `core/` to your core checkout, with `skip-worktree` set on `core` first so `git status`, `add -A` and `commit -a` ignore the link (the gitlink, `.gitmodules` and `core.version` stay). `hub core install` removes the link and checks the pinned commit out again. While linked: `hub core update` refuses and `instance.core` warns; never deploy in that state.
- In an instance `hub agent` runs Claude Code or Codex in `<home>`, sets `HUB_HOME` in the child, links the core skills into `<home>/.claude/skills` (relative symlinks, git-ignored, regenerated on every start and by `install --only skills.runtime`; Claude Code loads project skills from `.claude/skills/` of the folder it starts in and follows symlinked skill folders, so nothing is written to `~/.claude/skills`; `hub uninstall` removes only these links, and step `skills.legacy` reports old links an earlier `hub setup` left in `~/.claude/skills` with the one `rm` command to remove them), and gives stdio MCP servers absolute core paths plus `HUB_HOME`.
- Start-up: before the CLI is loaded, `bin/hub.mjs` checks that every workspace member of `core/app` has its dependencies installed at the versions the checkout names (`apps/installer/src/deps.ts`, Node built-ins only); when not, it runs the same `pnpm install` first (output on stderr), so a core whose checkout moved ahead of its `node_modules` never crashes on an import.
- ORM: Drizzle ORM over `better-sqlite3`, behind an async repository layer (decision 0001; libsql is the fallback).
- MCP: the knowledge tools (`knowledge_search`, `knowledge_get`) are a stdio MCP server in `app/packages/knowledge`, built on the official `@modelcontextprotocol/server`. Mail is reached only through Apple Mail (decision 0026): the agent reads through the installed `mail-mcp`, the hub writes through `osascript` (`hub mcp` `draft_write`, the send door, the open draft's text, Sent detection). The hub holds no mail login.
- Tests: Vitest (unit, and the rules test of `app/@rules`); Playwright with axe for the screens, in light and dark.

## What lives in SQLite (working state only)
The schema is `app/packages/db/src/schema.ts`; every table has a `project` column. Client keys (`clients`, `client_identifiers`), `marks`, drafts (status `ready hold done sent skipped`; Checked is a flag, not a status), the Hub's own record of each Mail draft version it wrote (`mail_versions`, and `mail_writes` for a write in flight, so a late save of Mail's is adopted by hash: P65), `batches`, `send_log` (mail and, since 0027, messenger sends: `channel`, `messenger_draft_id`) and `send_control`, `safety_rules`, `inbox_rows`, `enrollments` (follow-up sequences, `23`), the project index (`projects`, `project_addresses`, `project_questions`), the knowledge index (`knowledge_docs`, and the FTS5 virtual table `knowledge_fts` its migration makes), the messenger tables (`messenger_accounts`, `messenger_chats`, `messenger_messages`, `messenger_drafts`; since 0025 `messenger_chats` also holds each linked chat's rules, P71 M2b; `messenger_triage`, the pre-analysis verdict per message, deleted with its message, 0029; `messenger_link_refusals`, the HMAC of each chat the owner said is not a client, P84, 0028; unlinking a chat deletes its messages, verdicts and drafts in the same transaction, and the server purges expired messages at start and every hour, connected or not), `agent_settings` (the agent's model and advisor per project, set on Settings ▸ Agent, P55), the LLM ledger `llm_calls` (one row per attempt, P78, `27`), and the action log `agent_runs` and `agent_events`. Mail is read live and Notion stays the CRM; the Notion side has a dump and a dry-run restore (`app/packages/notion/README.md`).

## Monorepo
Turborepo + pnpm workspaces, best practices. Domains are packages, so each can be tested and replaced alone:
- `apps/admin` (Next.js + React + coss), `apps/server` (Hono API), `apps/installer` (the `hub` CLI).
- `packages/db` (Drizzle schema, migrations, repositories; includes the agent log), `packages/notion` (read-only dump and restore dry-run), `packages/messengers` (the Telegram bot's long polling, the Telegram user account on mtcute and WhatsApp on Baileys, the autolink matcher; see its README), `packages/config` `./chat-rules` (the vocabulary, defaults and bounds of a chat's rules, P71 M2b), `packages/send` (the Mailer and the send checks, `16` section 3B), `packages/connections` (the Notion token and the Telegram bot derived from `state/secrets`: inspect, probe, write-only store; used by the server, the CLI and the installer), `packages/contract` (the API's request and response schemas, shared with the admin; `@hub/contract/local` is the one registry of the local Open actions, P61: ids, argument schemas, transport, the `message:`/`mailto:`/`notion:` builders and the URL allowlist; `@hub/contract/scheme` the Hub's parts and `buildScheme`, their Mermaid text, P63; `@hub/contract/tips` the dock's tips with the CLI version each was checked on and `@hub/contract/help` Help's phrases, P63 patch B), `packages/projects` (`project.md` schema and registry; `@hub/projects/local-open` resolves an Open's key to a path inside its root and runs `/usr/bin/open`, injected: `HUB_OPENER=fake` (server only, refused without `HUB_DB`) appends each argv to `state/opener.jsonl` and opens nothing), `packages/sequences` (follow-up sequences: definition parser, transitions, due dates, stop rule; `23`), `packages/knowledge`, `packages/mail-filters`, `packages/config` (paths, settings, shared constants, the lint size caps, the instance switches `agent.default`, `agent.unattended`), `packages/agent` (what a Claude Code or Codex session gets: deny lists, the unattended sandbox, the generated session config, the Agent tools checks; `24`), `packages/terminal` (the embedded terminal's sessions on `node-pty`, Node only, imported by `apps/server` alone, except `@hub/terminal/readiness`, which the installer's doctor row also runs; `24`), `packages/llm` (`@hub/llm`, P78: the one door to a model API, `llm.object` and `llm.batch` over OpenRouter with a strict schema from zod, presets, a row per attempt in `llm_calls` of `packages/db`, the monthly cap; it imports `@hub/config` and zod only, the caller hands it the ledger; `HUB_LLM=fake` is its fake transport; `27`), `packages/log` (`@hub/log`: the agent session log of `25`, its writer, `hub log`'s reading and the activity feed's labels, `feed.ts`; the server reads it for `GET /api/projects/:slug/agent-feed` and watches `state/log` for the live topic `agent-log`; and `@hub/log/ops`, the ops log of `28` (P86): the one logger of the server and every package, its redactor, `hub logs`, `GET /api/ops/errors` and the live topic `ops-log`), `apps/admin` alone depends on `mermaid` 12.3.0 (P63 patch B, decision 0035: the Help scheme, loaded by `import()` on that page only), `packages/ui` (`@hub/ui`: the coss copies, the product primitives (`ActionButton`, `Field`, the page shell, list-detail, the data table, the brand header, the theme provider and switcher on `next-themes`), the feed's three synthesised tones and `useSound` (`@hub/ui/sound`, P59), `cn` and the tokens in `styles.css`; subpath exports, no barrel; the admin and any instance app import it, it imports no app and no other `@hub/*` package; decision 0024 in the owner's plan repo).
- Rules: packages never import from apps; one public entry per package (`contract` and `ui` export by subpath instead); the UI talks only to the server; internal packages export TypeScript source and each is checked by its own `tsc --noEmit` (no project references; every tsconfig extends `@hub/config/tsconfig.base.json`, and one whose code uses Node's globals lists `"types": ["node"]`, since TypeScript 6 no longer loads every `@types` package by itself); Turbo pipeline `build`, `test`, `lint`, `typecheck` cached.
