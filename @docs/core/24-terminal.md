# 24. The embedded terminal, the agent modes and Agent tools

A right-hand column in the admin where Claude Code, Codex or a plain shell run in the instance, beside the drafts they make (track P49, decision 0027). Always on: there is no switch (P66, decision 0032, which reverses 0027 point 1); the guards below make it safe, and when no tab can start the column says why and how to fix it. This page owns the contract, the guards, the presets, the two agent modes and the Agent tools rows.

## Switches (`config/config.json`, instance)

| Key | Default | What it does |
|---|---|---|
| `agent.default` | `claude` | The CLI `hub agent`, the `hub` menu and the terminal's `+` start first (`claude` or `codex`); the order the automatic start (below) tries them in |

A server restart (`./run.sh up`) applies a change. The permission mode has no key: every session runs with no prompts and the OS sandbox on (owner 2026-11-25); a leftover `agent.unattended` is read by nothing (`files.config-keys` WARNs naming it; delete it). The terminal has no key: a leftover `terminal` key is one nothing reads (`files.config-keys` WARNs naming it; delete it).

## When it cannot start (P66)

`terminalReadiness` (`@hub/terminal/readiness`) is the one check, run by the server and by `hub doctor` row `agent.terminal`, so they cannot disagree. It counts only what stops EVERY tab, Shell included, each with its fix line: node-pty not installed in the core, or not loading on this Node (no prebuild, an ABI mismatch after a Node upgrade): `pnpm --dir <core>/app install --frozen-lockfile`; its `spawn-helper` not executable: `chmod +x <path>`; the shell a tab starts (`$SHELL`, else `/bin/zsh`) missing: set `SHELL` to an existing shell. A missing or signed-out CLI is not a problem (Shell starts; the quiet line under the tabs says it, P57). The server runs it at start (log line `terminal: on (...)` or `terminal: cannot start: <reason> (fix: <fix>)`), keeps the answer, checks a problem again at most every 5 s and on Agent tools' Refresh. While a problem is set, `GET /api/terminal` carries `problem: {reason, fix}`, `POST /api/terminal/sessions` and `/ensure` answer 503 `{error, code: "terminal_unavailable", fix}`, and the admin still draws the strip and the column: the column says the reason and the fix with a copy button, the `+` items are disabled with the reason, and nothing starts by itself. Never a dialog, never hidden.

The install workflow sets up what it can: node-pty's `spawn-helper` gets its execute bit from the server at start, from row `agent.terminal`'s apply (`./run.sh setup`, `hub install`) and from `hub core update` after its `pnpm install` (a reinstall unpacks it without the bit). Doctor rows (group Agent, both run by `setup` and `install`, not audits): `agent.terminal` (the readiness above, FAIL with its fix; the API port on 127.0.0.1 only, FAIL otherwise; a running server with a `problem`, WARN with its reason) and `agent.clis` (one login-shell detection: each CLI's version and state with its install or sign-in line, and what opening the column starts; WARN when one is not ready, never FAIL, and nothing installs a CLI: `npm i -g` would write outside the instance).

## The mode of a hub agent session, and who is there

`hub agent <slug> [--cli claude|codex|shell] [--prepare]` starts the session in the instance root, bound to one project, with the server's Node first on `PATH`. The terminal's presets run exactly this command, so a session is the same from Terminal.app and from the admin.

One permission mode, no switch (owner 2026-11-25: no friction):

| | Every session |
|---|---|
| Prompts | none (Claude `--dangerously-skip-permissions`, Codex `-a never` with the hub's writing tools approved by name) |
| OS sandbox | on: Claude's `sandbox` settings block (`enabled`, `failIfUnavailable`, `allowUnsandboxedCommands: false`, `excludedCommands` = `ssh *`, `scp *`, `rsync *` (P159), every domain allowed but loopback and the names known to resolve to it (`LOOPBACK_HOSTS`, 3l), local binding allowed, `denyWrite` on the protected paths); Codex: the `hub` permissions profile |
| Network from commands | Claude: open since 3l (P147), every host but `LOOPBACK_HOSTS`, so the send route and the API stay out of reach; Codex: open since P159, loopback included (see below) |
| SSH (P159, owner 2026-11-26: always) | both: `ssh`, `scp`, `rsync` over ssh reach any host with the owner's own `~/.ssh` (config, known_hosts, keys, ControlMaster). Claude runs them outside the sandbox; Codex runs them inside, on its open network |
| MCP servers (mail-mcp, Notion, hub) | work unchanged: the CLI calls them outside the sandbox |
| Send tools off, strict MCP, deny rules, guard hook (Claude) or forbidden rules (Codex) | yes |
| Send policy server-owned (S11), manual send needs a ticket (S12) | yes |

Never: Codex `--dangerously-bypass-approvals-and-sandbox` or `--yolo` (`codexArgs` throws, `hub doctor` fails on a config that sets it). The sandbox is the guard.

**Attended or not comes from how the session started, never from the mode** (decision 0046). A session the owner starts (the dock, a terminal, a resumed session) is attended: `messenger_send` on his word, `client_create`, `chat_link`, any known chat of the project. A background run the Hub starts itself (an autopilot turn, a follow-up sweep turn) is not: its runner sets `HUB_AUTOPILOT_CHAT` or `HUB_FOLLOWUP_CLIENT` on the turn's `hub mcp` (`backgroundRunOf` of `@hub/config/follow-ups`), the turn has its own bound tools and no send. A link a client sent is opened with `link_fetch` of `hub mcp` (a public http(s) URL only, never localhost, a private address or `file:`; an image comes back as image content).

**Protected paths** (read-only in the sandbox, Edit deny rules in every mode, because Claude's Edit and Write tools are not sandboxed): `state/projects/` (the send policies and session files), `state/autopilot.json` (the instance's autopilot switch, decision 0048), `state/secrets/` (unreadable), `state/codex/`, `config/config.json` (the allow-list) and `config/mcp.json`, the core's live checkout (entry by entry since P159 part 2: its git dir and a worktree folder beside it are writable, below), `run.sh`, `.claude/`, `.codex/`, `.mcp.json`. Since 3l (P147, owner 2026-11-25: full access by default) the rest of `config/`, the instance's `.git`, `CLAUDE.md` and `AGENTS.md` are writable; what stays read-only is what holds the session's own permissions and guards. Claude also gets `state/log/` (the agent session log, [25-agent-log.md](25-agent-log.md)): its hooks write it, the agent cannot. **Reading and editing besides the protected paths** (P140 K3, the owner's decision of 2026-11-24, `skills/README.md` "Reading and writing files"; `denyRules` of `@hub/agent/deny`): a session reads and edits `projects/**`, other projects included; reads the database folder and the other tabs' drops but never edits them; and still neither reads nor edits `state/secrets/`, another project's session files or its Codex home (they hold that project's capability, P112 S3). The guard (`auditToolCalls`) warns on an Edit in another project's folder and says nothing on a Read or Grep there; a knowledge tool stays bound to the session's project. The database folder stays writable so `draft_write`'s record works inside the sandbox; `draft_write`'s record loads only its own project's folder.

**Codex** has no strict-MCP flag, so each project gets its own `CODEX_HOME`: `state/codex/<slug>/` with `config.toml` (the hub's MCP servers only, `disabled_tools` per server, the `hub` profile: `":root" = "read"`, `":workspace_roots" = "write"`, the protected paths `"read"`, secrets and other projects' session files under `state/projects/<other>` and Codex homes (P112 S3) `"none"`, other projects' folders and the other tabs' drops `"read"` (P140 K3), network `enabled = true` (P159), `~/.ssh` `"write"` and the owner's other token files `"none"` (`codexOwnerAccess`), the Notion server's `enabled_tools` = the allow-list (P112 S3: Notion is default-deny); the project trusted; the owner's `model` and `model_reasoning_effort` carried), `rules/hub.rules` (`hub send`, the API and loopback as `forbidden` prefixes), `skills/` (links to the core skills) and `auth.json` (a link to the owner's, never a copy). A remote MCP server that needs OAuth (Notion) signs in once per `CODEX_HOME`.

**The owner's own token files** (3l, P147): an attended session can read the instance (`state/secrets/` excepted) and the owner's home, except the fixed list `OWNER_SECRET_FILES` of `@hub/agent/session` (the Google connector's config, the Notion and OpenRouter keys, `~/.ssh`, `~/.aws`, `~/.netrc`, `~/.git-credentials`, `~/.config/gh`, `~/.npmrc`, `~/.docker/config.json`): each is both a Read deny rule and a sandbox `denyRead` (Claude); in Codex's profile each is `"none"` but `~/.ssh` (P159, below). `~/.zshrc` stays readable; the skills' rules say a key is never copied out of it. Background runs keep the tight profile.

Since 3l (P147, 2026-11-25) Claude's commands reach every host but `LOOPBACK_HOSTS`; the proxy normalises IP spellings before the deny, so a decimal IP to loopback stays refused (from the code, not yet re-measured), but another name that resolves to 127.0.0.1 reaches the admin (the owner's decision). Measured on Claude Code 2.1.220 and Codex 0.146.0 (2026-11-18), in the sandboxed mode, in a scratch instance: a decimal-IP `curl` to the send route exits 7 in both; `osascript` to Mail fails in both; `echo >>` the policy file is refused by the OS in both; Claude's Edit and Codex's `apply_patch` on it are refused; `draft_write`'s record works. Another CLI version is a WARN in Agent tools: rerun those checks.

**SSH, always (P159, owner 2026-11-26: «Надо разрешить агентам доступ по SSH обязательно… Всегда»).** Measured on Claude Code 2.1.220 and Codex 0.153.0 (2026-11-26), in throwaway sessions built from the generated files: `ssh -o BatchMode=yes host 'echo ok'` prints `ok` in both, `scp` and `rsync` copy a remote file. Before, both failed with `connect … port 22: Operation not permitted`.
- **Claude**: its sandbox proxy carries HTTP(S) only, so a sandboxed `ssh` has no route, whatever `allowedDomains` says; `ssh`, `scp` and `rsync` are `excludedCommands` (`claudeExcludedCommands` of `@hub/agent/session`), run outside the sandbox with no prompt in this mode, and read `~/.ssh` themselves. The settings come in through `--settings`, so Claude honours the list although `allowUnsandboxedCommands` is false; nothing else leaves the sandbox. The Bash text must start with the command: `ssh host 'cmd'` and `ssh host 'cmd' | tr …` work (measured); a `cd`, a redirect, a `$(...)` or `/usr/bin/ssh` keeps the call sandboxed and it fails. The agent's own `cat ~/.ssh/id_rsa` (`Operation not permitted`) and Read (deny rule) stay refused. The trade-off: these three run with the owner's full access, so a deliberate `rsync ~/.ssh/config ./x` (measured: it copies), a local `scp`, or `ssh -o ProxyCommand=…` reads or writes any file, the keys and the protected paths included. The `Bash(*localhost*)`-style deny rules still apply to their text.
- **Codex**: a prefix rule `allow` does not take a command out of the sandbox under `approval_policy = "never"` (measured on 0.153: the model is told never to ask for escalation), and the proxy mode (`features.network_proxy` with per-host rules) carries HTTP only. So the `hub` profile turns the network on (direct). ssh runs inside the sandbox and needs `~/.ssh` readable (with the key denied only the ssh-agent is left: `Permission denied (publickey)` after a reboot) and writable (a read-only folder makes ControlMaster's `unix_listener: cannot bind` fatal; Codex allows only `deny` on a glob, so the folder is writable as a whole). The trade-off: a Codex command reads the private key and reaches loopback: the Hub's API and mail-mcp's port answer a `curl` (its send tools are off only in Codex's MCP client). The owner's other token files are now closed in the profile.

**Improving the core (P159 part 2, owner 2026-11-26: «Надо убрать сэндбокс, чтобы наш агент мог спокойно работать с Core Reforms Hub… улучшать общие инструкции, скиллы»; the coordinator's delegated decision).** The live checkout (the instance's `core` link) is what the server and every session read, so it stays read-only; an attended session works in a worktree in `<core>-dock/<topic>` (one folder beside the core, derived from `paths.core`: `coreAccess` of `@hub/agent/core-access`). The steps the agent follows are in `skills/README.md` ("Improving the core") and the capabilities line's core part.
- **Claude**: `allowWrite` = the core's root and `<core>-dock`; `denyWrite` and the Edit deny rules name every entry of the checkout but `.git`, plus `.git/hooks` and `.git/config` (shared by every worktree: a planted hook would run unsandboxed in the next writer's commit). Measured on 2.1.220: a deny wins over an allow; Claude turns an `Edit(//<core>/**)` rule into a sandbox denial and resolves the instance's `core` link, so either closed the git dir (`cannot open '.git/FETCH_HEAD'`); an allowed `.git` itself is treated as a bare repository (its `refs`, `objects`, `HEAD` denied). `git push *` and `git -C * push *` run outside the sandbox (the GitHub credential, `~/.git-credentials`, stays closed to commands); a `cd` to a folder outside the working directories does not persist, so a worktree pushes with `-C`.
- **`hub guard`** (`coreGitViolations`, every mode, from the hook's `cwd` or `-C`): in the main checkout nothing that moves its HEAD, index, files or config (merge, pull, reset, checkout, commit, add and the like); anywhere in the core repo no `update-ref`, `symbolic-ref`, config write, `branch -f/-D/-M` of main, force, delete, mirror, `-u` or `--receive-pack` push, no remote but `origin`; a push to main only of a change inside `skills/` and `@docs/` against `origin/main` (an unreadable diff is refused). Anything else is pushed as a branch for the coordinator.
- **Codex**: its profile gives `"write"` to the git dir and `<core>-dock`, `"read"` to `.git/hooks` and `.git/config`; the checkout stays `"read"`. It has no guard hook: `rules/hub.rules` forbids `git update-ref`, `git symbolic-ref`, force, mirror and delete pushes and `git push origin main`/`HEAD:main` as prefixes (a prefix cannot see `-C` or a refspec), and it cannot push at all (the credential is closed), so main is the coordinator's there.
- Measured (2026-11-26, throwaway core clone with a scratch bare origin, the generated files with the guard hook): Claude made a worktree, edited a skill with the Edit tool, committed with explicit paths and pushed it to main; a write and an Edit to the checkout's skill file were refused; an `app/` change pushed to main, `merge --ff-only` in the checkout, `push --force` and `update-ref` were refused by the guard; a write to `.git/hooks` was refused; the branch itself pushed. Codex made a worktree and committed; writes to the checkout, `.git/hooks` and `.git/config` were refused; its push failed (the origin is not writable to it).
- **After main moves** the live checkout still has the old text: the coordinator updates it, and the next session start (the launcher rewrites the session files) or his `./run.sh agent <slug> --prepare` picks it up. The trade-offs: the core's root accepts a new top-level file (the entries are denied, not the folder); the instance's `core` link is not a sandbox entry (only its Edit rule holds), so a command could repoint it; the excluded `git push` runs with the owner's full access, and the guard reads its text, not its intent.

### The third kind: an autopilot turn (decision 0048, P139 A3)

The server, not the owner, starts it: one headless `claude -p` per client burst in a chat whose three autopilot switches are on (`packages/agent/src/autopilot`). It runs the Hub's own Claude Code (beside the Hub's Node, never one from `PATH`) on the owner's Claude sign-in (his plan, no key; `USER` must be set, A0), model `sonnet`, `--max-turns 12`, killed after 120 s, at most 2 at once and 100 a day on this Mac. Its files are per chat under `state/projects/<slug>/autopilot/<chat>/` (a protected path): a settings file with no hooks (`disableAllHooks`: the prompt hook would log its prompt as the owner's words), the advisor off and the folders' memory files excluded; an MCP file with only `hub`, bound to the project (its capability) and to the one chat (`HUB_AUTOPILOT_CHAT`). Flags: `--tools ""` (no built-in tool at all, so no shell and no sandbox to set), `--disallowedTools` for every other hub tool, `--allowedTools` and `--permission-mode dontAsk` for its five (`messenger_history`, `client_show`, `knowledge_search`, `knowledge_get`, `messenger_draft_write`), `--strict-mcp-config`, `--no-session-persistence`, the `autopilot-reply` skill as its appended system prompt, and the prompt (facts only, no client text) on stdin. Env: `USER`, `HOME`, `PATH`, `MCP_CONNECTION_NONBLOCKING=false`, `CLAUDE_CODE_DISABLE_ADVISOR_TOOL=1`, nothing of the server's `HUB_*`. It reads `stream-json`: the `init` event must show `hub` connected with exactly the five tools (else the turn is refused, `mcp_not_ready`); the draft is the one its own `messenger_draft_write` call wrote and the hub answered; `is_error` and any permission denial fail the turn. An e2e run uses `HUB_AUTOPILOT_BRAIN=fake` (only with `HUB_DB`); a test or a throwaway database gets no brain. Unmeasured: whether `disableAllHooks` in `--settings` also silences hooks of the owner's own `~/.claude/settings.json` in print mode, and a full turn from the launchd-started server.


### The fourth kind: a follow-up turn (decision 0050, P142)

The server starts it too: one headless turn per silent client of the daily sweep, through the same runner as an autopilot turn (the same binary, sign-in, env, `--tools ""`, `--strict-mcp-config`, `--max-turns 12`, 120 s, and one of the same two slots, an autopilot turn first), with the `follow-up-sweep` skill as its system prompt and `hub` bound to the project and to the one client (`HUB_FOLLOWUP_CLIENT`, the `clients` row id; another client is refused `followup_other_client`). Its nine tools: `client_show`, `client_map`, `message_show`, `knowledge_search`, `knowledge_get`, `draft_write`, `messenger_draft_write`, `follow_up_plan`, `bug_report` (P145); no send tool. The `init` event must show exactly those (else `mcp_not_ready`). At most 60 such turns a day on this Mac, apart from autopilot's 100. An e2e run uses `HUB_FOLLOWUP_BRAIN=fake` (only with `HUB_DB`). Everything else: [30-follow-ups.md](30-follow-ups.md).

A follow-up turn bound to a fixed bug's note (P145 B4) also carries `HUB_FOLLOWUP_BUG_NOTE`, the `bug_fixed_notes` row id: its draft is stamped on that note, and a mail note joins the day's lead batch ([30-follow-ups.md](30-follow-ups.md) "Bug reports").

### The fifth kind: a pass turn (decision 0055, P147)

The server starts it too: one headless turn per open lead (the lead pass) or per sender's newest open message (the mail pass), through the same runner and slots as a follow-up turn. `hub` is bound to the project and to that one lead (`HUB_LEAD_PAGE`, the page id) or that one inbound row (`HUB_MAIL_INBOUND`); another is refused. Its eight tools: `knowledge_search`, `knowledge_get`, `client_show`, `message_show`, `link_fetch`, `draft_write`, `lead_decide` or `mail_decide`, `bug_report` (`LEAD_PASS_HUB_TOOLS`, `MAIL_PASS_HUB_TOOLS`); no send tool. The rules are the `lead-pass` skill, or `triage-mail`'s `references/mail-pass.md`. Each turn ends in one decision; a reply is a draft in the day's lead batch, sent only by the owner's Send all ready. At most 30 turns a pass and 60 a day on this Mac for both passes. Everything else: [21-leads.md](21-leads.md) "The daily passes".

## Send policy and send ticket

`state/projects/<slug>/send-policy.json` replaces the `draft.recipients` and `send.*` rows of `project.md`; `hub send policy` is the one writer ([16-projects-and-knowledge.md](16-projects-and-knowledge.md) section 3B). Its optional `autopilot` block (decision 0048, P139: `mode` off, dry_run or on, the `chats` switched on, `disclose`, `quiet`) is written through the same writer by the owner's routes (`PUT /api/projects/:slug/autopilot`, a ticket from `POST /api/autopilot/tickets` bound to `autopilot:project:<slug>`) or `hub send policy autopilot <slug> mode|chat|disclose ...` in his own shell, which refuses inside a session. The instance switch `state/autopilot.json` has its own route (`PUT /api/autopilot`, ticket `autopilot:instance`). `POST /api/sends/tickets {project, draftId}` mints a single-use ticket (60 s, bound to `send:<draftId>`) for the admin's exact origin with `Sec-Fetch-Site: same-origin`; the apply step of `POST /api/projects/:slug/drafts/:id/send` needs it, else 403.

## The terminal: contract

Wire shapes: `@hub/contract/terminal`. Server: `@hub/terminal` (sessions, PTY, presets, env, socket; imported by `apps/server` only) and `apps/server/src/terminal/terminal.ts`, `routes/terminal.ts`.

| Route | What it does |
|---|---|
| `GET /api/terminal` | `{presets, sessions, clis, checkedAt, problem}` (`clis`: the detector's facts, below; no path; empty until the first detection finished; `problem`: null, or why no tab can start with its fix, above) |
| `POST /api/terminal/sessions` | `{preset: "claude" \| "codex" \| "shell", project?}` (strict: no command, no path). 201 with the session; 400 an unknown preset or a CLI without a project, 404 an unknown project, 409 at 8 live sessions, 503 `terminal_unavailable` while a problem is set. Exact admin origin and `Sec-Fetch-Site: same-origin` (P57) |
| `POST /api/terminal/ensure` | `{project?, theme?}` (P57): the running session of that project (200, `created: false`), else the server's pick starts (201, `created: true`, `why`: the one line when the pick was not the first choice, or that it resumed); P64: the pick resumes the project's last logged session when it can (below). One at a time per project, so two tabs get one session; 503 `terminal_unavailable` while a problem is set. Exact admin origin and `Sec-Fetch-Site: same-origin` |
| `DELETE /api/terminal/sessions/:id` | Closes the tab: SIGHUP to the process group, SIGKILL after 3 s |
| `POST /api/terminal/sessions/:id/drops` | P76, decision 0041: a multipart body of 1 to 10 files (field `file`), 20 MiB in all; each is written to `state/drops/<project or _shell>/<session>/<safe name>` (`hubPaths().drops`; the basename only, letters, digits, `._-`, at most 80 characters, `-2` on a clash; folders 700, files 600, never overwritten) and the answer is `{paths}`, absolute, in the order sent. The dock pastes them into the session (below). 404 an unknown session, 409 an ended one, 400 no file, 413 past the caps; exact admin origin and `Sec-Fetch-Site: same-origin`, no ticket (it types nothing). The folder is removed when the tab closes and when the server stops; the server empties `state/drops` at start |
| `POST /api/terminal/tickets` | `{session}`: a single-use ticket (30 s, bound to `term:<id>`) and the socket URL `ws://127.0.0.1:<api port>/terminal`; exact admin origin and `Sec-Fetch-Site: same-origin` |
| upgrade `/terminal` | straight to the API port (not through Next's rewrite). 404 for another path, 400 with a query string (a ticket in a URL is logged), 403 for a Host that is not loopback or an Origin that is not the admin's |

Socket: the first frame is `{op: "auth", ticket}` within 2 s, else close 4401 (4404 when the session is gone); then `ready`, a snapshot of the screen (`@xterm/headless` 5 000 lines, serialised), then the live stream. Bytes are binary frames both ways; control is JSON (`resize` clamped 2 to 500, `ping`/`pong`; `exit`, `taken`). One viewer per session: a second attach takes it and the first closes 4409. Output is batched at 16 ms; the PTY pauses above 1 MB queued in the socket and resumes under 256 KB.

Presets, a fixed server table: `claude` and `codex` spawn the argv `<server node> <hubBin> agent <slug> --cli <x>` through the owner's login shell for its environment (`$SHELL -l -i -c 'exec "$0" "$@"' <argv>`): nothing is typed into a prompt and no string is parsed, so a key pressed while the shell starts cannot corrupt the command (v0.9.1 typed it and a first key leaked in: `zsh: no such file or directory: д<path to hub.mjs>`); the tab ends when the CLI exits. `shell` is the owner's own login shell (not sandboxed, as in Terminal.app). Without a project in the admin URL only Shell is offered (a one-project instance always has its project, P57). The shell is `$SHELL -l -i` in the instance root; env: the server's minus `HUB_MAILER`, `HUB_DB`, `HUB_PORT`, `HUB_CONNECTIONS_PROBE`, `HUB_TERMINAL_SHELL`, `HUB_AGENT_TOOLS`, `NODE_OPTIONS`, plus `HUB_HOME`, `HUB_PROJECT`, `TERM=xterm-256color`, `COLORTERM=truecolor`, UTF-8 `LANG`, `TERM_PROGRAM=hub`, and `COLORFGBG` for the admin's resolved theme when the tab starts (`0;15` light, `15;0` dark). The screen's colours are the `--terminal-*` tokens of the current theme, re-read live, and xterm answers a program's OSC 10/11 colour queries with them, so Claude Code and Codex can match their palette; the owner's own CLI settings (Claude's `/theme`) are never changed. Sessions end with the server; closing the column or the page only detaches.

**The terminal starts itself (P57).** `@hub/agent/detect` `detectClis()` has two tiers. Tier 1 resolves each CLI on known folders (the server's own node folder, which the LaunchAgent pins; then the server's PATH; then `~/.local/bin` and `~/.claude/local`) and runs its `--version` and `claude auth status --json` / `codex login status` directly, in parallel, each cut at 10 s (measured 2026-11-19 under a launchd-like environment: 1.7 s, both ready). Tier 2, only for a CLI tier 1 did not settle (not found, `--version` fails, sign-in not read), is ONE spawn of the owner's login shell (`$SHELL -l -i -c <script>`, the environment a tab gets; stdin closed, the process group killed at 45 s): `command -v`, `--version` and the sign-in, each fenced by marker lines so a profile's output is ignored. Why both: under launchd (P67, v0.12.12) the login shell (conda, nvm and brew in the profile) did not answer in the old 15 s, so both CLIs read `unknown` for as long as the server ran; and the non-login PATH can name another `codex` (a broken nvm v22.11.0 one) than the login shell (v22.22.0, 0.146.0), so a binary that does not start is never tier 1's answer, it falls through to the login shell. A fact is `ready` (found, `--version` answers, signed in), `signed-out`, `missing` (not found, or `--version` fails) or `unknown` (the shell hung or said nothing), with its one fix line: `INSTALL_LINE` (`npm i -g @anthropic-ai/claude-code`, `npm i -g @openai/codex`) or `LOGIN_LINE` (`claude auth login`, `codex login`), the same lines the launcher and Agent tools say. ## Shared focus: the agent sees what the owner sees (P51, decision 0029)

"Ответь этому клиенту" or "ответь по этой записи" in the dock needs no explanation: the session knows what the admin shows, on every screen.

- **The admin publishes its focus, by refs.** The shell frame's publisher (`apps/admin/src/features/focus/`) posts this tab's focus to `POST /api/focus` 300 ms after it settles, again on window focus and visibility (the last focused tab wins), every 60 s while visible, and clears it on `pagehide`. Every route posts the same fields, derived from the router, never from a hand list of screens (P72): the route id, its title from the route table (`screenTitleOf`: "Knowledge", "Draft 42", "Mail"), and refs, domain ids written `<kind>:<id>` (`draft:42`, `client:7`, `run:10`, `knowledge:<index path>`, `project:<slug>`; `@hub/contract/focus` `REF_KINDS`, `parseRef`): `subject` (the record the address or the open card names: the Mail card, `client:7` on `/log?client=7`, P73), `pointed` (the last row in `#main` that got keyboard focus or a click, never hover, until another row takes it or the screen changes), `selected` (at most 200), `window` (up to 30 refs of the rows on screen and the list's total), `view` (the address's search state) and `pointer` (the outcome of the agent's last highlight). A screen joins by putting `agentRef(ref)` on its rows (`data-agent-ref`) and, when it opens a record its address does not name, calling `useFocusSubject` (`lib/focus.ts`); `test/focus.test.ts` runs every route of the table. The route is as strict as the send and terminal tickets (exact admin Origin, loopback Host, `Sec-Fetch-Site: same-origin`, a strict body): a forged focus would steer the agent. The server keeps the last one in memory and in `state/focus.json` (`schema: 2`; ids and refs only, no title, name, subject or body, no secret; mode 600; written only when it changed, the heartbeat at most once in 50 s; a `schema: 1` file reads as none). A hidden tab never replaces another tab's visible focus. No database table; the focus has no live topic and no GET.
- **One reader, one resolver per ref kind.** `readFocus` (`@hub/agent/focus`, `src/focus/read.ts`) reads the file and resolves each ref in the database opened read-only, scoped to the bound project, by its kind's resolver (`src/focus/resolvers/`: draft, client, run, knowledge, project, chat, mdraft, and since P98 inbound, a client's message of Mail ▸ Inbox with who, subject and when in its title): its title (client data, cut to 120 characters), its status and `read`, the server, tool and arguments that read it (the hub's `knowledge_get` with the entry's path, `draft_show`, `client_show`, `message_show`; `null` for a run and a project, which no tool reads yet). A ref of another project or a deleted one drops out; a kind without a resolver fails the package's test. States: `fresh` (visible, at most 10 minutes old), `stale`, `elsewhere` (another project: named nowhere), `none`. The prompt hook reads at `depth: "line"` (the subject and the pointed row resolved, the selection and the window counted); the `focus` tool and `hub focus --json` read everything.

## Agent tools (Settings ▸ Agent, P70; the Agents page in P63, on Connections before)

`@hub/agent` `agentChecks({paths, slug, cli, probe, facts})` returns rows `{id, cli, title, state: pass|warn|fail|skip, detail, fix}`; every row that is not a pass names one command line. The same rows serve `hub doctor` group `Agent` (one line per project and CLI, an audit row: `--fast` leaves it out) and `GET /api/projects/:slug/agent-tools` (the last result, computed on the first GET; `POST .../agent-tools/refresh` reruns it; Settings ▸ Agent `/<project>/settings/agent` renders them for the address's project: one sentence and Refresh, the rows that need a fix or a look with their fix lines and Copy, every row folded under All checks; Overview's parts read the cached result without running it, and its Agent sessions part holds every row no other part covers, so a row that lights Settings ▸ Agent's dot is also a "Needs you" item). `HUB_AGENT_TOOLS=fake` (e2e, refused without `HUB_DB`) returns fixed rows.
