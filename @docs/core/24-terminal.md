# 24. The embedded terminal, the agent modes and Agent tools

A right-hand column in the admin where Claude Code, Codex or a plain shell run in the instance, beside the drafts they make (track P49, decision 0027). Always on: there is no switch (P66, decision 0032, which reverses 0027 point 1); the guards below make it safe, and when no tab can start the column says why and how to fix it. This page owns the contract, the guards, the presets, the two agent modes and the Agent tools rows.

## Switches (`config/config.json`, instance)

| Key | Default | What it does |
|---|---|---|
| `agent.default` | `claude` | The CLI `hub agent`, the `hub` menu and the terminal's `+` start first (`claude` or `codex`); the order the automatic start (below) tries them in |
| `agent.unattended` | `false` | No prompts, the OS sandbox on (the table below). Only an exact `true` |

A server restart (`./run.sh up`) applies a change. The terminal has no key: a leftover `terminal` key is one nothing reads (`files.config-keys` WARNs naming it; delete it).

## When it cannot start (P66)

`terminalReadiness` (`@hub/terminal/readiness`) is the one check, run by the server and by `hub doctor` row `agent.terminal`, so they cannot disagree. It counts only what stops EVERY tab, Shell included, each with its fix line: node-pty not installed in the core, or not loading on this Node (no prebuild, an ABI mismatch after a Node upgrade): `pnpm --dir <core>/app install --frozen-lockfile`; its `spawn-helper` not executable: `chmod +x <path>`; the shell a tab starts (`$SHELL`, else `/bin/zsh`) missing: set `SHELL` to an existing shell. A missing or signed-out CLI is not a problem (Shell starts; the quiet line under the tabs says it, P57). The server runs it at start (log line `terminal: on (...)` or `terminal: cannot start: <reason> (fix: <fix>)`), keeps the answer, checks a problem again at most every 5 s and on Agent tools' Refresh. While a problem is set, `GET /api/terminal` carries `problem: {reason, fix}`, `POST /api/terminal/sessions` and `/ensure` answer 503 `{error, code: "terminal_unavailable", fix}`, and the admin still draws the strip and the column: the column says the reason and the fix with a copy button, the `+` items are disabled with the reason, and nothing starts by itself. Never a dialog, never hidden.

The install workflow sets up what it can: node-pty's `spawn-helper` gets its execute bit from the server at start, from row `agent.terminal`'s apply (`./run.sh setup`, `hub install`) and from `hub core update` after its `pnpm install` (a reinstall unpacks it without the bit). Doctor rows (group Agent, both run by `setup` and `install`, not audits): `agent.terminal` (the readiness above, FAIL with its fix; the API port on 127.0.0.1 only, FAIL otherwise; a running server with a `problem`, WARN with its reason) and `agent.clis` (one login-shell detection: each CLI's version and state with its install or sign-in line, and what opening the column starts; WARN when one is not ready, never FAIL, and nothing installs a CLI: `npm i -g` would write outside the instance).

## The two modes of a hub agent session

`hub agent <slug> [--cli claude|codex|shell] [--prepare]` starts the session in the instance root, bound to one project, with the server's Node first on `PATH`. The terminal's presets run exactly this command, so a session is the same from Terminal.app and from the admin.

| | Attended (default) | Unattended (`agent.unattended: true`) |
|---|---|---|
| Prompts | the CLI asks (Claude's default mode, Codex `-a on-request`) | none (Claude `--dangerously-skip-permissions`, Codex `-a never`) |
| OS sandbox | Codex: the `hub` profile; Claude: off | on: Claude's `sandbox` settings block (`enabled`, `failIfUnavailable`, `allowUnsandboxedCommands: false`, no allowed domain, no local binding, `denyWrite` on the protected paths); Codex: the `hub` permissions profile, `approval_policy = "never"` |
| Network from commands | Claude: yes; Codex: off | off (no loopback: the send route and the API are out of reach) |
| MCP servers (mail-mcp, Notion, knowledge-mcp) | work | work unchanged: the CLI calls them outside the sandbox |
| Send tools off, strict MCP, deny rules, guard hook (Claude) or forbidden rules (Codex) | yes | yes |
| Send policy server-owned (S11), manual send needs a ticket (S12) | yes | yes |

Never: Codex `--dangerously-bypass-approvals-and-sandbox` or `--yolo` (`codexArgs` throws, `hub doctor` fails on a config that sets it). In attended mode the person answering the prompts is the guard; in unattended mode the sandbox is.

**Protected paths** (read-only in the sandbox, Edit deny rules in every mode, because Claude's Edit and Write tools are not sandboxed): `state/projects/` (the send policies and session files), `state/secrets/` (unreadable), `state/codex/`, `config/`, the core, `run.sh`, `.claude/`, `.mcp.json`, `.git`, `CLAUDE.md`, `AGENTS.md`; other projects' folders are unreadable. Claude also gets `state/log/` (the agent session log, [25-agent-log.md](25-agent-log.md)): its hooks write it, the agent cannot. The database folder stays writable so `hub record-draft` works inside the sandbox; `hub record-draft` loads only its own project's folder.

**Codex** has no strict-MCP flag, so each project gets its own `CODEX_HOME`: `state/codex/<slug>/` with `config.toml` (the hub's MCP servers only, `disabled_tools` per server, the `hub` profile: `":root" = "read"`, `":workspace_roots" = "write"`, the protected paths `"read"`, secrets and other projects `"none"`, network `enabled = false`; the project trusted; the owner's `model` and `model_reasoning_effort` carried), `rules/hub.rules` (`hub send`, the API and loopback as `forbidden` prefixes), `skills/` (links to the core skills) and `auth.json` (a link to the owner's, never a copy). A remote MCP server that needs OAuth (Notion) signs in once per `CODEX_HOME`.

Measured on Claude Code 2.1.220 and Codex 0.146.0 (2026-11-18), unattended, in a scratch instance: a decimal-IP `curl` to the send route exits 7 in both; `osascript` to Mail fails in both; `echo >>` the policy file is refused by the OS in both; Claude's Edit and Codex's `apply_patch` on it are refused; `hub record-draft` works. Another CLI version is a WARN in Agent tools: rerun those checks.

## Send policy and send ticket

`state/projects/<slug>/send-policy.json` replaces the `draft.recipients` and `send.*` rows of `project.md`; `hub send policy` is the one writer ([16-projects-and-knowledge.md](16-projects-and-knowledge.md) section 3B). `POST /api/sends/tickets {project, draftId}` mints a single-use ticket (60 s, bound to `send:<draftId>`) for the admin's exact origin with `Sec-Fetch-Site: same-origin`; the apply step of `POST /api/projects/:slug/drafts/:id/send` needs it, else 403.

## The terminal: contract

Wire shapes: `@hub/contract/terminal`. Server: `@hub/terminal` (sessions, PTY, presets, env, socket; imported by `apps/server` only) and `apps/server/src/terminal.ts`, `routes/terminal.ts`.

| Route | What it does |
|---|---|
| `GET /api/terminal` | `{unattended, presets, sessions, clis, checkedAt, problem}` (`clis`: the detector's facts, below; no path; empty until the first detection finished; `problem`: null, or why no tab can start with its fix, above) |
| `POST /api/terminal/sessions` | `{preset: "claude" \| "codex" \| "shell", project?}` (strict: no command, no path). 201 with the session; 400 an unknown preset or a CLI without a project, 404 an unknown project, 409 at 8 live sessions, 503 `terminal_unavailable` while a problem is set. Exact admin origin and `Sec-Fetch-Site: same-origin` (P57) |
| `POST /api/terminal/ensure` | `{project?, theme?}` (P57): the running session of that project (200, `created: false`), else the server's pick starts (201, `created: true`, `why`: the one line when the pick was not the first choice, or that it resumed); P64: the pick resumes the project's last logged session when it can (below). One at a time per project, so two tabs get one session; 503 `terminal_unavailable` while a problem is set. Exact admin origin and `Sec-Fetch-Site: same-origin` |
| `DELETE /api/terminal/sessions/:id` | Closes the tab: SIGHUP to the process group, SIGKILL after 3 s |
| `POST /api/terminal/sessions/:id/drops` | P76, decision 0041: a multipart body of 1 to 10 files (field `file`), 20 MiB in all; each is written to `state/drops/<project or _shell>/<session>/<safe name>` (`hubPaths().drops`; the basename only, letters, digits, `._-`, at most 80 characters, `-2` on a clash; folders 700, files 600, never overwritten) and the answer is `{paths}`, absolute, in the order sent. The dock pastes them into the session (below). 404 an unknown session, 409 an ended one, 400 no file, 413 past the caps; exact admin origin and `Sec-Fetch-Site: same-origin`, no ticket (it types nothing). The folder is removed when the tab closes and when the server stops; the server empties `state/drops` at start |
| `POST /api/terminal/tickets` | `{session}`: a single-use ticket (30 s, bound to `term:<id>`) and the socket URL `ws://127.0.0.1:<api port>/terminal`; exact admin origin and `Sec-Fetch-Site: same-origin` |
| upgrade `/terminal` | straight to the API port (not through Next's rewrite). 404 for another path, 400 with a query string (a ticket in a URL is logged), 403 for a Host that is not loopback or an Origin that is not the admin's |

Socket: the first frame is `{op: "auth", ticket}` within 2 s, else close 4401 (4404 when the session is gone); then `ready`, a snapshot of the screen (`@xterm/headless` 5 000 lines, serialised), then the live stream. Bytes are binary frames both ways; control is JSON (`resize` clamped 2 to 500, `ping`/`pong`; `exit`, `taken`). One viewer per session: a second attach takes it and the first closes 4409. Output is batched at 16 ms; the PTY pauses above 1 MB queued in the socket and resumes under 256 KB.

Presets, a fixed server table: `claude` and `codex` spawn the argv `<server node> <hubBin> agent <slug> --cli <x>` through the owner's login shell for its environment (`$SHELL -l -i -c 'exec "$0" "$@"' <argv>`): nothing is typed into a prompt and no string is parsed, so a key pressed while the shell starts cannot corrupt the command (v0.9.1 typed it and a first key leaked in: `zsh: no such file or directory: д<path to hub.mjs>`); the tab ends when the CLI exits. `shell` is the owner's own login shell (not sandboxed, as in Terminal.app). Without a project in the admin URL only Shell is offered (a one-project instance always has its project, P57). The shell is `$SHELL -l -i` in the instance root; env: the server's minus `HUB_MAILER`, `HUB_DB`, `HUB_PORT`, `HUB_CONNECTIONS_PROBE`, `HUB_TERMINAL_SHELL`, `HUB_AGENT_TOOLS`, `NODE_OPTIONS`, plus `HUB_HOME`, `HUB_PROJECT`, `TERM=xterm-256color`, `COLORTERM=truecolor`, UTF-8 `LANG`, `TERM_PROGRAM=hub`, and `COLORFGBG` for the admin's resolved theme when the tab starts (`0;15` light, `15;0` dark). The screen's colours are the `--terminal-*` tokens of the current theme, re-read live, and xterm answers a program's OSC 10/11 colour queries with them, so Claude Code and Codex can match their palette; the owner's own CLI settings (Claude's `/theme`) are never changed. Sessions end with the server; closing the column or the page only detaches.

**The terminal starts itself (P57).** `@hub/agent/detect` `detectClis()` has two tiers. Tier 1 resolves each CLI on known folders (the server's own node folder, which the LaunchAgent pins; then the server's PATH; then `~/.local/bin` and `~/.claude/local`) and runs its `--version` and `claude auth status --json` / `codex login status` directly, in parallel, each cut at 10 s (measured 2026-11-19 under a launchd-like environment: 1.7 s, both ready). Tier 2, only for a CLI tier 1 did not settle (not found, `--version` fails, sign-in not read), is ONE spawn of the owner's login shell (`$SHELL -l -i -c <script>`, the environment a tab gets; stdin closed, the process group killed at 45 s): `command -v`, `--version` and the sign-in, each fenced by marker lines so a profile's output is ignored. Why both: under launchd (P67, v0.12.12) the login shell (conda, nvm and brew in the profile) did not answer in the old 15 s, so both CLIs read `unknown` for as long as the server ran; and the non-login PATH can name another `codex` (a broken nvm v22.11.0 one) than the login shell (v22.22.0, 0.146.0), so a binary that does not start is never tier 1's answer, it falls through to the login shell. A fact is `ready` (found, `--version` answers, signed in), `signed-out`, `missing` (not found, or `--version` fails) or `unknown` (the shell hung or said nothing), with its one fix line: `INSTALL_LINE` (`npm i -g @anthropic-ai/claude-code`, `npm i -g @openai/codex`) or `LOGIN_LINE` (`claude auth login`, `codex login`), the same lines the launcher and Agent tools say. The server keeps the answer in memory (`cliDetector`: one run at a time; all ready kept 10 min, anything else 60 s), detects in the background at start, again when any terminal session exits (he may have signed in or installed inside it), on Agent tools' Refresh, and when `GET /api/terminal` finds a stale answer with an `unknown` CLI (in the background: the read never waits; a `missing` one is not re-detected per minute, it would run the login shell each time); `ensure` waits at most 8 s for a detection, then picks from the last answer; the doctor detects fresh. `HUB_TERMINAL_SHELL=fake` or `HUB_AGENT_TOOLS=fake` answer both ready. `pickPreset` decides what an automatic start runs: the first READY CLI in `agent.default`'s order; else Claude Code installed but not signed in (its first screen is its own sign-in); else Shell (Codex not signed in is never picked by itself: its sign-in inside the generated `CODEX_HOME` is untested); unknown facts keep the config order; no project: Shell. The admin calls `ensure` when the column becomes visible (the strip, Ctrl+`, the phone's button, or a column restored open from storage once the page is visible), once the shell knows the address's project (v0.12.10: a column restored open after a restart read the terminal state before the projects and started Shell with no project), and no session of that project runs, at most once per project per page load; a collapsed strip on page load starts nothing, a crashed start is never restarted. When the pick was not the first choice one quiet line under the tabs says why, ending in the fix with a copy button ("Codex: Claude Code is not signed in · claude auth login"). The `+` menu stays the switch: a CLI not installed is disabled with its reason, one not signed in says so and still starts. On a one-project instance the terminal has that project on every route (Connections included); with two or more, Overview and Connections keep Shell only. The memory of one idle session (Claude plus the stdio MCP servers it spawns) is not measured yet.

**After a reboot (P67, decision 0033).** The instance's LaunchAgent starts the server at login, so the strip is there without a terminal; nothing starts in it until the column is opened (P57: a collapsed load starts nothing, and the agent opens no browser). Shells of the dock then run under launchd's job, a different responsible process from Terminal.app for macOS privacy prompts (Automation to Mail, folder access): the owner allows each once.

**The automatic start resumes the project's last session (P64).** After a restart (`hub up`) `ensure` does not start a blank agent: it asks `@hub/log/resume` `chooseResume()` for the picked CLI's last session of THAT project in the session log (`state/log/<slug>/`, P54): the newest by its last event within 24 h (`RESUME_MAX_AGE_MS`, a constant), with at least one prompt (the idle session an earlier automatic start left is skipped), a `transcript` the log named that still exists, the same `project` and `cli` on the events, and for Codex a rollout inside `state/codex/<slug>/`. Found: the argv gets `--resume <uuid>` (`hub agent <slug> --cli <x> --resume <id>`, still a fixed argv; `presetArgv` refuses anything but a UUID), the tab title ends in "· resumed", and the quiet line says "Resumed the Claude Code session of HH:MM (8d31964d). + starts a new one."; else a fresh start as before. The `+` menu (heading "New session", `POST /api/terminal/sessions`) never resumes. The launcher checks the id again against the log (`hub agent --resume` typed by hand gets the same isolation) and starts fresh with one line when it cannot; a resume whose CLI exits non-zero within 15 s (an unknown id: Claude "No conversation found", exit 1 in about 4 s; Codex "no rollout found", exit 1) gets ONE fresh start, said in one line; a resumed session that ran longer is never restarted. `hub agent` / `hub agent continue` resolve the bound project's last logged session the same way (no cut-off): the hub never passes Claude's `--continue` or Codex's `resume --last`, because every project's session runs in the instance root and `--continue` takes that folder's newest conversation, whichever project it was. Safety, measured 2026-11-19: Claude 2.1.220 applies every flag of the resuming process (`--settings` with its deny rules and hooks, `--strict-mcp-config --mcp-config`, `--disallowedTools`, `--append-system-prompt`), keeps the session id and the context; a resume is a new process, so it gets the current settings' hooks. Codex (measured on 0.153.0) re-reads `config.toml` on resume (a sandbox change applied) but keeps the developer instructions the session STARTED with (the hub's binding prompt, session rules and project identity): so a Codex session is resumed only when its rollout's first developer message equals `sessionInstructions()` now, else fresh ("Codex keeps the rules a session started with ..."). Not handled: a session still open in another terminal (Terminal.app) can be resumed a second time by the dock.

`node-pty` 1.1.0 (the one native dependency) ships `prebuilds/darwin-*/spawn-helper` without the execute bit under pnpm; the server sets it at start (`ensureSpawnHelper`, P66), `agent.terminal`'s apply and `hub core update` set it too, and the doctor row checks it. Tests: `HUB_TERMINAL_SHELL=fake` runs `app/test-support/fake-shell.mjs` and is refused without `HUB_DB`.

**Open in Claude Desktop is not offered (P61 section 9, owner item 7).** Claude Code's `/desktop` (and `claude --desktop --resume <id>`, Claude Code 2.1.285 or later) would continue a dock session in the desktop app, which starts its own process without any of the hub's rules (no deny list, no guard hook, no strict MCP set, no binding prompt; the claude.ai connectors, Gmail `send_message` among them, reach it directly): decision 0011 would not hold there. So the registry declares `agent.openInDesktop` with `offered: false`: the handoff row of the tab's tips (below) shows the button disabled with its reason on a Claude Code tab ("Not offered: Claude Desktop would run this session without the hub's rules") and on a Codex tab (the ChatGPT app keeps its own sessions and settings), none on a Shell tab or off macOS; `POST /api/local/agent.openInDesktop` answers 501 with the same sentence and `hub open agent.openInDesktop` exits 2. Nothing runs `claude --desktop`, writes into the PTY or opens a `claude:` link; `claude --desktop`, `codex app`, `hub open` and a bare `open` are in the deny rules and Codex's forbidden prefixes. The owner may still type `/desktop` himself, knowing what it drops.

**Tips per tab (P63 patch B).** Beside Close, an ⓘ button ("Tips for Claude Code", "Tips for Codex", "Tips for the terminal" on Shell) opens a popover like `?`: the open tab's CLI's tips and the Hub's own, from the one list `@hub/contract/tips` (Help shows all of them, grouped). Claude Code: `/voice` (hold Space to speak, `/voice tap`, `/voice off`; a claude.ai sign-in, not an API key; not yet tried in the dock, where macOS asks for the microphone for the app that started the Hub), `/resume` (its list shows every project's conversations: pick this project's), `/desktop` (not offered, why, and the disabled button). Codex: the last conversation comes back on opening, `/app` (not offered). The Hub: "ответь" / "перепиши короче" on the draft on screen, ⌘ Enter saves an edit, Hide stops nothing. Each CLI row carries `verifiedOn`, the version its keys and commands were checked on (its `--help`, the slash-command table in its binary, its docs; Claude Code 2.1.220, Codex 0.153.0); `hub doctor --only Agent` row `agent.tips` (an audit) warns when an installed CLI is newer, so the rows are checked again after an upgrade. Nothing in the popover types into the session.

**Drop a file on the terminal (P76, decision 0041).** A browser never hands over a dropped file's path (a Finder drag reaches Chrome as `types: ["Files"]` only), so the dock copies the file into the instance and pastes that copy's path. While a file drag is over the open tab's terminal (`@hub/ui/product/terminal`, `drop.ts` classifies the drop) the box shows a ring and "Drop to paste the path"; on drop the session pane checks the count and size (10 files, 20 MiB: the line names the file and the limit, nothing is pasted), posts the files to the drop route above, and pastes the answer through xterm's `paste`: each absolute path, bare when it has only letters, digits and `._/@+-`, else backslash-escaped as Terminal.app types it, one space apart and one space after, so he keeps typing and nothing is sent before Enter. The pane's status line says "1 file pasted" or why not. Dropped text or a URL is pasted as text (C0 controls other than tab and newline removed, at most 100 000 characters), no request. A folder is refused ("Folders are not taken: drop the files, or a zip of the folder."). A file dropped anywhere else in the admin is swallowed by the shell frame's guard (`features/shell/use-file-drop-guard.ts`, file drags only, so a text drag into an input still works) and never opens in the tab. Whether Claude Code or Codex turns a pasted image path into an attachment is theirs; either way the path is text the agent reads with its tools. A session of another project cannot read the folder (deny rules, the Codex profile).

## Shared focus: the agent sees what the owner sees (P51, decision 0029)

"Ответь этому клиенту" or "ответь по этой записи" in the dock needs no explanation: the session knows what the admin shows, on every screen.

- **The admin publishes its focus, by refs.** The shell frame's publisher (`apps/admin/src/features/focus/`) posts this tab's focus to `POST /api/focus` 300 ms after it settles, again on window focus and visibility (the last focused tab wins), every 60 s while visible, and clears it on `pagehide`. Every route posts the same fields, derived from the router, never from a hand list of screens (P72): the route id, its title from the route table (`screenTitleOf`: "Knowledge", "Draft 42", "Mail"), and refs, domain ids written `<kind>:<id>` (`draft:42`, `client:7`, `run:10`, `knowledge:<index path>`, `project:<slug>`; `@hub/contract/focus` `REF_KINDS`, `parseRef`): `subject` (the record the address or the open card names: the Drafts card, `client:7` on `/log?client=7`, P73), `pointed` (the last row in `#main` that got keyboard focus or a click, never hover, until another row takes it or the screen changes), `selected` (at most 200), `window` (up to 30 refs of the rows on screen and the list's total), `view` (the address's search state) and `pointer` (the outcome of the agent's last highlight). A screen joins by putting `agentRef(ref)` on its rows (`data-agent-ref`) and, when it opens a record its address does not name, calling `useFocusSubject` (`lib/focus.ts`); `test/focus.test.ts` runs every route of the table. The route is as strict as the send and terminal tickets (exact admin Origin, loopback Host, `Sec-Fetch-Site: same-origin`, a strict body): a forged focus would steer the agent. The server keeps the last one in memory and in `state/focus.json` (`schema: 2`; ids and refs only, no title, name, subject or body, no secret; mode 600; written only when it changed, the heartbeat at most once in 50 s; a `schema: 1` file reads as none). A hidden tab never replaces another tab's visible focus. No database table; the focus has no live topic and no GET.
- **One reader, one resolver per ref kind.** `readFocus` (`@hub/agent/focus`, `src/focus/read.ts`) reads the file and resolves each ref in the database opened read-only, scoped to the bound project, by its kind's resolver (`src/focus/resolvers/`: draft, client, run, knowledge, project): its title (client data, cut to 120 characters), its status and `read`, the server, tool and arguments that read it (knowledge-mcp `knowledge_get` with the entry's path, `draft_show`, `client_show`; `null` for a run and a project, which no tool reads yet). A ref of another project or a deleted one drops out; a kind without a resolver fails the package's test. States: `fresh` (visible, at most 10 minutes old), `stale`, `elsewhere` (another project: named nowhere), `none`. The prompt hook reads at `depth: "line"` (the subject and the pointed row resolved, the selection and the window counted); the `focus` tool and `hub focus --json` read everything.
- **`hub mcp`, the hub's MCP server** (stdio, server name `hub`, `HUB_PROJECT` required, database `readonly`; `draft_write` and `highlight` alone bump the live counter through a short separate connection, `bumpTopicIn`, P53): `focus`, `highlight` (P72: the pointer, below), `draft_show` (`draft`: its id, the same name `draft_write` takes, P83; status, recipients, `mailRef`, excerpt, reason, marks, evidence, context, Notion link, follow-up step, Activity; never the body: decision 0013), `client_show` (by id or email), `drafts_list` (a view of the Drafts list), `mail_brand`, `project_notion` (P82: the bound project's Notion databases by id, the same parse as the capabilities line), and `messenger_history` (P71 M2: one linked Telegram or WhatsApp chat, or a client's linked chats, with the chat's rules and its open draft), all read-only; `messenger_draft_write` (P71 M2 and M2b), the one messenger write: ONE unsent row in `messenger_drafts` of a linked chat (a short write connection; never a send, and no send tool exists), refused in code by the chat's rules (`reply_off`, `no_inbound`, `not_requested`, `no_nudge`, `too_soon`, `already_drafted`; `not_linked` for an unlinked or another project's chat, named nowhere), with the guard asking for a `messenger_history` read of that chat first (skill `triage-messages`); and `draft_write` (P52), the one Mail write: an unsent reply draft in the bound project's Mail account, a revision replacing the older hub draft of the thread. A revision names only the hub draft (`draft`: its id; P53): the hub finds the message it answers by the `mailRef` Message-ID in the project's accounts (INBOX first, about 3 s, then the other mailboxes, Sent included since P85), so the agent looks nothing up in mail-mcp. A `sent` draft is refused `already_sent` before Mail is asked (P83). A new message on the owner's words (P85) is a new reply with `owner_request` (his words, verbatim) to the newest message of the client's latest thread, ours in Sent or theirs: a message whose drafts are all finished then gets a new draft; a reply to our own message goes to that message's recipients minus ours (`no_recipient` when none). Every refusal of `draft_write` carries `retry` (`now`, `after_owner`, `no`) and `next`, the line for the owner (`WRITE_ADVICE`, `@hub/agent/mail-drafts`); only `mail_not_allowed` (osascript -1743) names a macOS permission, and `mail_not_running` says the Hub does not open Mail itself (opening it sends its Outbox, decision 0030). No send; the only rows written are `draft_write`'s records (P65) and `messenger_draft_write`'s drafts, each on a short write connection, and the names stay clear of `SEND_LIKE_TOOL`. Registered by `hub agent` in Claude's strict MCP file and in the Codex home like `knowledge-mcp` (`HUB_MCP_SERVERS`; taken from the core's `config/mcp.json` even when an instance's file predates it), so `mcp.present.hub` and `mcp.answers.hub` are Agent tools rows with no new code.
- **`hub` on the session's PATH (P52).** `hub agent` writes `<state>/bin/hub` (runs this instance's pinned core on the hub's Node with this `HUB_HOME`) and puts it, then that Node, first on the session's PATH, so skills and rules call `hub ...` in either CLI and in the sandbox.
- **The project's identity (P52).** After the session rules, `projectIdentity(slug, mail)` names the bound project's Mail accounts, addresses, aliases and `mail.domains` from `project.md` as its own mail.
- **Session rules from the core.** `sessionRules(slug)` (`@hub/agent/session-rules`) is appended to the binding prompt of both CLIs (Claude `--append-system-prompt`, Codex `developer_instructions`): "this client" means the focus, never ask what is on the screen, a reply request revises the focused draft (`skills/triage-mail/SKILL.md` section 2r), never send. The core `AGENTS.md` carries the same text; a docs test keeps them equal. Instances copy nothing.
- **One hook, because MCP cannot push.** Both CLIs run `hub focus --hook` on `UserPromptSubmit` (Claude: the generated settings; Codex 0.146: `[[hooks.UserPromptSubmit]]` in the generated `config.toml`, run with `--dangerously-bypass-hook-trust`, which skips only Codex's hook trust for the hub's own hook in a home only the hub writes, never the sandbox). It adds one `[Hub focus, data]` line while the focus is fresh (or says the admin shows another project), nothing otherwise, and any error is silence with exit 0. The line is generic and at most 400 characters: `[Hub focus, data] Knowledge · on knowledge:…/csv-export.md "Can I download everything…" approved (knowledge_get) · 12 of 57 on screen · search "csv" · 12 s ago (call the hub focus tool for detail)`. `bin/hub.mjs` starts it without the CLI: measured about 0.45 s warm (tsx and the database driver), under the 5 s hook timeout.
- **The session log (P54).** The same prompt hook also writes the prompt and the focus line it added to the agent session log; `hub guard` writes each tool call, and `hub log --hook` the answers and the session: [25-agent-log.md](25-agent-log.md).
- **Revise, never send.** mail-mcp `replace_reply` (like every mail-mcp write) stays denied: it takes an `outgoing_id`, which exists only for a reply window open in the current Mail.app session (a draft from an earlier session is a saved Drafts message with no outgoing id: measured 2026-11-18, `list_outgoing_messages` empty while 70 drafts existed), and it leaves Mail's auto-saved old draft behind for a `delete_draft` the agent may not call. So a revision is `draft_write` of the `hub` MCP server with `draft` = the draft id (P52, P53): it saves the new unsent version with Mail in the background, then deletes the older draft of the same account, subject and marker (only after the new one is found), and `hub record-draft` with the same `mailRef` updates the same draft id: Checked goes off. The open card shows the new text by itself (live topic `mail`) and, after the record, says "Changed by the agent". A vague request ("измени ответ", "что угодно") is a work order: the session writes a revision and says in one line what changed, never asks about tone first; "do you see my page?" is answered from `focus`, never with an offer of browser automation (`sessionRules()`, P53). For a few seconds Mail still lists the replaced draft as deleted; the send skips such drafts. The dock header shows "Agent sees: <the screen's title> · <the open record or the row he is on, by the words on it>" ("Agent sees: Knowledge · Can I download everything…", "Agent sees: Draft 12 · Fiona"; the label is computed in the browser and never posted) so a wrong focus is visible before he types.

- **The agent may point, never act (P72, decision 0038).** `highlight({refs, note})` of `hub mcp` takes up to five refs from `focus` and a note of at most 80 characters; it is refused unless the focus is fresh (`not_looking`), for a ref that names nothing in the bound project (`unknown_ref`) and for more than five; `refs: []` clears. It writes `state/pointer.json` (`hubPaths().pointer`, mode 600, refs and an id, never a title; one pointer at a time, live for 30 s) and bumps the live topic `pointer`. The admin then reads `GET /api/pointer` (titles resolved inside the pointer's project) and `@hub/ui/product/spotlight` draws a ring on each `[data-agent-ref]` row in `#main` (a live query at draw time, at most 800 ms wait for it to be visible) with "Agent: <note>" as text, announced in a polite status region; it scrolls the first row into view once (`block: "nearest"`), never while he types in a field or the terminal. Escape, a click anywhere, a route change or the 30 s remove it; nothing else on the page changes. A ref that is not on this screen is listed in the dock header, "Agent points at: <title> · Show"; Show is his click (`destOfRef` in `routes/resolve.ts`), and the ring is drawn on the screen he opens. The outcome (`shown`, `not-on-screen`, `dismissed`, `expired`) rides in the next focus post, so `focus.pointer` tells the agent whether he saw it. No tool clicks, fills, types, opens, navigates or sends; the PostToolUse guard ledgers every `mcp__hub__*` call. The pointer flows from the agent to the admin, which is why it alone has a GET and a live topic (decision 0038 point 5).

- **The model and the advisor, per project (P55).** Settings ▸ Agent's Agent group writes the `agent_settings` row of the project (the database, beside the safety rules; `GET`/`PUT /api/agent-settings`; absent row = `DEFAULT_AGENT_SETTINGS`: Sonnet, advisor off, Fable remembered). `hub agent` reads it at every start (`readAgentSettings`, read-only; the default when the database cannot be read) and `claudeSettings` pins it in `state/projects/<slug>/settings.json`, so a hub session never inherits the owner's personal `model` or `advisorModel` from `~/.claude/settings.json` (`--settings` is the flag layer, above the user's file, and a key it leaves out falls through): `model` always; advisor on, `advisorModel`; advisor off, no `advisorModel` and Claude Code's own off switch `CLAUDE_CODE_DISABLE_ADVISOR_TOOL=1` (in the file's `env` and in the child's environment, the authoritative copy). With the advisor on, one rule line (`ADVISOR_RULE`) follows the binding prompt in Claude's `--append-system-prompt`: consult before changing project instructions, before a draft on thin evidence or for a hard client, before a step that cannot be undone; not for lookups, not against the owner's explicit instruction. It is not in `sessionRules()` (shared with Codex and `AGENTS.md`). A change applies to the next session start; a running session is never restarted. Codex keeps its own default model and has no advisor. Read from Claude Code 2.1.220's own text, not from a run: `advisorModel` is `string().optional()`; the advisor needs a main model with an advisor rank (the aliases `sonnet`, `opus`, `fable` have one) and an advisor at least as capable (both choices are); the account must have the advisor feature.
