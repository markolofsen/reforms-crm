# 06. Local admin app (the agent's own interface)

Status: built (`app/apps/admin` and `app/apps/server`; screens Overview, Drafts (home), Activity, Knowledge, Settings (Sending, Mail, Agent, Connections, This Mac), Help; Client planned). Next.js (decision 0015). English UI only.

## What
A small local web app (Next.js + React) on the owner's Mac. It shows what the agent did and holds the owner's decisions, nothing else (decision 0025): the drafts the agent left unsent in Mail, each with its reason and checks; what the agent did with every client, one group per session; the project's standing. The owner reads, then sends one draft at a time, skips, holds, marks done, flags a client or stops sending. Preparing (choosing clients, a brief, enrolling in follow-ups, sorting) is a phrase in a session; the admin has no form for it and shows the result. The agent may also change the app's own screens while the owner uses it (live edit); the dev server's hot reload shows the change at once.

Agents reach Mail and Notion through their own connectors (`mail-mcp` for Apple Mail, the session's Notion connector); the hub gives them local tools (`hub record-draft`, `hub record-client`, `hub sequences`, the knowledge MCP, the `hub` MCP with `draft_write` for Mail drafts, the guard) and the database; the admin shows the state those leave.

It replaces a hosted helper app and, over time, the screens of a hosted back office that the agent now covers.

## Why local
- No hosting, no auth layer, no deploy chain: one owner, one Mac.
- The agent can read and edit the code of the app it serves; a hosted app cannot be changed that way.
- Data stays on the Mac: mail in Apple Mail, working state in `data/app.db` and `state/` under `HUB_HOME`, Notion through its MCP.

## Components
Base: coss ui (https://coss.com/ui), built on Base UI + Tailwind v4, shadcn-like registry plus a
particle catalogue of ready patterns. Skills `coss` and `coss-particles` are installed globally
(`~/.agents/skills`, symlinked to Claude Code). Rules from the skill that bind us:
- use existing primitives and particles first; do not invent APIs, check the docs;
- Drawer replaces Sheet; Hub's own rule is stricter: no dialogs or sheets for primary work, use inline disclosure;
- Tailwind v4 and `@base-ui/react` required.
- The copies and the product primitives live in the package `app/packages/ui` (`@hub/ui`), imported by subpath (`@hub/ui/button`, `@hub/ui/product/action-button`, `@hub/ui/cn`) with the tokens in `@hub/ui/styles.css`; the admin keeps only what knows its routes, hooks and API. Rules: `app/@rules/architecture-and-ownership.md` rule 15.

## One source per fact (decision 0009)
Notion is the one place for client records; Mail is the one place for the text of a draft. The admin database
holds only what exists nowhere else.

| Data | Lives in | Admin database |
|---|---|---|
| Client profile, leads, tasks, documents (reports are documents, decision 0022) | Notion (the agent writes it through the connector) | only the key: a `clients` row (project, email, name, replies owed, last contact, `updated_at`), made when the agent records a draft for that client. Nothing is copied in bulk; there is no sync |
| Draft text | Mail (an unsent draft the person edits and sends) | no copy: `drafts.body` is empty for a recorded draft (an optional 240-character preview at most); `mail_ref` points at the message |
| Draft review state ("I read the checks", done, hold, skipped), marks, batches, follow-up enrollments, the agent's run log | admin database only | yes |
| Project facts, filters, knowledge | files under `<projects folder>/<slug>/` (`<HUB_HOME>/projects`; see `08-local-app-stack.md`) | an index rebuilt from them |

A session reports each unsent draft it leaves with `hub record-draft --project <slug>` (JSON on stdin; one JSON line out, exit
0 only when it says `"ok":true`). The command writes straight to the database (no server needed), makes the client row if
it is missing, and keeps one open draft per client: the same `mailRef` again updates it, another one marks the old draft
`skipped` and inserts the new one. It never deletes a client (marks and the log hang on that row) and never writes `sent`.
Sent detection (`14`) finds a recorded draft in the project's Sent mailbox in Apple Mail once the person has sent it from Mail.
Because Notion owns the client record, the admin has no company or deal-value column, no "High value" filter and no `{company}` placeholder.

**The standing of a project** is a pure function of local facts (for example Stop sending, a failing Sent loop or doctor check, held suspicious mail, failed or stuck sends, the project still a draft, sends limited to the test list, the fake Mailer, the auto-send cap, expired knowledge, never triaged), so the status line and the Overview read one source and a model writes no sentence. The worst fact wins and is said once ("Sending is stopped", "Test mode: sends go to the test list only", "All clear"); test mode is a setting the owner chose, so it is level clear: said when nothing worse is, never a dot or a "Needs you" item (UX pass 2026-11-20), while expired knowledge is attention. `next` names the one page that fixes it (P70: Settings ▸ Sending for sending, the cap and test mode; Overview for what is fixed by a phrase in a session, a failing setup check, a draft project; Knowledge for expired entries; the other Settings panes for their parts), and that page carries a dot in the nav (a child's dot also lights its parent, and a parent in the phone's More lights More); an Agent tools row that needs a fix or a look puts the dot on Settings ▸ Agent, and every part Overview lists under "Needs you" lights the page it links to, so a dot and its item always come together. The to-review count belongs to the nav and the View menu and is never repeated in the line. Paused and archived projects raise nothing.

The Notion token is optional for setup (`hub setup` asks for nothing; `hub setup --automation`, `./run.sh token notion` or Settings ▸ Connections store it in `state/secrets/notion-token`, or in the file a project names in its settings; a project that names its own file never falls back to the shared one). It is read by the project doctor's database check, `notion-dump` and backups; the admin's home shows no Notion count.

What the Overview never carries: a client's name, address, subject or body, a deal value, a Notion property or a Notion page id of a record. The schemas have no field for them and refuse a stray one.

## Live updates (P50, decision 0028 in the owner's plan repo)
While the agent works (in the terminal column or another window) the screens update by themselves, within about a second, with no reload:
- **What changed is written by the database itself.** Migration 0019 gives every table three triggers (insert, update, delete) that bump one counter (`live_seq`) and record `(table, project, counter)` in `live_versions`, inside the writer's own transaction, whoever writes: the server, `hub record-draft` in a terminal, a migration, `sqlite3` by hand. A rolled-back write records nothing. The table holds one row per table and project, so it never needs pruning and every counter stays a resume point. What is not a row is watched by the server and bumped through the same path (`bumpTopic`): the pollers' state (`health`), the Connections files (`connections`, so a `hub token` in a terminal shows at once) and, per project, the agent session log's day files (`agent-log`, P59: a watch with one signature per project folder of `state/log`, every 500 ms; the `.cursor/` folder is not compared), the LaunchAgent (`autostart`, P67: `state/autostart/starts.jsonl`, the off file and the switch, every second; not its log), and the core update check (`core`, P68: a finished check or a changed `state/core-update.json`, every second). A new table needs its triggers in its migration; `packages/db/src/live.test.ts` fails without them, and the server's `Record<LiveTable, LiveTopic>` fails `tsc`.
- **The server tails it.** Every 200 ms it reads the counter (one page); when it moved, it reads the changed rows, maps each table to one of 13 topics (`@hub/contract/live`), waits 100 ms to merge a burst, and sends one frame on `GET /api/live`. A client still busy with the last frame gets one `reset` instead of a queue.
- **The admin invalidates, it is never pushed data.** One tab per browser holds the Web Lock `hub-live` and opens the EventSource (HTTP/1.1 allows about six connections per origin across all tabs); it passes every frame to the other tabs over a `BroadcastChannel`. Each tab invalidates the query keys of the frame's topics (`TOPIC_KEYS` in `apps/admin/src/lib/cache/keys.ts`, the one key factory), so only what changed is read again, through the normal API and its contract parse. A hidden tab only marks its queries stale; its focus refetch catches up. A row change never reads Mail (decision 0013): the open draft's text in Mail is read on open, on focus and on the one Mail topic, `mail`, which `draft_write` bumps after it wrote a draft of the project (P53), so a revision by the agent shows on the open card within about a second plus the Mail read. When the agent re-recorded the draft under an open card, the card also says "Changed by the agent since you opened it" with Reload. When Mail holds more than one draft of the thread, the card shows the one the Hub recorded (else the newest) and names every Mail id, saying which one the Hub wrote, so the owner keeps one; that text has no hash, so it cannot be Checked and the send refuses it. The address names the card on screen: a wide pane replaces a bare `/drafts` with the first row's `/drafts/<id>` (routes rule 9). New Activity sessions are announced in a polite live region ("2 new").
- **The agent activity feed (P59).** The sidebar's footer shows the last five things the agent did in the project (`GET /api/projects/:slug/agent-feed`, read from the tail of the session log, labels computed on the server: [25-agent-log.md](25-agent-log.md)), refetched on the topic `agent-log`. A row is the time, a label ("reads draft 3", "asks you a question") and, when it names a draft, a link to its card; nothing else is a control. The terminal strip's dot (and the phone's terminal button) takes the attention colour while the agent waits on the owner, until he opens the column. One tone per turn that ended (attention, ready, problem; synthesised by `@hub/ui/sound`, muted by the speaker switch in the footer; only the tab holding Web Lock `hub-sound`, after a click in it, plays, and that tab refetches the feed even when hidden).
- **The fallback is the pulse.** The Drafts status line says "Live" while the stream is up and "Reconnecting, data may be old" after 5 s without it. While it is down, the page polls `GET /api/pulse` every 10 s as before P50 and refetches every list when the database file moved; a stream the server cut (a restart: the `/api` rewrite answers 500) is opened again after 1, 2, then 5 s, resuming after the last frame the page applied. The Activity and Overview timers are gone.
- **Through the `/api` rewrite.** The stream goes through Next's rewrite like every call, so `proxy.ts` and the Host guard apply unchanged and no ticket is needed (a cross-origin page cannot read a same-origin stream without CORS). `Cache-Control: no-cache, no-transform` is load-bearing: without it Next gzips the proxied stream and holds every frame (measured in the L0 spike: 0 frames in 8 s; with it 1 to 4 ms per frame, and a stream with only 15 s pings stayed open past 165 s under the 120 s `proxyTimeout`).

## What a screen shows by default
Each screen opens on what the next decision needs and keeps the rest one step away (`app/@rules/admin-principles.md`). Drafts has one View menu with counts (`DRAFT_VIEWS`, `app/apps/admin/src/routes/search.ts`; the view is `?filter=`): To review (`ready`), Hold, Thin basis (`thin_basis`: drafts whose record says too little was read), Finished (done, sent, skipped), Follow-ups (`sequences`, the open steps of a follow-up sequence, [23-sequences.md](23-sequences.md)), Not by email, All, and the batches read-only (`?batch=`). Above the list sits one status line, never a paragraph or an accordion. A row is three lines (name and time, the subject on the full width, a line of chips); selecting turns the list's header line into "N selected · Skip · Hold · Clear" in place, so nothing moves. The list footer "N of N loaded" shows only when there is more to load. A failing setup check is a "Needs you" item on Overview, named with its detail; passing checks are not listed (`hub project doctor <slug>` lists them all). An Open lives on the thing it opens (P70, `app/@rules/admin-principles.md` rule 12): Knowledge's header has Open folder and each entry row its Open; the files no screen lists (`project.md`, the project folder, Workflows, today's agent log) are on Help; off macOS (`localOpen` false) none of them renders. A mechanical cap holds the first viewport to 36 tab stops and the first draft on a phone to 200 px down (`app/@rules/ui-specifications.md` rule 4a).

## Rules
- The agent only creates drafts. The app sends only when a person confirms one draft (decision 0011, `16` section 3B): Send on a ready draft whose checks the person read ("I read the checks", bound to the Mail text they saw), with the exact mail shown first, through the one route `POST /api/projects/:slug/drafts/:id/send`, whose apply needs the page's single-use ticket. Bulk = many drafts, never sent in bulk.
- The terminal column (always there; when no tab can start it says why and the fix, P66) runs Claude Code, Codex or the owner's shell for the project in the URL; opened, it starts the best ready CLI by itself (P57: Claude Code first, one line when it fell back); it is a viewing preference in `localStorage`, never URL state ([24-terminal.md](24-terminal.md)).
- Bind to 127.0.0.1 (`next dev -H 127.0.0.1`: without the flag Next listens on every address); no remote access in the first version. Next has no DNS-rebinding guard of its own, so `src/proxy.ts` refuses any Host that is not a loopback name and any write whose Origin is not; the API repeats the check.
- The tab publishes what it shows (P51): the agent in the dock reads it as "this client" through `hub mcp` and the prompt hook; the selection stays component state shared in memory (`lib/focus.ts`), never URL state ([24-terminal.md](24-terminal.md)).
- Open and Reveal (P61) show a fact in the program that holds it (Mail, Notion, Finder, the file's own app) and change nothing in the Hub. One registry declares them (`@hub/contract/local`); Mail and Notion are plain links, a file or folder goes through `POST /api/local/:action` with a key. `hub open` is the owner's terminal form; the agent is denied it and a bare `open` (`app/@rules/admin-principles.md` rule 1).
- English only, per the owner.
