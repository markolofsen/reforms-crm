# Project setup (interview, no UI)

> Layer: **core** (universal). Project names, people and addresses in this file are examples; one owner's facts live in `projects/<slug>/` (custom). Rule: `@docs/LAYERS.md`.

Spec: `@docs/core/16-projects-and-knowledge.md` (read sections 3, 3C and 8 first).
**One project per set of mailboxes; a brand is a row.** Products whose mail reaches the same accounts (forwarded domains, aliases) are rows of `## Brands` in ONE project, never a second project: never create `<product>-support` on a mailbox another project already reads (the account claim refuses it, and it would split one client's history). You do all the work; the owner only answers.
Talk to the owner in Russian, briefly; every file is English. Never send mail. Never set or change the send policy (`send.*`, `draft.recipients`): it is `state/projects/<slug>/send-policy.json`, outside your reach, and only the owner changes it with `hub send policy set` in his own shell; never write those rows into `project.md` (they are ignored and fail the doctor). Never write a secret value, only file names. One session, one project (`skills/README.md` Rules, item 2): set up only the slug named; asked for another, say to start `hub agent <other>`.

## Modes
- **new**: no `projects/<slug>/`. Go to step 1.
- **adopt**: the folder has `project.md` without `## Settings` (a folder that predates schema v1). Keep the databases list untouched; ask only for missing required fields.
- **resume**: the owner says "continue setup" or `project_questions` has an open row. Read it, ask that one question, then continue from step 5.

## Steps
1. **Read before asking.** Read `project.md` (if any), its `## Answers`, and open rows of `project_questions`. A field that has a Settings row is decided: do not ask it.
2. **Derive what you can**, silently:
   - `mail.accounts` from `list_accounts`; `mail.addresses` and `mail.sender` from those accounts' addresses.
   - Notion databases: `notion-search` for the project's teamspace, `notion-fetch` the Clients, Leads and Reports data sources (a Knowledge database, if one exists, is not used: ignore it unless the owner wants it migrated); take the `collection://` ids.
   - `languages`, `timezone` from the host and the mail you can see.
3. **Ask, one question per message**, in this order, skipping any already decided. Each: what, why (one clause), your proposed default, at most three options.
   1. Name and slug (propose from the domain or teamspace; slug is `[a-z0-9-]+`; a later change is `hub project rename <old> <new>`, never a hand-moved folder). Then the **kind**: run `hub project kinds`, pick the one that fits what the owner described (default `generic`), and confirm it in the same message as a proposal, not a separate question. The kind decides which fields are required (a `shop` needs no Notion databases, a `sales-pipeline` also needs `leads`) and which modules `doctor` checks. A project that fits none stays `generic`; do not invent a kind (adding one is a code change, doc 16 section 3A).
   2. Mail: confirm the derived accounts, addresses and sender; ask for form-lead and alias addresses only if the owner has them, and for `mail.domains` when other domains forward into these accounts.
   2b. Brands (only when the project receives mail for more than one product: several `mail.domains`, or accounts of different products): one message naming each product with its addresses and domains, the names to be exactly the Notion `Brand` options; then the sign-off line (`signoff`, one for every brand, no text proposed); then the signature per brand (who signs, the product, the site; one answer per brand, or one pattern for all); then `knowledge.scope` (asked only with two or more brands; propose `shared`, offer `by-brand`: "each product's facts stay apart"). Write them with `hub project setup <slug> --signoff "<line>" --brand "<Brand>=<addresses, domains>" --brand-signature "<Brand>=<line><br><line>"` (one flag per brand; the hub validates every address against the project's own) or edit the table by hand in the layout of doc 16 section 3C. Every row's Answered date and `By`; an empty Signature is allowed while `draft` (doctor warns) and fails once `active`. Never invent a signature text.
   3. Notion: confirm the found databases; if none exist, say so and offer to run the `notion-project-deploy` skill, then continue.
   3a. Notion setup for the Hub (one line to the owner, not a question; P97, `@docs/setup/access.md` section "The hub integration"): the hub integration needs Read content, Update content (the send stamp, a lead's Status and Client) and Insert content (one new Clients card for a lead at the first reply sent), and the whole teamspace shared with it. Where to tick them: app.notion.com → Developer tools → Developer connections → the connection "Hub: <Instance>" → Configuration → Capabilities → Content capabilities: tick Read content, Update content, Insert content (never a delete); the teamspace grant is the Content access tab of the same page. He ticks them himself; you never change an integration. Notion cannot report capabilities, so a missing one shows later as the doctor's `notion lead writes` row or a note on a lead card. If the project has a Leads database and its site sends notification mails (a `robot@…` sender), propose `leads.notice_senders` with those addresses.
   4. Knowledge: it is a folder of Markdown files (`knowledge/files/`), edited by hand and searched locally; nothing to choose. Ask about an old Notion Knowledge database only when `notion-search` in step 2 found one; otherwise ask only whether there are documents to bring in once. If the owner says yes, plan one migration with `knowledge-import`; Notion is not read again afterwards. Record `knowledge.source` = `files`.
   5. Tone: one line ("warm, brief, no exclamation marks"); offer 2 examples as options.
   6. Test mode: say that drafts go only to the test list (`allow_list` of `config/config.json`) until the owner runs `hub send policy set <slug> draft.recipients any` himself; record nothing for it.
   7. Connectors (P62; asked once per project, only when `hub connectors list` names any): which Google Calendar and Drive connectors this project's sessions may use, from any Google account (they are not tied to the mailboxes). Show each with its account and the projects that already attach it; propose none. Calendar only for a kind with the calendar module (`hub project kinds <kind>`); a support kind gets Drive only. Record `calendar.connector`, `drive.connector` (comma lists) and, when he names folders, `drive.folder`, each with today's date and `By=owner`; "none" is recorded as an `## Answers` row only. Then say: run `./run.sh agent <slug> --prepare` and sign in with `/mcp` in this project's Claude Code session (`@docs/core/26-capabilities.md` section 7). Adding a connector is his own command (`hub connectors add`), never yours.
   Never exceed six questions, plus the brand questions of 2b in a multi-product project (one per brand at most) and the connector question 7. Optional fields (`timezone`, `mail.mailboxes`, `run.*`, `notion.token_file`, `calendar.name`, `calendar.id`, `calendar.timezone`) take their defaults and are shown once at the end. `signoff` has no default text: without a `## Brands` table it may stay empty (a draft then ends with the body); with one it is asked in 2b.
4. **Record after each answer, not at the end.** Write or update the Settings row (value, today's date, `By=owner` for an answer, `agent` for a derived value, `default` for a default); append one row to `## Answers`; mark the `project_questions` row `answered`.
5. **Create the files** (new): `projects/<slug>/project.md` in the layout of doc 16 section 3, with the `kind` row right after `schema` (`By=owner` if the owner chose it, `default` for `generic`), `knowledge/files/` empty. Copy the starter workflows: `cp -R app/projects/_template/workflows projects/<slug>/workflows` (ten Draft playbooks the project then owns; none is picked by an agent until the owner sets `status: Active`; `hub workflows list <slug>`). Copy the starter follow-up sequences the same way: `cp -R app/projects/_template/sequences projects/<slug>/sequences` (two Draft files; the owner enrols clients in the admin; `hub sequences check <slug>`). Copy the kind's starting taxonomy: `hub project kinds <kind>` prints it as JSON; write its `audiences`, `category` and `stages` as `## <axis>` sections of `knowledge/taxonomy.md` (format: doc 16 section 5, "Taxonomy"; skip an empty axis). The project owns the file from then on. Then `hub dev init <slug> --apply`: the project's own `@dev/` kanban for its development plans (dry run first; it never overwrites). Leave `status: draft`. Outside `## Notion databases` write no `- key: value` list items.
6. **Run `hub project sync`, then `hub doctor --project <slug>`.** On a failed check, do not guess: report the check, then ask one correction question quoting the old answer (doc 16 section 8.6).
7. **Knowledge**: if `knowledge.source` is not `files`-only-empty, run the `knowledge-import` skill for this project.
8. **Activate**: when doctor passes, set `status: active`, `setup.doctor: <date> pass`, `setup.completed: <date>`, sync again. The recipients rule is the owner's command (`hub send policy`), never yours.
9. **Close**: print one summary: project, accounts and addresses, databases found, knowledge count, defaults applied, test mode on or off, next step.

## Checks (all must hold before you say done)
- `hub dev index <slug> --check` passes (the project has its `@dev/`).
- `project.md` parses (`hub project sync` exits 0) and `setup.doctor` says `pass` with today's date.
- Every field the project's kind requires has a Settings row or a section entry (`hub project show <slug>` prints the kind and any `missing_required`); no row duplicates; dates are ISO.
- No address, account or `mail.domains` entry is also claimed by another project (sync reports it).
- With a `## Brands` table: doctor rows `brands table parses` pass, `every project domain has a brand` and `every brand has a signature` pass (or warn only while `draft`, each warning named in the summary).
- `git status` shows only `projects/<slug>/` changes from you; stage explicit paths, never `git add -A`.
- You asked each field at most once, and a question you could not ask now is one open `project_questions` row.
