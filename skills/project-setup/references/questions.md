# The interview questions (project-setup step 3)

One question per message, in this order, skipping any already decided. Each: what, why (one clause), your proposed default, at most three options.

   1. Name and slug (propose from the domain or teamspace; slug is `[a-z0-9-]+`; a later change is `hub project rename <old> <new>`, never a hand-moved folder). Then the **kind**: run `hub project kinds`, pick the one that fits what the owner described (default `generic`), and confirm it in the same message as a proposal, not a separate question. The kind decides which fields are required (a `shop` needs no Notion databases, a `sales-pipeline` also needs `leads`) and which modules `doctor` checks. A project that fits none stays `generic`; do not invent a kind (adding one is a code change, doc 16 section 3A).
   2. Mail: confirm the derived accounts, addresses and sender; ask for form-lead and alias addresses only if the owner has them, and for `mail.domains` when other domains forward into these accounts.
   2b. Brands (only when the project receives mail for more than one product: several `mail.domains`, or accounts of different products): one message naming each product with its addresses and domains, the names to be exactly the Notion `Brand` options; then the sign-off line (`signoff`, one for every brand, no text proposed); then the signature per brand (who signs, the product, the site; one answer per brand, or one pattern for all); optionally ask for the visible From name when the shared mailbox serves multiple brands; then `knowledge.scope` (asked only with two or more brands; propose `shared`, offer `by-brand`: "each product's facts stay apart"). Write them with `hub project setup <slug> --signoff "<line>" --brand "<Brand>=<addresses, domains>" --brand-signature "<Brand>=<line><br><line>" --brand-display-name "<Brand>=<visible name>"` (one flag per brand; the hub validates every address against the project's own; the display name changes only the visible name, never the technical sender address) or edit the table by hand in the layout of doc 16 section 3C. Every row's Answered date and `By`; an empty Signature is allowed while `draft` (doctor warns) and fails once `active`. Never invent a signature text.
   3. Notion: confirm the found databases; if none exist, say so and offer to run the `notion-project-deploy` skill, then continue. If the owner says "обнови ссылки" / asks to refresh the menu, skip no unrelated setup question: reread the teamspace and replace only `## Links`, keeping manually named links whose targets still validate.
   3a. Notion setup for the Hub (one line to the owner, not a question; P97, `@docs/setup/access.md` section "The hub integration"): the hub integration needs Read content, Update content (the send stamp, a lead's Status and Client) and Insert content (one new Clients card for a lead at the first reply sent), and the whole teamspace shared with it. Where to tick them: app.notion.com → Developer tools → Developer connections → the connection "Hub: <Instance>" → Configuration → Capabilities → Content capabilities: tick Read content, Update content, Insert content (never a delete); the teamspace grant is the Content access tab of the same page. He ticks them himself; you never change an integration. Notion cannot report capabilities, so a missing one shows later as the doctor's `notion lead writes` row or a note on a lead card. If the project has a Leads database and its site sends notification mails (a `robot@…` sender), propose `leads.notice_senders` with those addresses.
   4. Knowledge: it is a folder of Markdown files (`knowledge/files/`), edited by hand and searched locally; nothing to choose. Ask about an old Notion Knowledge database only when `notion-search` in step 2 found one; otherwise ask only whether there are documents to bring in once. If the owner says yes, plan one migration with `knowledge-import`; Notion is not read again afterwards. Record `knowledge.source` = `files`.
   5. Tone: one line ("warm, brief, no exclamation marks"); offer 2 examples as options.
   6. Test mode: say that drafts go only to the test list (`allow_list` of `config/config.json`) until the owner runs `hub send policy set <slug> draft.recipients any` himself; record nothing for it.
   7. Connectors (P62; asked once per project, only when `hub connectors list` names any): which Google Calendar and Drive connectors this project's sessions may use, from any Google account (they are not tied to the mailboxes). Show each with its account and the projects that already attach it; propose none. Calendar only for a kind with the calendar module (`hub project kinds <kind>`); a support kind gets Drive only. Record `calendar.connector`, `drive.connector` (comma lists) and, when he names folders, `drive.folder`, each with today's date and `By=owner`; "none" is recorded as an `## Answers` row only. Then say: run `./run.sh agent <slug> --prepare` and sign in with `/mcp` in this project's Claude Code session (`@docs/core/26-capabilities.md` section 7). Adding a connector is his own command (`hub connectors add`), never yours.
   8. Booking link (P155, skippable, one message): «Ссылка для записи на звонок (Calendly и т.п.)? Если у брендов разные, по брендам.» Record `booking.url` (an https URL, or `none`; Enter skips it), and a brand's own in its `Booking` column (`hub project setup <slug> --brand-booking <Brand>=<url>`, or `none` for a brand that never offers one). The agent offers it once per conversation (`skills/README.md` rule 19).
   Never exceed six questions, plus the brand questions of 2b, the booking question 8 in a multi-product project (one per brand at most) and the connector question 7. Optional fields (`timezone`, `mail.mailboxes`, `run.*`, `notion.token_file`, `calendar.name`, `calendar.id`, `calendar.timezone`) take their defaults and are shown once at the end. `signoff` has no default text: without a `## Brands` table it may stay empty (a draft then ends with the body); with one it is asked in 2b.
