# State and data

Scope: where each kind of state lives in the admin. Adapted from the shared "state and data" page; the generated-client, store and SWR lanes collapse into TanStack Query (pull data) plus the URL plus component state. The app is a client of the Hono API: server components fetch nothing (P32 N3 tried one server-fetched first list and kept none).

## Rules

1. MUST: classify before writing. Server data lives in TanStack Query; navigation state (screen, subject, filter) lives in the URL; ephemeral UI state (an expanded row, a draft in an input) lives in the component. A fourth place needs a reason written in the PR. URL state is not query-cache state and not storage: the address holds screen, subject, filter and project; the remembered project is the cookie `hub_project` (so `proxy.ts` can read it before a page renders) and the shortcuts and rail switches are `localStorage`, both behind `lib/storage.ts` (`routes-and-url-state.md`); the theme choice is `next-themes`' own key (rule 7). The embedded terminal (P49) is a viewing preference, not screen state: three `localStorage` keys, `terminal` (open or closed), `terminal-width` (the saved column width) and `terminal-tab` (the active session); its sessions are server data (`GET /api/terminal`, in the Query cache) and its bytes go over the socket of `features/terminal/socket.ts`, the one module that owns it (a socket is not a fetch, so it does not pass through `read`).
2. MUST: a query key names the resource and every input that changes the result, built only by the one key factory `keys` in `lib/cache/keys.ts` (resource first, then the project, then the inputs, so a prefix names every view of one project). No component writes a key literal.
3. MUST: a mutation invalidates or updates the canonical query key, never patches a component copy.
4. MUST: one boundary reads an API reply. A legacy operation uses `read(schema, call)` in `lib/api/client.ts`; a migrated JSON operation uses the generated `@hub/api` function through `readGenerated` in the facade. Both paths own retry, error normalization, and runtime parsing, so a stale server fails with a sentence instead of a render crash. Error bodies are parsed, not cast; callers get types from the contract or generated Zod schema, never from a hand-written wire shape or a cast.
4a. MUST: generated operations do not own React Query or domain state. The root QueryClient and `keys` factory remain the only cache owners, and a facade invalidates the canonical key after a mutation; feature code never imports generated hooks, cache keys, or raw cache mutation APIs.
4b. SHOULD: domain data hooks or connected wrappers own `useQuery`, `useMutation`, `useQueryClient` and invalidation. Existing feature-level subscriptions remain a migration exception recorded in P111/P116; new features must not add another owner.
4c. MUST: composer state uses the discriminated `ComposerState` from `@hub/contract/composer`; body, draft identity, editing/recorded status, saving, error, blocked and unavailable data may not be inferred from independent optional flags or a local state union in a feature component. Features map their mutation flags through `composerStateOf`; the shared UI consumes the resulting state without choosing recovery or send semantics.
5. MUST: every list and mutation has all of: loading, empty, error (with Retry), stale or refetching, and partial result where the server can return one. A toast is never the only record of an outcome.
6. MUST: a mutating control disables while pending (no double submit) and reports the failure inline.
7. MUST: browser storage and the project cookie are touched in one module (`lib/storage.ts`), with try/catch, because they can throw or come back empty. Keys are defined there, never as a literal at a call site (`shortcuts`, `rail`, `terminal`, `terminal-width`, `terminal-tab`, and `sound`, P59: the agent sounds' mute switch, "off" when muted). The one exception is `hub-theme`, written and read only by `next-themes` inside `@hub/ui/product/theme` (`design-system-and-tokens.md` rule 10): the library owns it, so no admin code names or reads it. A stored value is read through `useStored` / `useRememberedProject` (`useSyncExternalStore`), never in a `useState` initializer (rule 11).
8. SHOULD: optimistic updates roll back on error and say so.
9. SHOULD: derive instead of storing; no `useEffect` that copies props or query data into state.
10. SHOULD: time-sensitive data states its freshness ("Live", "Reconnecting, data may be old", or "updated N min ago").
11. MUST: the first render is stable. The server renders HTML with no viewport, storage, cookie or clock, so a client component's first render must produce the same markup there and in the browser, or hydration fails (the largest new bug class on Next, research 19 section 6). Read the viewport, storage, the cookie and the clock through `useSyncExternalStore` with a server snapshot (`useMediaQuery` returns `false`, `useStored` and `useRememberedProject` return `null`), or only after mount (the shell gates its data views behind the frame's loading state, so `useClock`, `useMediaQuery` and the sidebar state run after the gate; a terminal saved open appears after mount, and is restored only from 1024px; the terminal's strip and the phone's terminal button draw an empty box of their size until mount, so the server HTML names no terminal). Layout that depends on width uses CSS breakpoints, never a width branch in the first render. Never `Date.now()`, `Math.random()`, `window` or `localStorage` in render or in a `useState` initializer.
12. MUST: Next caches no API data. Replies live only in the Query cache (`gcTime` as configured); the root layout is `force-dynamic`; the mail body of a draft is read live on every open and kept nowhere (decision 0013). That read and Sent detection are the only mail reads, both through Apple Mail (decision 0026): no screen shows a live mail count or a mail history, so no screen carries a freshness stamp for mail. A server-fetched first paint is not used; adding one needs a written reason and a single source of truth for that list.

13. MUST: live updates invalidate, they never push data (P50). One stream per browser: the tab holding the Web Lock `hub-live` opens the one EventSource on `/api/live` and passes its frames to the other tabs over the `BroadcastChannel` `hub-live`; both live only in `lib/cache/live.ts`. A frame is parsed with `parseLiveEvent` of `@hub/contract/live`; a `change` invalidates the keys `TOPIC_KEYS` names for its topics and projects (a `Record<LiveTopic, ...>`, so a new topic fails `tsc`), a `reset` or a frame the page does not know refreshes everything (`refreshData`). A hidden tab passes `refetchType: "none"` and catches up on focus, with one exception (P59): the tab that plays the agent feed's tones (it holds the Web Lock `hub-sound`, `@hub/ui/sound`; `setSoundHolder` in `lib/cache/live.ts`) refetches the feed on `agent-log` while hidden, because a tone heard with the admin in the background is the point. Only the topic `mail` names a Mail key (P53): it moves when the hub itself wrote a Mail draft of the project (`draft_write`), so the open card reads Mail again; a row change never reads Mail (rule 12). No screen adds its own `refetchInterval`: the pulse polls every 10 s only while the stream is down, and an open input is never overwritten by a refetch (a changed open draft says so, with Reload).

14. MUST: the shared focus (P51, P72 decision 0038) is published, not URL state. The shell frame's publisher derives it from the address, the screen's subject and selection, the row he is on and the rows on screen (`features/focus/derive.ts`, pure and generic over every route: the route id and the route table's title, never a list of screens) and posts it from `lib/api/terminal.ts` only. Every screen uses the one channel, `lib/focus.ts` (the store and its two hooks; in `lib`, since `hooks/` is at its eight files): its rows carry `agentRef(ref)` (`data-agent-ref`), a record it opens that the address does not name goes through `useFocusSubject(ref, label)`, its picked rows through `useFocusSelection(refs)`; `pointed` and `window` come from the two observers on `#main` (`features/focus/use-main-observers.ts`: `focusin` and `pointerdown`, never hover; an `IntersectionObserver`). Only refs are posted: a row's label stays in the browser for the dock header. None of it is stored or in the address. The agent's pointer is read on the live topic `pointer` (`GET /api/pointer`) and drawn by `features/focus/pointer.tsx`; its outcome rides in the next post. The server stamps the time; the browser's clock is never sent.
