# Routes and URL state

Scope: navigation in the Next.js admin (App Router): real paths, the project in the path when the instance has more than one (`/lisbon/mail/c/42?filter=all`) and no project at all when it has one (`/mail/c/42`). Local page: it began as an adapted copy of the shared "declarative routes" page and describes this app's own layer (decisions `0014` for the idea, `0015` for Next).

The layer, in one picture: `src/app/` holds only the files Next names (`page.tsx`, `layout.tsx`, `not-found.tsx`, `error.tsx`) and each page renders one client `features/<job>/section.tsx`; `src/routes/` (pure data and types: `table.ts`, `search.ts`, `paths.ts`, `typed.ts`, `resolve.ts`, `meta.ts`, `sections.ts`, `guards.ts`) declares every destination; `src/hooks/` (`use-route`, `use-project`, `use-go`, `use-search-state` (`useSearch`), `use-section-nav`, `use-hotkeys`: the remembered off switch of page shortcuts) read and move; the key dispatcher is `@hub/ui/use-hotkey`; `components/app-link.tsx` is the one internal link; `components/local-action.tsx` the one Open (P61: links built by `@hub/contract/local`); `lib/external.ts` hands a registry link to the system from code; `src/proxy.ts` runs before every request.

## Rules

1. MUST: `dest` in `src/routes/paths.ts` is the only producer of a destination (`dest("mail.conversation", { id: 42 }, { filter: "all" })`, a `Dest`; P127 A1: one builder over the route table, filling the row's pattern with its params and leaving out every default of its search). A path or address string literal outside `src/routes/` is a defect; `dest` takes the route id, its params and its search typed from the row, so a wrong route, param or value fails `tsc` (`test/paths.types.tsx`). Each row's pattern is checked against the file tree by `defineRoute` through `typedRoutes`, so a page that does not exist fails `next typegen`, `tsc` and `next build`; `route()` in `routes/typed.ts` does the same for a literal.
2. MUST: the only internal link is `AppLink`. It takes a `Dest` (`to={dest("mail.conversation", { id })}`), never a string and never a framework `UrlObject` (typed routes do not check one: P32 N0), and renders a real `<a href="/lisbon/mail/c/42">`. No exception (P70): the sidebar's core version line links Settings ▸ This Mac with an `AppLink`, like every other link; `/health` (the server's own facts, outside the shell, no `ROUTE_TABLE` row) is linked from nowhere in the shell and has no builder in `paths.ts`. A plain click moves through the framework router (the shell stays mounted); a modified click, another target and open-in-new-tab are the browser's. Code moves with `useGo()` (`go(dest(…))`, `{ replace: true }` for a filter), never `router.push("/…")` with a string.
3. MUST: `next/link`, `next/navigation` and `next/router` are imported only by `src/app/**`, `src/hooks/**` and `src/components/app-link.tsx`. `routeOf()` in `routes/typed.ts` is the one door from an address text to a `Route` for `router.push/replace`: it refuses anything that is not a page of the tree (an external or `//host` address included). No `"use server"` file: navigation and writes never go through a Server Action (decision 0015).
4. MUST: only two modules touch the address bar: `hooks/use-search-state.ts` (`window.history.replaceState`, shallow: no server round trip, the framework router follows it; `router.replace` there made five RSC requests, P32 N0) and `lib/external.ts` (`openLink`: `location.href` = a link the registry `@hub/contract/local` built, for an `href` action run from code rather than an anchor, such as Reply in Mail after the clipboard, P61; or a new tab for a web page, P131 rule 17). `lib/storage.ts` owns `document.cookie` for the project. Anything else that names `window.location`, `history` or `document.cookie` is a defect.
5. MUST: the URL is the state of a screen. Subject = path (`/lisbon/mail/c/42`), the view, query text, the batch and Activity's one client = query (`?filter=waiting`, `?q=…`, `?batch=3`; Activity `?filter=` and `?client=1`, P73: an old `?run=` is dropped, since Activity shows no session; Settings ▸ Agent's Tools view `?filter=all`, P75; the Messengers panel's views `?filter=linked|hidden` and its channel `?channel=telegram|whatsapp`, P71 M3 and P84c (an old `?filter=all` reads as the default, To do); `?filter=sends` is Activity's send history, an admin view that never reaches the activity API). A key the parser does not know is dropped (rule 8): an old `/mail?new=1` link opens Drafts, since nothing in the admin creates a batch (P48). A component keeps no second copy that Back, reload and a shared link cannot restore. Ephemeral UI (an expanded row) may stay local. The embedded terminal (P49) is not URL state, on purpose: Back must not open or close a terminal, and a link to a terminal means nothing off this machine (its sessions live in one local server). Its open state, width and tab are stored preferences (`state-and-data.md` rule 1); `Ctrl+`` toggles it through `useHotkeys` of `@hub/ui/use-hotkey` (rule 12) as a modifier chord, the one chord that also fires while a field or the terminal has focus. The project a new terminal is for is the project of the address (`Place`, none on the projectless routes, where only Shell is offered); the browser sends that slug and a preset name, never a command or a path.
6. MUST: an unknown path is a real 404 (`not-found.tsx`); a non-numeric or zero id (`/mail/c/abc`), the removed `/mail/<id>` and `/mail/in/<id>` (P99, no redirect) and an extra segment render the explicit Not found state with a link to Mail, never another screen. A bad id is streamed: its HTTP status is 200 with the Not found body and title (`notFound()` after streaming starts cannot change the status, research 19 section 5), so a test asserts the visible state and the title, never a status code for it. There is no `/clients` alias; `REDIRECTS` in `guards.ts` is empty and an entry needs a reason and a removal condition. The old hash addresses are gone, with no shim.
7. MUST: a row or card that navigates is an `AppLink` with a real `href`, not an `onClick` that sets the address.
8. MUST: search is parsed once, in `routes/search.ts` (plain functions over the enums of `@hub/config`, the same ones the API validates; a value outside its enum resets to the default). `URLSearchParams`, `params.get(` and `.searchParams` stay out of `features/`, `components/` and `hooks/`; the live query is read by `hooks/use-route.ts` and `hooks/use-project.ts` only (`useSearchParams`), and a page file reads `await props.searchParams` for its metadata.
9. MUST: a filter REPLACES the history entry (`useSearch(SPEC)`'s `set`), a subject PUSHES (`go(dest("mail.conversation", { id }))`), so Back goes from a detail to its list and never steps through views. The default value drops its key from the address. The address names the conversation on screen (P53, P99): on a pane wide enough for the split, Mail opens its first person and, once the list has settled for the view and search, REPLACES a bare `/mail` with `/mail/c/<client id>`; a narrow pane opens nothing and keeps `/mail`. A person the address names opens whatever the view (Activity links a Done conversation while the list shows Needs you). So a draft recorded at the top never swaps the conversation under the owner, and the focus (P51) names the same client. A menu column item (`SectionNav`, P125: a Knowledge topic, an Activity kind) is a link and PUSHES, so Back undoes a choice made in the column; the controls in the list header still replace.
10. MUST: the project is a path segment, never a query (P48 point 15). With two or more projects every scoped address starts with it: `/lisbon/mail/c/42`, `/lisbon/log?client=1`, `/lisbon/settings`. With one project it is left out: `/mail/c/42`, `/log`, `/settings`; the whole admin is that project. There is ONE route tree (P127 A2, owner remark 2026-11-23): a scoped page exists only as `app/(shell)/[project]/mail/…`, and `defineRoute` judges its path with `/[project]` in front at compile time (`typedRoutes`). A bare scoped address (`/mail/c/42`) is served by `src/proxy.ts` with a rewrite, never a redirect, to the inside form `/_/mail/c/42` (`NO_PROJECT`, the `[project]` of an address that names none): the address bar keeps `/mail/c/42`, `usePath` and `resolveRoute` read both forms as one address (`addressOf`), a page titles it with `addressedProject(project)` (null for `_`), and `PAGE` never accepts `_` as a project, so no destination carries it. `Place {project, multi}` (`hooks/use-project.ts`, from the registry) is what `formatDest` needs to write an address; a component never builds the prefix. `canonicalAddress` in `routes/guards.ts` is the one normaliser, run once by `useEnsureAddress` in the shell frame with `replace`: a bare scoped path with two projects gets the remembered project (cookie `hub_project`, through `lib/storage.ts`) or the first one; a path-form address on a one-project instance folds back to the bare form; a dead slug goes to the remembered project, else the first (`pickProject`); `/` is Overview with two or more projects, Drafts with one; `/overview` is a page on every instance (P63; until then it replaced to Drafts with one project) (`admin-principles.md` rule 7). The query-era addresses (`?project=lisbon`, until 2026-11-18) are read by `resolve.ts` and written in the path form by `canonicalAddress`, with a dated comment and `test/routes.test.ts` covering it; delete that branch when nothing links the old form. Four routes are about the instance, not a project (`PROJECTLESS`, the `scoped: false` rows): `/overview` (every project), `/help` (P63), and two Settings panes, `/settings/connections` (the instance's keys) and `/settings/mac` (this install on this Mac) (P70); they never carry a project. Their page exists once, at the top of the tree; a project segment before one (`/lisbon/overview`, `/lisbon/help`, `/lisbon/settings/connections`) is Not found (P127 A2: the fold page of P70 went with the twins; the sub-nav links the bare pane, so nothing wrote that form). A child page has its parent's scope (`/<project>/settings/mail`), or is projectless under a scoped parent; never scoped under a projectless parent, whose address could not carry the project (`NAV_SHAPE` in `table.ts` refuses that at compile time, with `@ts-expect-error` cases in `test/paths.types.tsx`). A slug may not equal a top-level segment (`RESERVED_SEGMENTS`: the first segment of every table row, plus `health` and `api`: today `overview`, `drafts`, `messengers` (P71 M3), `log`, `knowledge`, `settings`, `help`; `project`, `agents` and `connections` were freed by P70). `src/proxy.ts` redirects nothing: the server cannot know the registry's count, and one normaliser is simpler than two; its one change to an address is the rewrite above, which the address bar never shows.
11. MUST: the title comes from the route: each page file exports `generateMetadata` reading `pageTitle()` over `ROUTE_META` (`routes/meta.ts`); the breadcrumb reads the same table. Nothing writes `document.title`.
12. MUST: keys that navigate are derived from `SECTIONS` (`g o` Overview, `g e` Mail, `g m` Messengers (P71 M3), `g a` Activity, `g k` Knowledge, `g s` Settings, `g h` Help; P70 removed `g p`, `g t`, `g c`) by `use-section-nav`; only parents have a chord (P63: a child is one Tab away in the sub-nav); no key handler names a path. All key maps go through `useHotkeys` of `@hub/ui/use-hotkey` (typing guard, modifier guard, chord window); the page shortcuts pass `shortcutsOn` of `hooks/use-hotkeys` (the remembered off switch).
13. MUST: the skip link is an anchor whose click handler focuses `#main` and prevents the default: a plain `#main` fragment would add a history entry and a hash to the address.
14. MUST: `src/routes/` imports no React, component, feature or hook, and no navigation library (`import type { Route } from "next"` is the one allowed `next` import). `next/*` navigation is for the modules in rule 3.
15. MUST: a page file is thin (at most 40 lines): await the params, give the title, render one feature. `routes/table.ts` is the one declaration of which pages exist (decisions 0021 and 0025): one `defineRoute(path, meta)` row per page, where `path` is the file-tree pattern (`typedRoutes` checks it, `/mail/[id]` included) and `meta` says its section, whether it is scoped to a project, its title and crumb, and, for a page in the nav, its entry (`label`, `icon`, `order`; a parent, a section, also its `g` chord and its phone place, `phone: "bar"` or `"more"`; a child names its parent, `parent: "settings.page"`, and has neither: P63). Every row is on every instance (the `when: "multi"` of Overview went with P63). A parent's landing is its first page in the sub-nav, named by the row's own `title` while the nav names the section by `nav.label` (P70: the nav says Settings, the landing is Sending). Children are drawn only in `components/sub-nav.tsx`, on every page of the parent, the landing first, each with its page's dot (P75: never in the sidebar, open or rail, nor on the phone bar; from 640px a link each; below it one coss `Menu` naming the pane on screen, since six panes do not fit a 360px header line); `childrenOf(section)` in `sections.ts` gives them in order, and `NEXT_ROUTE` maps each `statusDto.next` place to its page. `SECTIONS`, `childrenOf`, the nav, the chords, `PAGE`, `PROJECTLESS`, `ROUTE_META`, `RouteId`, the typed route and `dest` derive from it; the shell reads the nav from it and lists nothing by hand. Why not `@djangocfg/nextjs`'s `defineRoute`: it brings server utilities and their dependencies (chalk, conf, consola, semver) into a local admin, it has no notion of a project placed in the path, and it does not tie a row to the file tree through `typedRoutes`; the local one is about forty lines with the same shape. A new page is (P127 A1): (1) one `defineRoute` row with its `params` (one parser per `[name]` segment of the path, `PARAMS_MATCH` checks the names), its `search` (a spec of `routes/search.ts`, shared where the routes share a view, `MAIL_SEARCH`) and, in the nav, its `nav`; (2) its one page file: under `src/app/(shell)/[project]/` when scoped (titled with `addressedProject(project)`), at the top of `src/app/(shell)/` when projectless; (3) the screen, which reads its address with `useRoute("x.y")` (that route or null) and its search with `useSearch(SPEC)`; (4) an icon key in `nav-icon.tsx` when it is in the nav. The typed route (`Resolved`), `resolveRoute`, `dest`, `destOf` and the search's parse and set are derived from the row, never written per route. `defineRoute`'s path check, `NAV_SHAPE` and `PARAMS_MATCH` each name the bad row; `test/route-files.test.ts` forces the page file (a page without a row, and a twin page: none).
16. SHOULD: a new link, param or key uses `dest`, `useSearch` and `SECTIONS`; it never adds a literal. Path routing is the design; do not add a second router or a `#/` form.
17. MUST: a link that leaves the app for Notion, Telegram or WhatsApp is built from the destinations table of `@hub/contract/local` (P131: every Notion host form, `t.me`/`tg:`, `wa.me`/`whatsapp:`; `urlRefusal` reads the same table) and rendered by `components/links/open-link.tsx` (`useOpenLink`, `OpenLinkButton`, `OpenLinkItem`): the app's link in the same tab when the server's probe says this Mac has the app (`apps` on the instance), else the web page in a new tab, and the label says which. Code that opens a link calls `openLink` of `lib/external.ts`. No such host or scheme literal and no `target="_blank"` anywhere else in `src`. Why: the browser cannot tell whether a scheme has a handler (timer and blur tricks misfire both ways), and a choice made per caller drifts (five ways of opening Notion before P131). Nothing is prefilled: an open only opens.
