## Standing rules

1. Read `@docs/core/06-local-admin-app.md` and `@docs/core/08-local-app-stack.md` first.
2. Components: coss primitives and particles first (skills `coss`, `coss-particles`); do not invent coss APIs, check the docs. No dialogs for primary work: inline disclosure; Drawer only if an edge panel is unavoidable (Sheet is gone in coss).
3. The agent never sends and has no path to a send (decision 0011). The app sends only one draft at a time, after a person has seen the exact mail and confirmed it: the one route `POST /api/projects/:slug/drafts/:id/send` (`apps/server/src/routes/sends.ts`, checks in `@hub/send`). Nothing sends in bulk, on a timer from the admin, or without "I read the checks" switched on. Tests and e2e use the fake Mailer only (`HUB_MAILER=fake`, refused without `HUB_DB`); never put a real send in a test. The admin's only Mail writes besides Send are a person's Save and Restore of one draft (P56, `routes/draft-mail.ts`, the send ticket's door), through the agent's writer; the hub removes only Mail drafts its own record says it wrote (`mail_versions`, matched by account and Message-ID, decision 0031; never by a line in the text, by subject or by recipient), to Trash, never permanently.
4. Every agent edit to the admin app is one git commit on branch `app-live`, made by a hook, so a bad edit reverts alone: `app/@rules/live-edit.md` (`pnpm live`). Never edit `apps/admin` in the main checkout while a live session runs.
5. Data: SQLite is working state only; mail lives in Apple Mail and is read only through it (decision 0026), Notion is the CRM. Schema changes go through a migration, never an ad-hoc ALTER.
6. UI language: English. A table is `@hub/ui/product/data-table` (the coss `Table` with the grid look, `admin-principles.md` rule 5); widths in percent; every list shows its counts in its View menu.
7. Bind to 127.0.0.1: `next dev` and `next start` always with `-H 127.0.0.1`, and `src/proxy.ts` refuses a foreign Host or Origin (`architecture-and-ownership.md` rules 11-12). Three doors are stricter, on purpose: the terminal's socket, its tickets (`/api/terminal/tickets`) and its two starts (`/api/terminal/sessions`, and `/api/terminal/ensure`, P57: it starts a session without a click on a `+` item), the send ticket of a manual send (`/api/sends/tickets`), the shared focus (`POST /api/focus`: a forged focus would steer the agent), and the local Open (`POST /api/local/:action`, P61: an open takes the owner's screen; no ticket, since nothing is written or sent), and the autostart switch (`POST /api/instance/autostart`, P67: it changes what the Mac runs at login; only `launchctl enable|disable` of the instance's own label, never a plist), accept only the exact admin Origin (`http://127.0.0.1:<admin port>` or `http://localhost:<admin port>`, never another loopback port, never a missing Origin) with `Sec-Fetch-Site: same-origin`, and the socket opens only with a single-use ticket (30 s) sent as its first frame, never a cookie or a token in the URL: any local page on another port is loopback too, and cookies are not port-isolated. No secrets in a tracked file, no `NEXT_PUBLIC_*` variable: tokens live only in the git-ignored `state/secrets/` (override `HUB_CONFIG_DIR`).
8. MUST: locations come only from `@hub/config/paths` (`hubPaths`). No `join(root, "projects"|"state"|"config"|...)`, no `app/projects` string, no direct read of `HUB_HOME`, `HUB_PROJECTS`, `HUB_DB`, `HUB_CONFIG_DIR`, `HUB_CONFIG_FILE` outside `packages/config`; `apps/installer/test/home-seams.test.ts` enforces it. Precedence and layouts: `@docs/core/08-local-app-stack.md` (decision 0016).
8a. One screen per job, and a screen only when it answers a question no other screen answers (`admin-principles.md` rule 2). Drafts (routes `/drafts`, `/drafts/42`; the home of every instance: the agent's work lands there and the owner's decisions are made there; a batch is the read-only view `/drafts?batch=3`; Follow-ups, Not by email and Thin basis are views of its View menu, never sections), Activity (route `/log`: what the agent did, a table grouped by session), Project (route `/project`, the landing: status and the one Stop sending, the send history, the open question; with two child pages, P63: Knowledge, `/project/knowledge`, and Setup, `/project/setup`: the setup facts, mail filters, health, the safety rules under Advanced), Agents (route `/agents`, per project, P63: the Agent tools rows of both CLIs; later P55's model and advisor and P62's connectors), Connections (route `/connections`: the Notion token and the Telegram bot, the projects' mail accounts read-only, and "This Mac": whether the Mac starts this instance at login, P67), Overview (route `/overview`, every instance, P63: the parts of the Hub with their standing; with two or more projects also one table row per project, first, and then it is the entry), Help (route `/help`, P63: where the wiring is shown and where the shortcuts are; patch B adds the phrases to say and where the files live). Planned: Client. Adding a screen needs a reason written here. The terminal dock is not a screen: it is a dock beside every screen, always there (no switch, decision 0032), because its job (Claude Code or Codex running while the owner watches drafts land) needs the screen next to it, not instead of it. Reason for Overview: no screen shows the Hub's parts (the mailboxes, mail-mcp, the agent CLIs and their tools, Notion, knowledge, the guard, the send door, the core) with the broken one among them; Connections answers where each key stands and sets it, Project answers one project's settings, Agents one project's sessions, and each part on Overview links to the one of them that fixes it. With two or more projects the owner's first question (which project needs me) belongs to no scoped screen either, so the project table comes first; with one project that table would repeat Project's status line, so it is left out, and the parts are not. It is a cross-project route (`routes-and-url-state.md` rule 10) and reads, never writes. Reason for Connections: a token belongs to the instance, not to one project (one Notion token serves every project), so inside Project it would be repeated per project or hidden behind a project choice; and the owner asks "is everything connected" as one question. Connections also holds how this instance starts on this Mac (P67, decision 0033): it is the instance's, not a project's, for the same reason as a token. It is the second projectless route. Reason for Agents (P63): Agent tools are a project's (`/api/projects/:slug/agent-tools`), and on the projectless Connections they had to pick a project, the mismatch this rule removed when it made Connections projectless; Agents answers "can this project's agent sessions work, and how are they set", which no other screen does. It is scoped (`/<project>/agents`), so it cannot be a child of Connections. Reason for Knowledge and Setup as child pages of Project (P63): Knowledge is the one project fact with a list to act on (entries, expired and unapproved ones, each with its Open) and it grows; setup facts, mail filters, health and the safety rules are one question, "is this project set up right", written by `project-setup` and `mail-filters` or set once; the landing keeps what is a decision or needs one. Mail filters, Health and the safety rules are not pages of their own: each is a line or a table that matters only when it fails, and Overview's parts say that. Connections, Drafts and Activity have no children. Reason for Help (P63): "what do I say, and where is it" is answered by no screen (each empty state names one phrase); in patch A it holds two lines (Overview for the wiring, `?` for the shortcuts), so the nav entry leads somewhere real, and it never copies the `?` list. The third projectless route.
9. Verification: a screen is done when the agent has opened it in the browser at 360, 768 and 1280 px (no sideways page scroll, touch targets 44px high below 1024px, the views in one View menu with counts, light and dark) and the owner's main path works with the keyboard. `pnpm e2e` (Playwright, installed Chrome, throwaway DB, a production build served by `next start`; `verification.md` rule 6) runs the flows in `apps/admin/e2e`; add a flow when a screen is added. Flows that create data are named `z-*.spec.ts` so they run after the smoke flows (one worker, one seeded database).
10. Skills: dev-time (coss) are referenced in `skills.md`, not copied; run-time skills stay in `reforms-crm/skills/`.
11. Layout (decision 0004): `app/` is the one Turborepo + pnpm monorepo: `apps/server`, `apps/admin`, `apps/installer` (`@hub/installer`, bin `hub`: agent, up, doctor, setup, plus hidden commands, each with `hub <name> --help`; root script `pnpm hub`); `packages/db` (`@hub/db`), `packages/config`, `packages/ui` (`@hub/ui`: coss copies, product primitives, `cn`, tokens; imported by apps, imports none), `packages/notion` (`@hub/notion`, CLI `notion-dump`); there is no mail package: mail is Apple Mail only (`mail-mcp` for the agent, `osascript` for the hub; decision 0026); `packages/send` (`@hub/send`: the Mailer and the send checks, shared by `hub send` and the server, since packages never import apps); `packages/connections` (`@hub/connections`: the instance's Notion token and Telegram bot, the only two keys, derived from `state/secrets`: inspect, probe, write-only store, remove, redact, shape checks; shared by the wizard, `hub token`, the doctor steps, the server and the admin's Connections panel; the one owner of the Telegram token shape); `packages/contract` (`@hub/contract`: the zod schemas of every API reply and request, the live topics and the focus shape, shared by the server, the admin, the CLI and `@hub/agent`; `@hub/contract/local` is the one registry of the local Open actions (P61): ids, argument schemas, transport, the `message:`/`mailto:`/`notion:` builders and the URL allowlist; nothing else builds those links); `packages/agent` (`@hub/agent`: the agent sessions of both CLIs, the deny rules, Agent tools, the shared-focus reader, `hub mcp` and `sessionRules()`); `packages/terminal` (`@hub/terminal`: the terminal's PTY sessions, presets and socket; imported by the server only); `packages/sequences`, `packages/projects` (also `@hub/projects/local-open`, P61: an Open's key to an absolute path inside its own root, and the one runner of `/usr/bin/open`, argv only, shared by the server, `hub open` and `hub up`), `packages/knowledge`, `packages/mail-filters`, `packages/messengers` (each owns its subject; the package README or the core page says how); `projects/<name>/project.md` lists a project's Notion databases. Every package is a workspace member: no own lockfile, no own `pnpm-workspace.yaml` (the esbuild build policy lives once in `app/pnpm-workspace.yaml`); tsconfig extends `@hub/config/tsconfig.base.json`. `pnpm dev` runs everything; root script `db:migrate`; the schema lives in `packages/db/src/schema.ts` and every table has a `project` column: filter by it in every query.
12. coss components are copied into `packages/ui/src/ui` from `https://coss.com/ui/r/<name>.json` (rewrite `@/registry/default/{ui,lib}` to relative paths: `./button`, `../cn`; an app then imports `@hub/ui/<name>`); do not hand-edit them.
13. A table is `@hub/ui/product/data-table` (rule 6); no data-grid library is a dependency (the admin lists are short and server-paged). Admitting one needs the written reason of `architecture-and-ownership.md` rule 14 first.
14. The API: the admin reads a reply only through `read(schema, call)` in `lib/api/client.ts`, parsed with a `@hub/contract` schema; the one stream, `GET /api/live`, carries only invalidations and is read only in `lib/cache/live.ts` (`state-and-data.md` rule 13); `@hub/server` is imported as `import type` only, and the admin imports no `@hub/db` or Server Action (`architecture-and-ownership.md` rule 3). Repositories are async; a sync driver stays behind them.
15. Drizzle: in a correlated sub-select write literal table names; drizzle drops qualifiers in a single-table select and `id` becomes ambiguous.
16. The admin database is not a client directory (decision 0009). A `clients` row exists only because the agent recorded a draft for that client (`hub record-draft`, repo method `drafts.record`); never bulk-copy clients from Notion, never add a column for a Notion fact (company, deal value), never delete a client row (marks and the log cascade). The Drafts screen lists only clients that have a draft; nothing lists every client row, because choosing clients is the agent's job (`admin-principles.md` rule 1).
17. Messengers (`@hub/messengers`): the agent imports only `@hub/messengers`; `@hub/messengers/human` (link, approve, send) is for entry points that know a person is present and mint a `humanActor`. Never import it from an agent tool. Chats are linked to clients by the owner only; ingest stores allow-listed chats only. The bot token is a NEW bot's, in `state/secrets/telegram-bot-token`, never a webhook bot's.
