## Standing rules

1. Read `@docs/core/06-local-admin-app.md` and `@docs/core/08-local-app-stack.md` first.
2. Components: coss primitives and particles first (skills `coss`, `coss-particles`); do not invent coss APIs, check the docs. No dialogs for primary work: inline disclosure; Drawer only if an edge panel is unavoidable (Sheet is gone in coss).
3. The agent never sends and has no path to a send (decision 0011). The app sends only one draft at a time, after a person has seen the exact mail and confirmed it: the one route `POST /api/projects/:slug/drafts/:id/send` (`apps/server/src/routes/sends.ts`, checks in `@hub/send`). A messenger draft goes through the same door (P71 M4, decision 0036 point 7): `POST /api/projects/:slug/messengers/drafts/:id/send` in the same file, a dry run with the exact chat and text, a ticket minted with `kind: "messenger"`, the `send_log` row first (column `channel`), one send, no retry, and its own guards (`apps/server/src/send/messenger-door.ts`: an inbound message in the chat, `MESSENGER_DAILY_CAP` and `MESSENGER_SPACING_SECONDS` per account, `draft.recipients: test` admits only `telegram:<id>` / `whatsapp:+<number>` entries of `allow_list`, Stop sending); the admin's two Sends share one flow (`components/send/send-flow.ts`, `test/send-boundary.test.ts`), and no messenger send is automatic or in bulk. Nothing sends on a timer from the admin, for the agent, or without "I read the checks" switched on. A campaign (P85) is many drafts, one batch in Mail, each sent by its own click through this door, or (P85b, decision 0011 amendment of 2026-11-20 point 4) by Send all Checked of that one batch: `POST /api/projects/:slug/batches/:id/send` (same file) is a dry run of every Checked draft of the batch through `assess`, then one confirmation naming the count and every recipient, a ticket minted for exactly those draft ids and text hashes (`POST /api/sends/batch-tickets`), and a run on the server (`apps/server/src/send/batch-door.ts`, `runBatch` in `@hub/send`) that sends one draft at a time through `sendDraft` with every guard again, its own `send_log` row each (actor `admin-batch`), its own cap and spacing (`BATCH_SEND_DAILY_CAP` 50 per project per 24 h, `BATCH_SEND_SPACING_SECONDS` 20), Stop of the run and Stop sending between two mails, and a refusal or failure listed without stopping the rest; the batch panel (`features/mail/batch-send.tsx`) is its only caller (`test/send-boundary.test.ts`). No other bulk send exists, and none is automatic. A draft may also be a new thread (P85b: a client with no thread at all, `draft_write` with `to`, recorded with `newThread`, no `mailRef`); the door sends it as a new message. A draft may answer our own sent message (a new message on the owner's words, `owner_request` / `ownerRequest`); Sent detection then matches it by its own recorded Mail versions, its thread and a send after it was made, never by its `mailRef` (the answered message) and never by a Sent message already attributed to another draft (`apps/server/src/sent.ts`). Tests and e2e use the fake Mailer only (`HUB_MAILER=fake`, refused without `HUB_DB`); never put a real send in a test. The admin's only Mail writes besides Send are a person's Save and Restore of one draft (P56, `routes/draft-mail.ts`, the send ticket's door), through the agent's writer; the hub removes only Mail drafts its own record says it wrote (`mail_versions`, matched by account and Message-ID, decision 0031; never by a line in the text, by subject or by recipient), to Trash, never permanently.
4. Every agent edit to the admin app is one git commit on branch `app-live`, made by a hook, so a bad edit reverts alone: `app/@rules/live-edit.md` (`pnpm live`). Never edit `apps/admin` in the main checkout while a live session runs.
5. Data: SQLite is working state only; mail lives in Apple Mail and is read only through it (decision 0026), Notion is the CRM. Schema changes go through a migration, never an ad-hoc ALTER.
6. UI language: English (P81: the phrases Help and the empty states show are English too, one per skill from `phrase()` in `@hub/contract/help`; the owner may say them in any language; enforced by `test/rules.test.ts` "no Cyrillic", which allows one line, the Re/Fwd prefixes of `apps/server/src/sent.ts`). A table is `@hub/ui/product/data-table` (the coss `Table` with the grid look, `admin-principles.md` rule 5); widths in percent; every list shows its counts in its View menu.
7. Bind to 127.0.0.1: `next dev` and `next start` always with `-H 127.0.0.1`, and `src/proxy.ts` refuses a foreign Host or Origin (`architecture-and-ownership.md` rules 11-12). Three doors are stricter, on purpose: the terminal's socket, its tickets (`/api/terminal/tickets`) and its two starts (`/api/terminal/sessions`, and `/api/terminal/ensure`, P57: it starts a session without a click on a `+` item) and its file drop (`POST /api/terminal/sessions/:id/drops`, P76, decision 0041: it writes the dropped files under `state/drops/` and types nothing; no ticket), the send ticket of a manual send (`/api/sends/tickets`) and of a batch send (`/api/sends/batch-tickets`, P85b: bound to the batch and the confirmed draft ids and text hashes), the shared focus (`POST /api/focus`: a forged focus would steer the agent), and the local Open (`POST /api/local/:action`, P61: an open takes the owner's screen; no ticket, since nothing is written or sent), and the autostart switch (`POST /api/instance/autostart`, P67: it changes what the Mac runs at login; only `launchctl enable|disable` of the instance's own label, never a plist), accept only the exact admin Origin (`http://127.0.0.1:<admin port>` or `http://localhost:<admin port>`, never another loopback port, never a missing Origin) with `Sec-Fetch-Site: same-origin`, and the socket opens only with a single-use ticket (30 s) sent as its first frame, never a cookie or a token in the URL: any local page on another port is loopback too, and cookies are not port-isolated. No secrets in a tracked file, no `NEXT_PUBLIC_*` variable: tokens live only in the git-ignored `state/secrets/` (override `HUB_CONFIG_DIR`).
8. MUST: locations come only from `@hub/config/paths` (`hubPaths`). No `join(root, "projects"|"state"|"config"|...)`, no `app/projects` string, no direct read of `HUB_HOME`, `HUB_PROJECTS`, `HUB_DB`, `HUB_CONFIG_DIR`, `HUB_CONFIG_FILE` outside `packages/config`; `apps/installer/test/home-seams.test.ts` enforces it. Precedence and layouts: `@docs/core/08-local-app-stack.md` (decision 0016).

18. Logging (P86): the server and every package write what failed or happened through the ops log, `ops(source).error|warn|info|debug(message, fields)` of `@hub/log/ops`, never a raw `console.*`: each line gets a time, a level and a source, is redacted in one place (`redactOps`: secret-named fields masked, body-named fields dropped, phones, jids, emails, keys and the stored secrets masked in every string) and lands in `state/log/ops-<day>.jsonl` (7 days, 20 MB a day) with a human copy on stderr. A failure is logged where it is caught, once, with its reason (`status`, `kind`, `reason`; a field named `code` is a secret); never a message's or a mail's text. A CLI's printed answer is not a log line: `apps/installer/test/ops-log-rules.test.ts` fails on a `console.*` in `apps/server/src` or `packages/*/src` outside its explicit list of CLI files, each with why; the installer is the `hub` CLI and prints to the user. `hub logs` and Overview's Recent errors read it. `@docs/core/28-ops-log.md`.
