## Standing rules

1. Read `@docs/core/06-local-admin-app.md` and `@docs/core/08-local-app-stack.md` first.
2. Components: coss primitives and particles first (skills `coss`, `coss-particles`); do not invent coss APIs, check the docs. No dialogs for primary work: inline disclosure; Drawer only if an edge panel is unavoidable (Sheet is gone in coss).
3. The agent never sends and has no path to a send (decision 0011). The app sends only one draft at a time, after a person has seen the exact mail and confirmed it: the one route `POST /api/projects/:slug/drafts/:id/send` (`apps/server/src/routes/sends.ts`, checks in `@hub/send`). Nothing sends in bulk, on a timer from the admin, or without "I read the checks" switched on. Tests and e2e use the fake Mailer only (`HUB_MAILER=fake`, refused without `HUB_DB`); never put a real send in a test. The admin's only Mail writes besides Send are a person's Save and Restore of one draft (P56, `routes/draft-mail.ts`, the send ticket's door), through the agent's writer; the hub removes only Mail drafts its own record says it wrote (`mail_versions`, matched by account and Message-ID, decision 0031; never by a line in the text, by subject or by recipient), to Trash, never permanently.
4. Every agent edit to the admin app is one git commit on branch `app-live`, made by a hook, so a bad edit reverts alone: `app/@rules/live-edit.md` (`pnpm live`). Never edit `apps/admin` in the main checkout while a live session runs.
5. Data: SQLite is working state only; mail lives in Apple Mail and is read only through it (decision 0026), Notion is the CRM. Schema changes go through a migration, never an ad-hoc ALTER.
6. UI language: English. A table is `@hub/ui/product/data-table` (the coss `Table` with the grid look, `admin-principles.md` rule 5); widths in percent; every list shows its counts in its View menu.
7. Bind to 127.0.0.1: `next dev` and `next start` always with `-H 127.0.0.1`, and `src/proxy.ts` refuses a foreign Host or Origin (`architecture-and-ownership.md` rules 11-12). Three doors are stricter, on purpose: the terminal's socket, its tickets (`/api/terminal/tickets`) and its two starts (`/api/terminal/sessions`, and `/api/terminal/ensure`, P57: it starts a session without a click on a `+` item) and its file drop (`POST /api/terminal/sessions/:id/drops`, P76, decision 0041: it writes the dropped files under `state/drops/` and types nothing; no ticket), the send ticket of a manual send (`/api/sends/tickets`), the shared focus (`POST /api/focus`: a forged focus would steer the agent), and the local Open (`POST /api/local/:action`, P61: an open takes the owner's screen; no ticket, since nothing is written or sent), and the autostart switch (`POST /api/instance/autostart`, P67: it changes what the Mac runs at login; only `launchctl enable|disable` of the instance's own label, never a plist), accept only the exact admin Origin (`http://127.0.0.1:<admin port>` or `http://localhost:<admin port>`, never another loopback port, never a missing Origin) with `Sec-Fetch-Site: same-origin`, and the socket opens only with a single-use ticket (30 s) sent as its first frame, never a cookie or a token in the URL: any local page on another port is loopback too, and cookies are not port-isolated. No secrets in a tracked file, no `NEXT_PUBLIC_*` variable: tokens live only in the git-ignored `state/secrets/` (override `HUB_CONFIG_DIR`).
8. MUST: locations come only from `@hub/config/paths` (`hubPaths`). No `join(root, "projects"|"state"|"config"|...)`, no `app/projects` string, no direct read of `HUB_HOME`, `HUB_PROJECTS`, `HUB_DB`, `HUB_CONFIG_DIR`, `HUB_CONFIG_FILE` outside `packages/config`; `apps/installer/test/home-seams.test.ts` enforces it. Precedence and layouts: `@docs/core/08-local-app-stack.md` (decision 0016).
8a. One screen per job, and a screen only when it answers a question no other screen answers (`admin-principles.md` rule 2). Six sections (P70): Overview (route `/overview`, every instance: what needs you, the rest folded; with two or more projects also one table row per project, first, and then it is the entry), Drafts (routes `/drafts`, `/drafts/42`; the home of every instance: the agent's work lands there and the owner's decisions are made there; a batch is the read-only view `/drafts?batch=3`; Follow-ups, Not by email and Thin basis are views of its View menu, never sections), Activity (route `/log`: what happened, a table of what the agent did grouped by session, repeats of one client and outcome folded into one line with a count (`admin-principles.md` rule 5), and since the UX pass of 2026-11-20 the send history as its View menu's Sends view, `?filter=sends`: what was sent is activity, not a setting), Knowledge (route `/knowledge`, per project: every entry of the knowledge base, with its Open), Settings (route `/settings`, opening on its first pane, Sending; five panes: Sending `/settings` (Stop sending, who drafts may go to, autosend, the checks before sending: controls only), Mail `/settings/mail` (the project's accounts and its filters), Agent `/settings/agent` (first the Agent group, P55: the model of the project's Claude Code sessions, Sonnet or Opus, and the advisor, off by default, its model Fable or Opus shown only while it is on, "Applies to the next agent session", Codex one read-only line; then Connectors, P62: one line per Google connector attached to the project (Calendar or Drive, its hub name, its account, what the session may do with it), or one line "None attached" with the phrase; no control, since a connector is attached in project.md by a phrase; then Checks: the rows of both CLIs that need a fix or a look, every row folded under All checks, the connector rows among them), Connections `/settings/connections` (the Notion token and the Telegram bot), This Mac `/settings/mac` (start after a restart, P67; the core version and its update command, P68)), Help (route `/help`: what to say to the agent, the tips for each agent CLI, where the project's files live, each with its Open, and last "How it works", the Hub's wiring drawn live by Mermaid, P63 patch B, decision 0035). Planned: Client. Adding a screen needs a reason written here. The terminal dock is not a screen: it is a dock beside every screen, always there (no switch, decision 0032), because its job (Claude Code or Codex running while the owner watches drafts land) needs the screen next to it, not instead of it. Reason for Overview: no screen shows the Hub's parts (the mailboxes, mail-mcp, the agent CLIs and their tools, Notion, knowledge, the guard, the send door, the core) with the broken one among them, and the Drafts status line says one fact, so a second broken one would be invisible until the first is fixed; the facts fixed by a phrase in a session (a failing setup check, a draft project, the agent's open question) have no settings pane to land on. Overview holds them, each with the place or the phrase that fixes it, and no control. With two or more projects the owner's first question (which project needs me) belongs to no scoped screen either, so the project table comes first; with one project that table would repeat the Drafts status line, so it is left out. It is a projectless route (`routes-and-url-state.md` rule 10) and reads, never writes. Reason for Knowledge as a section: it is content he reads and corrects (the facts the agent cites in his name), not a setting (`admin-principles.md` rule 12), it is the one project list besides drafts that he acts on (expired, not approved), and it grows; under Settings it would be a fact set once, which it is not. Reason for Settings: what is set rarely and changes how the Hub behaves is one place, grouped by what it governs, as on a Mac (`admin-principles.md` rule 12); each pane answers one question: Sending "what lets a mail out", Mail "which mail does the agent read", Agent "can this project's sessions work, how do they start, and what do they reach", Connections "where does each instance key stand" (a token belongs to the instance, not to one project: one Notion token serves every project), This Mac "how does this install run on this Mac". Instance panes (Connections, This Mac) sit beside project panes on purpose: the owner thinks of them as settings, and on a Mac System Settings mixes the machine's and the user's panes in one list; their addresses name no project (`routes-and-url-state.md` rule 10). Settings has no landing page of its own: an empty page listing the panes would cost a click; it opens on Sending, so Stop sending is one click from any screen. Reason for Help: "what do I say, where is it, and how does it fit together" is answered by no screen (each empty state names one phrase); it holds the phrases (`@hub/contract/help`, the skills README's Example column word for word), the tips (`@hub/contract/tips`, the same list the dock's tips button shows per tab), the project's files no screen lists (`project.md`, the project folder, Workflows, today's agent log), and the drawing of how the parts connect, built from the same `GET /api/scheme` as Overview's parts. The drawing is on Help, not Overview (P63 patch B): Overview answers "what needs you" and holds nothing else in view (P70), while a picture of every part is read once to understand the Hub, not every day; Overview's "All parts" is its text alternative, one link away. Help never copies the `?` list. Overview and Help are projectless sections. Drafts, Activity, Knowledge, Overview and Help have no children.
9. Verification: a screen is done when the agent has opened it in the browser at 360, 768 and 1280 px (no sideways page scroll, touch targets 44px high below 1024px, the views in one View menu with counts, light and dark) and the owner's main path works with the keyboard. `pnpm e2e` (Playwright, installed Chrome, throwaway DB, a production build served by `next start`; `verification.md` rule 6) runs the flows in `apps/admin/e2e`; add a flow when a screen is added. Flows that create data are named `z-*.spec.ts` so they run after the smoke flows (one worker, one seeded database).
10. Skills: dev-time (coss) are referenced in `skills.md`, not copied; run-time skills stay in `reforms-crm/skills/`.
11. Layout (decision 0004): `app/` is the one Turborepo + pnpm monorepo: `apps/server`, `apps/admin`, `apps/installer` (`@hub/installer`, bin `hub`: agent, up, doctor, setup, plus hidden commands, each with `hub <name> --help`; root script `pnpm hub`); `packages/db` (`@hub/db`), `packages/config`, `packages/ui` (`@hub/ui`: coss copies, product primitives, `cn`, tokens; imported by apps, imports none), `packages/notion` (`@hub/notion`, CLI `notion-dump`); there is no mail package: mail is Apple Mail only (`mail-mcp` for the agent, `osascript` for the hub; decision 0026); `packages/send` (`@hub/send`: the Mailer and the send checks, shared by `hub send` and the server, since packages never import apps); `packages/connections` (`@hub/connections`: the instance's Notion token and Telegram bot, derived from `state/secrets` (the third key, OpenRouter's, is read only by `@hub/llm`, P78): inspect, probe, write-only store, remove, redact, shape checks; shared by the wizard, `hub token`, the doctor steps, the server and the admin's Settings ▸ Connections; the one owner of the Telegram token shape); `packages/contract` (`@hub/contract`: the zod schemas of every API reply and request, the live topics and the focus shape, shared by the server, the admin, the CLI and `@hub/agent`; `@hub/contract/local` is the one registry of the local Open actions (P61): ids, argument schemas, transport, the `message:`/`mailto:`/`notion:` builders and the URL allowlist; nothing else builds those links); `packages/agent` (`@hub/agent`: the agent sessions of both CLIs, the deny rules, Agent tools, the shared-focus reader, `hub mcp` and `sessionRules()`; P62's connectors: the kinds and their allowlists, the resolver that writes a project's connectors into its session file, the guard's connector rules and the capabilities line); `packages/terminal` (`@hub/terminal`: the terminal's PTY sessions, presets and socket; imported by the server only); `packages/sequences`, `packages/projects` (also `@hub/projects/local-open`, P61: an Open's key to an absolute path inside its own root, and the one runner of `/usr/bin/open`, argv only, shared by the server, `hub open` and `hub up`), `packages/knowledge`, `packages/mail-filters`, `packages/messengers`, `packages/llm` (`@hub/llm`, P78: the one door to a model API, typed structured calls over OpenRouter, a ledger row per attempt in `llm_calls`, the monthly cap; imports `@hub/config` and zod only, `@docs/core/27-llm.md`) (each owns its subject; the package README or the core page says how); `projects/<name>/project.md` lists a project's Notion databases. Every package is a workspace member: no own lockfile, no own `pnpm-workspace.yaml` (the esbuild build policy lives once in `app/pnpm-workspace.yaml`); tsconfig extends `@hub/config/tsconfig.base.json`. `pnpm dev` runs everything; root script `db:migrate`; the schema lives in `packages/db/src/schema.ts` and every table has a `project` column: filter by it in every query.
12. coss components are copied into `packages/ui/src/ui` from `https://coss.com/ui/r/<name>.json` (rewrite `@/registry/default/{ui,lib}` to relative paths: `./button`, `../cn`; an app then imports `@hub/ui/<name>`); do not hand-edit them.
13. A table is `@hub/ui/product/data-table` (rule 6); no data-grid library is a dependency (the admin lists are short and server-paged). Admitting one needs the written reason of `architecture-and-ownership.md` rule 14 first.
14. The API: the admin reads a reply only through `read(schema, call)` in `lib/api/client.ts`, parsed with a `@hub/contract` schema; the one stream, `GET /api/live`, carries only invalidations and is read only in `lib/cache/live.ts` (`state-and-data.md` rule 13); `@hub/server` is imported as `import type` only, and the admin imports no `@hub/db` or Server Action (`architecture-and-ownership.md` rule 3). Repositories are async; a sync driver stays behind them.
15. Drizzle: in a correlated sub-select write literal table names; drizzle drops qualifiers in a single-table select and `id` becomes ambiguous.
16. The admin database is not a client directory (decision 0009). A `clients` row exists only because the agent recorded a draft for that client (`hub record-draft`, repo method `drafts.record`); never bulk-copy clients from Notion, never add a column for a Notion fact (company, deal value), never delete a client row (marks and the log cascade). The Drafts screen lists only clients that have a draft; nothing lists every client row, because choosing clients is the agent's job (`admin-principles.md` rule 1).
17. Messengers (`@hub/messengers`): the agent imports only `@hub/messengers`; `@hub/messengers/human` (link, approve, send) is for entry points that know a person is present and mint a `humanActor`. Never import it from an agent tool. Chats are linked to clients by the owner only; ingest stores allow-listed chats only. The agent's messenger tools (`messenger_history`, `messenger_draft_write` in `hub mcp`, P71 M2) read and write through `@hub/db` only, never `@hub/messengers`, so no Telegram client loads in `hub mcp`. The bot token is a NEW bot's, in `state/secrets/telegram-bot-token`, never a webhook bot's.
