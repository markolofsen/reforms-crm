# Approval and capability boundaries

Scope: safety: dispatch, agent sessions and every door that writes Hub state or delivers a message (headline: `README.md` rule 3). History: decision 0047.

## Rules

1. MUST: `approval_policy=never` is the one mode of every session, not a bypass: the OS sandbox stays on, and only the hub's own writing tools get an approval override, by name; each still passes project scope, schema, draft-only and server checks.
2. MUST: attendance comes from how a session started, never from the permission mode (owner 2026-11-25): a session the owner starts is attended; a background run the Hub starts (an autopilot turn, a sweep turn: `backgroundRunOf`) is not. Both share one deny list, with one exception (decision 0046): `mcp__hub__messenger_send` is denied in a background run only. Every other send, adapter call, `HumanActor`, `SendAuthorization` and ticket is denied in every session. The deny lists bind the model's processes (the CLI, its shell, its MCP servers); the send door reads no session mode (P112 S3). Decision 0048 (P139): the autopilot's switches are written only by the owner's routes (`apps/server/src/messengers/autopilot/routes.ts`, an `autopilot:<scope>` ticket) and `hub send policy autopilot` in his own shell; their files (`state/autopilot.json`, the `autopilot` block of `state/projects/<slug>/send-policy.json`) are protected paths in every mode, and no hub MCP tool writes them.
3. MUST: `hub.draft_write`, `hub.client_record` and `hub.messenger_draft_write` never send, never write a `send_log` row and never construct a `HumanActor` or a `SendAuthorization`.
4. MUST: attended mode keeps `on-request` approval; no bypass flag or policy rewrite, ever.
5. MUST: unknown tools, unknown modes, a missing project scope and cross-project ids fail closed before a Hub tool runs. A Notion tool off `NOTION_ALLOWED` (`@hub/projects/notion-tools`) is refused in every mode, an unknown one too (P112 S3). `hub mcp` binds to `HUB_PROJECT` only with the launcher's project capability for that slug (`HUB_PROJECT_CAPABILITY`, `packages/agent/src/mcp/binding.ts`), checked once at start; without it every tool refuses `unbound`.
6. MUST: background jobs and inbound handlers cannot mint an owner actor or a `SendAuthorization`, or call a delivery adapter. There is no automatic messenger reply mode; one needs a new decision record first (decision 0003), never a setting. Decision 0048 is that record for the messenger autopilot (P139). Its switches are a flag of their own, never a `reply_mode` value: the instance file, the project's `autopilot` block and the chat's place in it, all three on (`packages/projects/src/autopilot.ts`); `app.db` holds only the chat's pause, which can stop autopilot and never start it. The ingest wakes its scheduler (`apps/server/src/messengers/autopilot/scheduler.ts`, A2), which only decides when a turn runs; a turn holds no send. Its one sender is `applyMessenger` with the `autopilot` member of `MessengerAuthority` (A4, `apps/server/src/messengers/autopilot/deliver.ts`), called only after a turn's brain returned a `send` verdict in mode `on`, with the text the turn's own `messenger_draft_write` call carried (never a row read back); its audit row is held to autopilot's share of the account. Only mechanical limits stand before it (the three switches, the pause, Stop sending, the budgets, the spacing, quiet hours): no code judges the text (owner, 2026-11-24), the `autopilot-reply` skill does, with one exception at the write, not the door (P155 verdict 8): `messenger_draft_write` and `draft_write` refuse a booking link that is not the thread's resolved one, or a second offer (`booking_link_mismatch`, `packages/projects/src/brands/booking.ts`); the owner's Send is never refused for it. The turn's model process (`claude -p`, `packages/agent/src/autopilot`) gets no built-in tool and exactly five hub tools bound to the one chat (`AUTOPILOT_HUB_TOOLS`), none of them a send.
7. MUST (decision 0046, amends decision 0003 and 0045 point 1): in an attended session the agent may send ONE messenger draft on the owner's word, through `mcp__hub__messenger_send` (the chat and the draft id, nothing else). The server, not the tool, verifies the word in the project's session log: an owner `prompt` that tells it to send ("отправь", "send it"), written after the draft's last change, the newest prompt of its session, at most 12 hours old, not negated, and naming the chat unambiguously. It then calls the same door as the owner's Send button (`applyMessenger`), with `actor: agent_on_owner_word` and the word's log reference on the `send_log` row; a reference is unique: one send per word. Every refusal carries a code and the next step; the agent never retries a refused or failed send.
8. MUST: Mail is never sent by the agent, in any mode: there is no Mail send tool, and the agent send route refuses anything but a messenger draft. An email is sent only by the owner's click in the admin (decision 0046 point 4).
9. MUST: the agent send route answers only the hub MCP server (a token under `state/secrets`, which every session is denied), is reached only from a session the owner started (a background run's `hub mcp` has no send port), and never takes the owner's words or a session id from its caller as proof.
10. MUST: a person's send is one draft at a time, after the exact text was shown and confirmed, through the one door: `POST /api/projects/:slug/drafts/:id/send` for Mail and `.../messengers/drafts/:id/send` for a messenger draft (`apps/server/src/send/sends-routes.ts`, checks in `@hub/send`): a dry run, a ticket, the `send_log` row first, one send, no retry.
11. MUST: the one bulk send is Send all Checked of one batch (decision 0011 amendment of 2026-11-20): a dry run of every Checked draft, one confirmation naming the count and each recipient, a ticket bound to those draft ids and text hashes, then one draft at a time on the server with every guard, its own cap and spacing, and Stop between two mails. Nothing sends on a timer or in bulk otherwise.
12. MUST: a messenger send passes its own guards (`packages/messengers/src/door.ts`): the project is active, a known chat (decision 0049: linked, or the owner's own reply in an unlinked one), an inbound message in the chat, the draft's client is still the chat's (none for an unlinked chat), the daily cap and spacing per account, `draft.recipients: test` admitting only allow-listed ids, and Stop sending.
13. MUST: the admin's other Mail writes are a person's Save and Restore of one draft and Tidy; the Hub removes only Mail drafts its own record says it wrote (`mail_versions`, by account and Message-ID; decision 0031), to Trash, never permanently. One inbound message moves to its account's Junk or Trash (P147 3n, `apps/server/src/passes/mail-junk.ts`, both recoverable in Mail) on the owner's Spam or Delete, his review click on a junk proposal, or `mail_junk` in a session he started; the agent's call is refused for a known sender (a Clients card, a mail we sent, a lead), and `mail_junk` is exempt from the send-like name check by this rule (`packages/agent/src/deny.ts`).
14. MUST: tests and e2e use the fake Mailer only (`HUB_MAILER=fake`, refused without `HUB_DB`).
15. MUST (P112 S2): a send door is its stages, each a function on fresh reads, in this order: assessment, authorization, final checks, audit (`send_log` first), delivery. The messenger door's authorization takes the caller's stated `MessengerAuthority` (no default) and mints the one `SendAuthorization`, bound to the draft, chat, account, text hash and send-policy generation; the confirm and the send re-check it on the stored row. The final checks read the project's lifecycle and policy generation again before the row. A `HumanActor` takes no part in a send. A new sender is a new member of `MessengerAuthority` through the same stages, never an unguarded alternate delivery path. Decision 0061 adds the public Watch target specialization through this door family: it shares the internal authorization registry, Stop, physical-account budgets and transactional `send_log`, while keeping public proposals separate from private messenger drafts. Each outcome is one `ops("send")` line, which carries the action id.
16. MUST (decisions 0050 and 0055, P142, P147): the daily follow-up sweep and the daily lead and mail passes are the only scheduled runs that start a model, and none adds a send path. A pass turn holds its eight tools bound to one lead (`HUB_LEAD_PAGE`) or one inbound message (`HUB_MAIL_INBOUND`) and no send tool; its replies wait in the day's lead batch for the owner's Send all ready, and a run never resumes by itself after a restart. A fixed bug's note (P145 B4) is a sweep turn bound to its note (`HUB_FOLLOWUP_BUG_NOTE`) and waits the same way. The sweep: Its turn holds the nine tools bound to one client (`HUB_FOLLOWUP_CLIENT`; another client is `followup_other_client`) and no send tool; a Mail nudge is always a draft (`@hub/send` refuses `follow-up-nudge` in `send.mode: auto`); a messenger nudge is sent only in an autopilot chat, through the door with the `autopilot` authority under decision 0048's switches, checked again right before the send, at most one a day per chat and three in a row. The plan (`follow_ups`) is the agent's notes: no tool, door or draft check refuses because of it.

17. MUST (decision 0061, P167): public Watch membership and reviewed replies require the protected `state/projects/<slug>/watch-policy.json` owner grant: exact real account, source/direction scope, provenance and generation. Readability is not membership. Durable membership attempts and account waits survive restart; pending requests are inspected, manual gates are not bypassed. A public reply uses a real immutable public proposal and the distinct `watch_review` authority; the private door refuses that authority. Assessment and final checks re-read policy, lifecycle, source identity/content, permissions and exact draft hash. The shared audit transaction reserves the stable account/peer/reply target and provider random id before one delivery; ambiguity is held for reconciliation, never a fresh-id retry. No public author becomes a client, no private-chat sender is reused and no existing inbound or draft-write path gains delivery. The control CLI talks to the guarded server and creates no Telegram client/model/timer. Source strategy and review belong to the external operation, not a new Hub autopilot.

18. MUST (decision 0062, P167 continuation): the browser reads only existing immutable public proposals for the exact configured source/project/account/peer. Its review routes require the exact admin origin and a single-use 60-second ticket bound to proposal, full payload and current combined policy, consumed before asynchronous work. The browser cannot create proposals, supply source-rule acceptance or mint owner authority. Delivery still uses `watch_review`; no automatic retry or new ticket follows an uncertain request. A durable sending/uncertain row after reload is unresolved, and only a matching provider receipt is sent. Optional photo delivery additionally requires an explicit `photoReplies` grant, a verified project-local immutable JPEG/PNG and the reviewed caption. Bind the complete asset descriptor and caption to the payload; prepare and persist the provider photo identity before send reservation, then repeat every guard after upload. Preview and list never upload or send, and reconciliation verifies the prepared identity instead of Telegram's re-encoded bytes. No provider secrets or local paths enter browser DTOs.
