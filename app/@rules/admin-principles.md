# Admin principles

Scope: what a screen of the admin may show and ask, before any layout or component question. Read it before you design, add or change a screen. An original page of this project (decision 0025 in the owner's plan repo). The other pages say how to build it; this one says what to build.

## Rules

1. MUST: the admin shows data and what the agent did; the owner only decides. A control exists only when it is an owner decision: Send (after "I read the checks"), Skip, Hold, Done, Undo, Stop sending and Resume, the client flags, Stop follow-ups, Edit (P56: his own words before Send are the last part of the decision, not preparation; the agent prepares, he corrects; Save writes Mail through the agent's one writer and turns Checked off), Restore (P56: the Hub's own copy back from Mail's Trash when the Mail draft is gone, never a dead end), Open and Reveal (P61: the same fact in the program that holds it (Mail, Notion, Finder, the file's own app); changes nothing in the Hub and asks no agent; one registry, `@hub/contract/local`, one component, `components/local-action.tsx`), Hand off to Claude Desktop (P61 section 9: it would end the dock session and continue it in the desktop app, without the hub's rules, so it needs one confirmation naming that, never a remembered "don't ask"; not offered today, owner item 7: the button is shown disabled with its reason), Start after a restart (P67, decision 0033: whether this Mac starts the Hub at login; Settings ▸ This Mac; it changes no project, and Off never stops the server that answers), and a few settings. Where an Open or a setting sits is rule 12. Preparation (choosing clients, writing a brief, enrolling in follow-ups, sorting) is a phrase in a session, never a form in the admin: an empty state names the phrase to say, and what the agent prepared shows as a read-only view (a batch is `?batch=`, Follow-ups lists its steps with Stop). Why: the agent reads the clients in Notion and Mail; the admin database holds only clients the agent already recorded (`README.md` rule 16), so a builder in the admin could never see whom to pick. Check: review against this rule; the send door stays the one write that sends (`README.md` rule 3).
2. MUST: a screen exists only when it answers a question no other screen answers; the list of screens and the reason for each is `README.md` rule 8a. Overview exists on every instance (P63) with one job (P70): what needs you. It opens on "Needs you": the agent's open questions, then each part of the Hub that is broken or needs a look, worst first, with what is wrong, the fix line (the source's own, or the phrase a session needs) and one link to where it is fixed; when nothing needs him, one line, "Everything works". Every part, healthy and "Not checked here" ones included, is folded under "All parts"; it holds no control. Its project table, which answers "which project needs me", exists only with two or more projects, first. Why: a screen that repeats another is read twice and trusted less. Check: review; the one- and two-project scenarios (`ui-specifications.md` rule 1a).
3. MUST: list first. Under a screen's header line comes its content (the list, the table, the card); no paragraph, banner, accordion or explainer sits above it. A screen's standing is at most one status line (rule 10). Why: on real data a four-line paragraph and an accordion pushed the first draft 381 px down a phone. Check: `FIRST_ROW_MAX_PHONE` (200 px) and `CONTROL_CAP` (36 tab stops) in `e2e/a-layout.spec.ts` (`ui-specifications.md` rule 4a).
4. MUST: no page max-width; text measure only. Pages, panes, lists and tables fill the pane. Every screen is one `@hub/ui/product/page`: a header line (the section title, actions at the end) and a body that fills the pane, padding 16 px (24 px from 640 px). Running prose (the draft body, notes, help and empty-state text) carries the `measure` utility of `styles.css` (`max-inline-size: 70ch`); nothing else is narrowed. Why: line length is a reading cost for prose, while a centred column wasted 100 to 400 px on each side of every list. Check: rules test "no max-w- on a page or pane container" (`test/rules.test.ts`).
5. MUST: logs and lists of records are tables, `@hub/ui/product/data-table` (the coss `Table` with the grid look: hairline rows, 36 px rows from 1024 px and 44 px below, the header sticky in the pane's scroll container, widths in percent). The outcome of a row is in the row: no Details disclosure per row. A value the hub does not know (model, tokens, cost, duration) is hidden, never shown as "0s" or "$0.00". Below 640 px a row becomes two lines; no column is moved behind a click. Why: Activity showed eight identical rows and put who and what behind one click each. Check: review; the Activity scenario (`ui-specifications.md` rule 1a).
6. MUST: one list-detail. A screen with a subject to open (Drafts, Activity) is `@hub/ui/product/list-detail` (`design-system-and-tokens.md` rule 13); a screen with no subject (Knowledge, the five Settings panes, Overview, Help) is one page. No resizable panes, no second split component, with one exception: the terminal column (P49), the one resizable surface, because a terminal's useful width depends on the program it runs (about 80 columns for Claude Code, far fewer for a plain shell), so no one width fits. The terminal is a dock beside every screen, not a screen (`README.md` rule 8a). Collapsed it never disappears: from 640px it is a 44px strip on the right edge, full height (an icon, the open tab's program written vertically, a dot while a session runs or while the agent waits on him: P59, the attention colour then, cleared when he opens the column or the next prompt arrives, also for a session that is not in the dock; on a phone the same dot is on the top line's terminal button), one button that expands it to the column; collapsing returns to the strip and the sessions keep running. The sidebar holds no terminal button. Below 640px the strip would take a column from a 360px screen, so the phone's top line holds the one terminal button and the terminal opens as a full-screen layer. The strip is always there (no switch, decision 0032); when no tab can start (P66) the column says the reason and the fix line with a copy button and the `+` items are disabled with the reason, never hidden. Opening the column starts the best ready CLI by itself (P57: the first ready one in `agent.default`'s order, Claude Code by default, else Shell; at most once per project per page load; never on page load with the strip collapsed); when that was not the first choice, one quiet line under the tabs says why with the fix to copy, never a dialog; the `+` menu is the switch and says a CLI's state. Starting an agent is the hub's job, not a choice he makes. The sidebar's footer holds the agent activity feed (P59): the last five things the agent did in the project, each a label computed on the server and, when it names a draft, a link to the card; never a control that asks the agent anything (rule 1), not a screen and not a log view (no history, no filter: `hub log` is the history), hidden when the newest row is over an hour old; beside the theme the one sound switch (a setting). Why: one layout learned once; a split with nothing to open is an empty pane; he works on a card while the agent runs, so finished or waiting must reach him without the column open. Check: review; `e2e/a-layout.spec.ts` (no sideways scroll at each width).
7. MUST: a one-project instance shows no project chrome: no project switcher, no project table on Overview, and `/` opens Drafts. Overview is first in the nav on every instance (P63), and with two or more projects it is also the entry, and the switcher sits under the brand header (`routes-and-url-state.md` rule 10). Why: a picker of one item is noise, and with one project a project table repeats the Drafts status line; the parts of the Hub repeat nothing. Check: `e2e/b-routing.spec.ts` (entry and `/overview` per seed), `test/routes.test.ts`.
8. MUST: the brand comes from the instance config. The brand header (`@hub/ui/product/brand-header`, the top of the sidebar; the top line on a phone) shows `name` of `config/config.json` (fallback "Hub") and the `logo` file it names (served by `GET /api/instance/logo`), else a monogram from the name. No per-instance code, style or upload screen. Why: every instance gets the core by a pin bump; the only difference is data. Check: the `@hub/config` test (no name gives "Hub"); `hub doctor` warns when the named logo file is missing; review.
9. MUST: settings by frequency, over Settings (P70). Settings opens on Sending (`/settings`): its sentence (the project's worst fact when Sending fixes it, else whether sending runs) and Stop sending or Resume; then Sends, as a table, only when a send exists; then who drafts may go to and autosend, read only, each with the owner's own command (`./run.sh send policy set <slug> draft.recipients any`) and its copy button, since the send policy is his alone and out of the agent's reach (P49 S11; P70 Q1: no switch here); last Checks before sending (the safety rules, "Blocks Send" or "Warns", a switch each, the words and days inline), closed with a one-line summary that names a rule set off. It stays closed then too: its 20 switches and two fields would pass `CONTROL_CAP` in the first viewport (P70 S1, measured against rule 3's cap), so the summary says it instead. Every other pane opens on what it governs (Mail: the project's accounts, then its filters; Agent: one sentence and Refresh, then one table per CLI; Connections: the two keys; This Mac: start after a restart, then the core version). Every pane carries the sub-nav (Sending, Mail, Agent, Connections, This Mac) in its header line. A setting that edits a project file (the mail filters, the project status) is a phrase to the agent, shown read only. Why: 18 switches were in view and none had ever been changed by the owner; and one place for what is set rarely is where he looks first, as on a Mac. Check: `e2e/y-settings.spec.ts` (the first viewport at 1280 shows the sentence, Stop and Sends; Checks closed; a rule set off is named in the summary).
10. MUST: one status sentence, no repeated count. A screen's standing is said once: the worst fact in plain words (`statusDto.sentence` of `@hub/contract/overview`), at most one link to the place that fixes it (`next`: Overview, Knowledge, or the Settings panes Sending, Mail, Agent, Connections and This Mac; never the list itself), and the numbers the line adds (reply owed, last triage age). The page that fixes the worst fact carries a dot in the nav; a child page's dot also lights its parent, and on a phone More lights for the sections inside it. A count shown in the nav or the View menu (to review) is never repeated in the line or a heading, and no number appears twice on one screen. Why: one fact was said three times on one screen (header, list, sidebar footer). Check: `e2e/y-status-line.spec.ts` (one scenario per level), `test/status-line.test.ts`; copy review per screen.
11. MUST: the row and the selection. A draft row is three lines (the name and the time; the subject on the full width; a meta line of chips), 64 px high at 1280; the subject is never cut below 40 characters at 1280. Views are one View menu with counts, never a row of chips. Selecting never inserts a bar: the list's header line turns into "N selected · Skip · Hold · Clear" in place, at the same height, and announces the count (`accessibility.md` rule 5); a selected row shows its checkbox and the tint; the focus ring is inset (`accessibility.md` rule 3). Why: the inserted bar moved the first row 50 px and the subject was cut to 15 characters. Check: `e2e/z-selection.spec.ts` (the first row does not move when a row is selected), `e2e/a-layout.spec.ts` (the subject at 1280, `SELECTING_CAP`).
12. MUST: the principle of correspondence (P70). An Open lives on the thing it opens: a button that opens a file or folder sits on the row or the header of the screen that lists it (an entry's Open on its Knowledge row, Open folder in Knowledge's header), and a screen that shows none of it has no Open for it; the files no screen lists (`project.md`, the project folder, Workflows) are on Help, "Where things live", the one screen whose question is "where is it". A setting lives with what it governs: what gates Send with Sending, the mail rules with Mail, the agent's model with the agent's tools, an instance key with the instance's other keys. A page is something he works with; Settings is what he sets once: Drafts, Activity and Knowledge are content, Overview is standing, and everything set rarely that changes how the Hub behaves is one place, Settings, grouped by what it governs. The test of every control, now and later: what does it govern or open, and where would the owner look for it first? "Nowhere in particular" means it goes or moves. Why: a Files menu on the Project landing opened files no screen showed, and the owner could not guess why it was there. Check: review against this rule; `e2e/z-local-actions.spec.ts` (an Open only where its target is listed, none with `localOpen: false`).
