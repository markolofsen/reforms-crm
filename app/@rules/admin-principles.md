# Admin principles

Scope: what a screen of the admin may show and ask, before any layout or component question. Read it before you design, add or change a screen. An original page of this project (decision 0025 in the owner's plan repo). The other pages say how to build it; this one says what to build.

## Rules

1. MUST: the admin shows data and what the agent did; the owner only decides. A control exists only when it is an owner decision: Send (after "I read the checks"), Skip, Hold, Done, Undo, Stop sending and Resume, the client flags, Stop follow-ups, and a few settings. Preparation (choosing clients, writing a brief, enrolling in follow-ups, sorting) is a phrase in a session, never a form in the admin: an empty state names the phrase to say, and what the agent prepared shows as a read-only view (a batch is `?batch=`, Follow-ups lists its steps with Stop). Why: the agent reads the clients in Notion and Mail; the admin database holds only clients the agent already recorded (`README.md` rule 16), so a builder in the admin could never see whom to pick. Check: review against this rule; the send door stays the one write that sends (`README.md` rule 3).
2. MUST: a screen exists only when it answers a question no other screen answers; the list of screens and the reason for each is `README.md` rule 8a. Overview exists only with two or more projects, because only there it answers "which project needs me". Why: a screen that repeats another is read twice and trusted less. Check: review; the one- and two-project scenarios (`ui-specifications.md` rule 1a).
3. MUST: list first. Under a screen's header line comes its content (the list, the table, the card); no paragraph, banner, accordion or explainer sits above it. A screen's standing is at most one status line (rule 10). Why: on real data a four-line paragraph and an accordion pushed the first draft 381 px down a phone. Check: `FIRST_ROW_MAX_PHONE` (200 px) and `CONTROL_CAP` (36 tab stops) in `e2e/a-layout.spec.ts` (`ui-specifications.md` rule 4a).
4. MUST: no page max-width; text measure only. Pages, panes, lists and tables fill the pane. Every screen is one `@hub/ui/product/page`: a header line (the section title, actions at the end) and a body that fills the pane, padding 16 px (24 px from 640 px). Running prose (the draft body, notes, help and empty-state text) carries the `measure` utility of `styles.css` (`max-inline-size: 70ch`); nothing else is narrowed. Why: line length is a reading cost for prose, while a centred column wasted 100 to 400 px on each side of every list. Check: rules test "no max-w- on a page or pane container" (`test/rules.test.ts`).
5. MUST: logs and lists of records are tables, `@hub/ui/product/data-table` (the coss `Table` with the grid look: hairline rows, 36 px rows from 1024 px and 44 px below, the header sticky in the pane's scroll container, widths in percent). The outcome of a row is in the row: no Details disclosure per row. A value the hub does not know (model, tokens, cost, duration) is hidden, never shown as "0s" or "$0.00". Below 640 px a row becomes two lines; no column is moved behind a click. Why: Activity showed eight identical rows and put who and what behind one click each. Check: review; the Activity scenario (`ui-specifications.md` rule 1a).
6. MUST: one list-detail. A screen with a subject to open (Drafts, Activity) is `@hub/ui/product/list-detail` (`design-system-and-tokens.md` rule 13); a screen with no subject (Project, Connections, Overview) is one page. No resizable panes, no second split component, with one exception: the terminal column (P49), the one resizable surface, because a terminal's useful width depends on the program it runs (about 80 columns for Claude Code, far fewer for a plain shell), so no one width fits. The terminal is a dock beside every screen, not a screen (`README.md` rule 8a). Why: one layout learned once; a split with nothing to open is an empty pane. Check: review; `e2e/a-layout.spec.ts` (no sideways scroll at each width).
7. MUST: a one-project instance shows no project chrome: no project switcher, no Overview in the nav, `/` opens Drafts and `/overview` replaces to Drafts. With two or more projects the switcher sits under the brand header, Overview is first in the nav and is the entry (`routes-and-url-state.md` rule 10). Why: a picker of one item is noise, and with one project the Overview repeats Project. Check: `e2e/b-routing.spec.ts` (entry and `/overview` per seed), `test/routes.test.ts`.
8. MUST: the brand comes from the instance config. The brand header (`@hub/ui/product/brand-header`, the top of the sidebar; the top line on a phone) shows `name` of `config/config.json` (fallback "Hub") and the `logo` file it names (served by `GET /api/instance/logo`), else a monogram from the name. No per-instance code, style or upload screen. Why: every instance gets the core by a pin bump; the only difference is data. Check: the `@hub/config` test (no name gives "Hub"); `hub doctor` warns when the named logo file is missing; review.
9. MUST: settings by frequency. Project opens on the status sentence and Stop sending or Resume; then Sends, as a table, only when a send exists; then Knowledge, Mail filters and Health, one line each, closed unless one fails; last Advanced (safety rules as a table), closed with a one-line summary and opened when a rule is off. A setting that edits a project file (recipients mode, project status) is a phrase to the agent (`project-setup`), shown read-only. Why: 18 switches were in view and none had ever been changed by the owner. Check: `e2e/y-project.spec.ts` (first viewport at 1280 shows status, Stop and Sends; Advanced closed; a rule set off opens it).
10. MUST: one status sentence, no repeated count. A screen's standing is said once: the worst fact in plain words (`statusDto.sentence` of `@hub/contract/overview`), at most one link to the place that fixes it (`next`: Project or Connections, never the list itself), and the numbers the line adds (reply owed, last triage age). The section that fixes the worst fact carries a dot in the nav. A count shown in the nav or the View menu (to review) is never repeated in the line or a heading, and no number appears twice on one screen. Why: one fact was said three times on one screen (header, list, sidebar footer). Check: `e2e/y-status-line.spec.ts` (one scenario per level), `test/status-line.test.ts`; copy review per screen.
11. MUST: the row and the selection. A draft row is three lines (the name and the time; the subject on the full width; a meta line of chips), 64 px high at 1280; the subject is never cut below 40 characters at 1280. Views are one View menu with counts, never a row of chips. Selecting never inserts a bar: the list's header line turns into "N selected · Skip · Hold · Clear" in place, at the same height, and announces the count (`accessibility.md` rule 5); a selected row shows its checkbox and the tint; the focus ring is inset (`accessibility.md` rule 3). Why: the inserted bar moved the first row 50 px and the subject was cut to 15 characters. Check: `e2e/z-selection.spec.ts` (the first row does not move when a row is selected), `e2e/a-layout.spec.ts` (the subject at 1280, `SELECTING_CAP`).
