# @hub/messengers

Messengers in the local CRM (track P8, decision 0003; track P71, decision 0036). Three channels: a **Telegram bot on grammY 1.46.0, long polling** (no webhook, no tunnel), the owner's own **Telegram user account over MTProto with mtcute 0.32.8** (P71 M1), and his own **WhatsApp number as a linked device with Baileys 7.0.0-rc14** (`baileys` on npm, the maintained name of `@whiskeysockets/baileys`; P71 M5). The two user accounts send only through the server's send door (P71 M4).

**Status.** Optional. The server starts the bot poller when `state/secrets/telegram-bot-token` exists (`apps/server/src/messengers/bot.ts`), and one connection per user-account session under `state/secrets/sessions/` (`telegram-user.ts`, `whatsapp.ts`); `HUB_MESSENGERS=off` disables all of them, and each reports its state in `/api/health`. The bot token is set on Settings ▸ Messengers or with `hub token telegram` (access: `@docs/setup/access.md`); the Telegram account and the WhatsApp number are connected there too. The Messengers section (P71 M3) is the review queue of the linked chats. Linking to the one client history with mail goes through `client_identifiers`. Every reply is an unsent draft the owner sends himself; nothing delivers in the background.

## Two entries, on purpose

| Import | For | Contains |
|---|---|---|
| `@hub/messengers` | the agent, the server, tests | adapters, ingest, poller, `clientHistory`, `createDraft`, `normalizeIdentifier`, types. Nothing here links, approves or sends. |
| `@hub/messengers/human` | an entry point that knows a person is present (and the server's autolink, P84) | `humanActor`, `linkIdentifier`, `unlinkIdentifier`, `knowChat`, `forgetChat`, `linkUserChat`, `linkUserChatToRecord`, `addClientEmail` (P141 C4), `discardDraft` (each needs a `HumanActor`); and a user account's login (`createLoginFlows`), WhatsApp's pairing (`createWaPairing`, `qrRows`) and session writes (`writeSession`, `removeSession`): only a person logs in or scans a QR code. One export needs no `HumanActor`: `autoLinkUserChat` (P84), the Hub's own link on an exact match, called only by `apps/server/src/messengers/autolink/autolink.ts` after it checked `messengers.autolink`, the refusals and the match. |
| `@hub/messengers/door` | the server's send routes only | `assessMessenger`, `applyMessenger` and the types `MessengerAuthority`, `MessengerDoorDeps`, `MessengerProjectPolicy` (P112 S2, below). |

Draft-first is enforced by types and by what can be imported, not by a prompt:

- An agent can only `createDraft` (status `draft`, in a known chat; the agent's tools admit a linked chat, or an unlinked one only on the owner's words in an attended session: decision 0049, P141 U5).
- `adapter.send` takes a `ConfirmedDraft`, a branded type minted only in `send-confirmed.ts` (the door's confirm and send, not in any package entry). A hand-built or cast object is refused at run time (WeakSet check), and the package `exports` map blocks a deep import of the minter.
- A `HumanActor` is minted only by `humanActor()`: by the messengers CLI when stdin is a TTY, and by the server behind the admin gate (exact admin Origin, loopback Host, `Sec-Fetch-Site: same-origin`; decision 0036 point 7): the Telegram and WhatsApp link routes and the autolink's `link` of a record the owner picked. It plays no part in a send (P112 S2). The agent and `hub mcp` never import `@hub/messengers/human`.
- **The send door's stages** (`door.ts`, P112 S2), each a function, in order and each on fresh reads: the assessment (`assessMessenger`: the project's lifecycle, the draft still waiting, a linked chat with an inbound message, the draft's client still the chat's, Stop sending, the recipients policy, the account connected, its cap and spacing); the authorization (`authorize`: the caller's `MessengerAuthority` and confirmation against the assessment; mints the one `SendAuthorization` of `authorization.ts`, bound to the draft, chat, account, text hash and send-policy generation); the final checks (lifecycle and policy generation read again); the audit (the `send_log` row first, Stop sending, cap, spacing and the one-time owner-word reference re-checked in its write); the delivery (confirm and one send, each re-checking the text hash on the stored row; no retry). Each outcome is one ops line, source `send`, with the request's action id. The caller always names its authority (`owner_click` after the route took the admin's ticket, `owner_word` for decision 0046); there is no default. The project facts come in by composition (`policy(project)`: `apps/server/src/send/messenger-policy.ts`), so this package reads no project file.
- **The seam for decision 0048** (P139, not built): the server's messenger autopilot is one more member of `MessengerAuthority` (its actor and the turn it answers) with its cases in `actorOf` and `referenceOf`; it passes the same five stages. The door reads no session mode, so the unattended deny lists (which bind the model's processes) never reach it.
- `telegram_user` (P71 M4) and `whatsapp` (M5) send through the server's send door only (decision 0036 point 7: `packages/messengers/src/door.ts`, P126 D1): a dry run, a ticket, the `send_log` row first, one `sendText` through the adapter's `send`, no retry, after the guards (an inbound message in the chat, 30 a day and 20 s apart per account, `allow_list` entries `telegram:<id>` or `whatsapp:+<number>` in test mode, Stop sending). The poller holds `pollOnly(adapter)`, so the receiving side has no send path. Nothing is copied by hand any more: the copy path (`copyDraft`, the CLI's `copy`) went with M5.
- There is no automatic Messenger delivery today and no reply mode that asks for one: no background runner creates a send-log row, mints a `SendAuthorization` or calls an adapter. The owner reviews the draft and uses the explicit Send action; MCP and the agent package never receive a send capability. Decision 0048 is the record for the one automatic mode (P139): a server runner behind its own code guard, through this door, in chats the owner switched on.

## The Telegram user account (P71 M1)

The owner's own account (decision 0036; he connects his main number, the risk of a ban is his). Pieces:

| File | Does |
|---|---|
| `telegram-user.ts` | `createTelegramUserAdapter` over a small `MtClient` interface: mtcute's new-message events go into a bounded queue (1000) that `poll` drains, so `runPoller`, the cursor (the highest stored message id) and the backoff are the bot's one path. Private chats with people only (no groups, channels, bots or Saved Messages); text kept, media as its kind, both directions (`out` for his own replies). After a restart or an overflow the next poll reads the linked chats' history from the cursor. `toUserAdapterError`: `logged_out`, `banned` and a flood wait over an hour **park** the account (fatal for `runPoller`, recorded as `parked <code>: ...` in `messenger_accounts.last_error`, never retried by itself); a shorter flood wait is waited out; a socket error is `network` (backoff). |
| `telegram-user-api.ts` | The only file that imports mtcute: `MemoryStorage`, mtcute's log off, a dialog pass on connect to warm its in-memory peer cache (a bare user id cannot be resolved without it). Loaded lazily (`mtcuteClients()`). |
| `telegram-user-login.ts` | The login: `api_id` and `api_hash`, phone, code, 2FA password, one call each; values in memory for 10 minutes, never logged; refusals are sentences that never echo what was typed. Only the final session is stored. |
| `sessions.ts` | `state/secrets/sessions/telegram_user-<id>/session`, mode 600 in a 700 folder: the session string with the `api_id` and `api_hash` mtcute needs on every connect. Not in `app.db`, not backed up. |

Privacy (decision 0049, which amends 0036 point 3): with `cacheUnlinked` (the server's setting) every private chat's messages are cached for `CACHE_DAYS` (30) and the chat becomes known on its first inbound message; without it, a message of a chat that is not known is dropped in the event handler (and again at the drain), leaving no row, no counter and no log line. In both cases only its identity (id, name, phone, username) goes to `onUnlinked` for the autolink (P84, section below). A chat is linked by `linkUserChat` (the owner's pick in the dialog picker), `linkUserChatToRecord` (his Link of a Notion record) or the autolink's `autoLinkUserChat`, each of which also imports its last 30 days. The picker reads dialogs on demand; suggestions match a dialog's Telegram id or phone against the client's identifiers (`client_identifiers` has no username kind, so a username is never a suggestion source). Its `send` (P71 M4) takes only a `ConfirmedDraft` for a known chat (`chat_not_known` otherwise) and maps Telegram's refusal like a poll error; a park it reports parks the account.

`@mtcute/node` depends on better-sqlite3 12; its native build is refused in `pnpm-workspace.yaml` (`allowBuilds: better-sqlite3: false`) because `MemoryStorage` never loads it. The server's supervisor is `apps/server/src/messengers/accounts/telegram-user.ts`.

## WhatsApp as a linked device (P71 M5)

The owner's own number (decision 0036 point 2; not the WhatsApp Business API: the risk of a ban is his), linked like WhatsApp Web: Settings ▸ Messengers ▸ WhatsApp, Connect, then he scans the QR code with his phone (WhatsApp ▸ Settings ▸ Linked devices ▸ Link a device). Pieces:

| File | Does |
|---|---|
| `whatsapp.ts` | `createWhatsAppAdapter` over a small `WaSocket` interface, the same shape as the Telegram user adapter: Baileys' events go into a bounded queue (1000) that `poll` drains, through the one `runPoller`. Private chats with a person only; text kept, media as its kind, both directions. The chat id is the number as `normalizeIdentifier("whatsapp")` keeps it (`+` and digits), so `client_identifiers` (kind `whatsapp`), the allow-list and `allow_list` (`whatsapp:+<number>`) agree. The cursor is the newest message time (WhatsApp ids are not ordered); after a restart WhatsApp itself delivers what arrived offline. Baileys does not reconnect by itself: a close is the next poll's failure and that poll opens a new socket (a 515 restart is not an error), one socket at a time: a connect in flight is shared by `poll`, `start` and the import, and the close of a socket already replaced is ignored. Every close carries WhatsApp's reason (`Stream Errored (conflict): conflict type=device_removed`, `Connection Failure: reason=401`), which `toWaAdapterError` appends in brackets, so `messenger_accounts.last_error` says why a number was parked. `toWaAdapterError`: 401, 411 and 500 park as `logged_out`, 403 as `banned` (no flood wait exists here), 440 (opened elsewhere) stops without a park, 429 waits, the rest is `network`. |
| `whatsapp-api.ts` | The only file that imports Baileys, loaded lazily (`baileysSocketFactory()`). Building a socket connects at once, so no test builds one. Options that are privacy rules: Baileys' log at `warn` into the server's log through `whatsapp-log.ts` (`waLogger`: warn and error lines only, jids, numbers of 6 digits or more and key-shaped strings masked, an object that is not a node or an error named by its keys, never printed), plus one `whatsapp close: code N <reason>` line per close; `shouldIgnoreJid` drops groups, broadcasts, newsletters and status before an event is built; `markOnlineOnConnect: false` (his phone keeps ringing for new messages); `syncFullHistory: false`. A LID chat is read through its phone alias (`remoteJidAlt`), else dropped. The WhatsApp Web version is fetched once per process from Baileys' repository (`fetchLatestBaileysVersion`, 5 s, GitHub, never WhatsApp); on a failure the version this Baileys release carries is used. |
| `whatsapp-log.ts` | No Baileys import: `waLogger`, `logLine`, `redactWa`, and `disconnectDetail` (a close's Boom: its message and the `<stream:error>` child or `<failure>` attributes, redacted). |
| `whatsapp-auth.ts` | The auth state: Baileys' creds and Signal keys, one file each in `state/secrets/sessions/whatsapp-<number>/` (`creds.json`, `key.<type>.<id in base64url>.json`), mode 600 in a 700 folder, written atomically; a folder or file readable by others is refused. Not in `app.db`, not backed up; recovery is a new scan. It never imports Baileys (`BufferJSON` is applied in `whatsapp-api.ts`), so the pairing and the tests run on it. |
| `whatsapp-pairing.ts` | Connect: a socket over an empty in-memory store, the QR code (a new one about every 20 s) as module rows for the admin to draw (`qrRows`, `qrcode-generator`; the QR string never leaves the server), then on the phone's scan Baileys reports `paired`, sends the device's signature (`pair-device-sign`) and WhatsApp closes with 515: **only on that 515** does the store go to the number's folder and the supervisor connect the number from its files, over the same creds. The pairing socket is never closed on `paired`: Baileys emits it before the signature, in the same handler, and a close there cut the reply off, so WhatsApp kept the half-registered device for 5 to 8 minutes and then logged it out with 401 (saas, twice on 2026-11-20; `FakeWaSocket.pairSigned` tests it). Nothing is written before the scan; a pairing lives 3 minutes. |
| `fake-wa.ts` | `FakeWaSocket` (and `FakeBoom`): the fake Baileys socket every test runs on. |

Privacy (decision 0049): as on Telegram, a private chat's messages are cached for 30 days while `cacheUnlinked` is on (the Mac's WhatsApp app reader), else a message of a chat that is not known is dropped in the event handler and at the drain. Baileys has no dialog list to read on demand, so the picker reads a directory held **in this process's memory only**: each private chat's number, its name and the key and time of its newest message, never a text; it goes with the process or the disconnect and is never written. The import on link asks the phone for the chat's history before that newest message (`fetchMessageHistory`) and waits up to 15 s for the answer, so the newest message seen before the link is not imported (it is the anchor), and a chat with no message since the connection opened imports nothing: new messages arrive anyway. **Verify at the real link** (owner items): the phone's answer to an on-demand history request, and LID chats' phone aliases. Disconnect logs the device out on WhatsApp's side (it leaves Linked devices) when it is connected, then deletes the folder. Baileys' preinstall (a Node version check) and protobufjs' postinstall are refused in `pnpm-workspace.yaml`; `sharp`, a peer of Baileys for media, is installed but never loaded. The server's supervisor is `apps/server/src/messengers/accounts/whatsapp.ts`.

## Chats link themselves (P84, decision 0036 point 3 as amended 2026-11-20)

The owner delegated it ("decide the optimal"): a private chat of a connected account links itself to a client when its phone (E.164) or Telegram username equals the identifier of exactly one client record.

| File | Does |
|---|---|
| `autolink.ts` | Pure: `buildDirectory` (records with their phone keys, each for both channels or one, and username keys), `matchDialog` (`unique`, `ambiguous` for two or more, `none`), `e164` (a number with `+` or `00` only: a local number is never guessed into one), `username`. A saved contact name never matches. |
| `signature-phones.ts` | `extractSignaturePhones`: the numbers with their country code in a mail's signature block (after a sign-off or `-- `, else the last 12 lines; quoted text and a reply header cut). Deterministic, no model. **Not wired:** the server reads no mail text, and a signature is the sender's own text, so when it is wired it may only suggest, never autolink. |
| `telegram-user.ts`, `whatsapp.ts` | `onUnlinked`: each inbound message of an unlinked Telegram chat, and each unlinked WhatsApp chat seen, hands the matcher its identity, never the text, before it is dropped. |

The records come from the server (`apps/server/src/clients/directory.ts`): the project's Notion Clients data source read only, in memory, every 6 h, `Synthetic` and `Do not contact` rows left out; identifiers from the pack's Clients fields (`schema/clients.json`, `@docs/notion/README.md`): `Phone` (or any other `phone_number` property, or one named Mobile or Tel) for both messengers, `WhatsApp` for WhatsApp chats only, `Telegram` (a username, `@name` or `t.me/name`, or a number) for Telegram chats only; `matchDialog` takes the dialog's channel and looks up only that channel's keys. The coordinator (`apps/server/src/messengers/autolink/autolink.ts`) links a `unique` match when the project's `messengers.autolink` is `on` (the client row from its Notion email and name, the identifier, the allow-list with `messenger_chats.autolinked` = the reason, 30 days imported, an Activity line `linked`), keeps everything else in memory for the Chats screen, scans a Telegram account's 500 newest dialogs when it connects, and skips a chat whose HMAC is in `messenger_link_refusals` ("never link this chat"; the key is `state/secrets/autolink-key`, not backed up). WhatsApp has no dialog list on demand: it sees the chats seen since its socket opened, and a chat linked by its first message imports from the phone's history before that message (P71 M5 finding 2), so that first message itself may be missing.

## Data (migrations 0003, 0025, 0027, 0028 and 0029 in `@hub/db`)

`messenger_messages` (text kept in full, `retain_until` = stored + 90 days, `purge` deletes past it), `messenger_chats` (the known chats, decision 0049: a row is KNOWN, a `client_identifiers` row naming it makes it LINKED; since 0025 each chat's rules, since 0044 `profile_name`), `messenger_accounts` (poll cursor, last ok, last error), `client_identifiers` (client, kind `email|telegram|telegram_username|phone|whatsapp`, value; unique per project, kind and value), `messenger_drafts` (since 0025 also `owner_request`, the owner's words that admitted a draft in an `on_request` chat, and `nudge`, a follow-up after our own last message). `send_log` (0027) carries a messenger send's row (`channel`, `messenger_draft_id`); `messenger_link_refusals` (0028) the HMAC of each chat the owner refused; `messenger_triage` (0029) the pre-analysis verdicts.

Ingest stores known chats (and makes a chat known on its first inbound message when the cache is on) and never links anything. Linking is the owner's (the picker on Settings ▸ Messengers, Link on Chats, or `messengers link`) or the autolink's on an exact match (above).

**Unlink keeps the chat, Hide forgets it** (decision 0049): `unlinkIdentifier` removes only the identifier, so the chat stays known and its copy expires with the cache; `forgetChat` (Hide, Never link, `messengers forget`) goes through `repos.messengers.forgetChat`, which deletes the chat's `messenger_messages`, its `messenger_drafts` and its `messenger_chats` row in ONE transaction.

**Retention runs without a channel** (gap 2): the server purges at start and every hour (`apps/server/src/messengers/purge.ts`), whatever is connected; a running poller still purges every 6 h, and `messengers purge` by hand.

## Rules per chat (P71 M2b, research 23 section 2)

The Settings page puts the project-level reply policy first: `messengers.language` and `messengers.instruction` are the project defaults. Per-chat columns below are explicit gates or exceptions and are shown under each linked chat's `Advanced rules` disclosure; draft-first remains the safe default.

Columns on `messenger_chats`, set only by the owner (Settings ▸ Messengers since M3, through the gated `PUT /api/projects/:slug/messengers/chats/:id/rules` over `repos.messengers.setChatRules`): `reply_mode` `off` | `on_request` | `draft` (default `draft`; no auto value, 0036 point 8), `instruction` (the owner's words, at most 4 000 characters), `language` (BCP-47; null: the client's), `prefilter` (default off; the pre-analysis below). The vocabulary, defaults and bounds live once in `@hub/config/chat-rules`; the migration's CHECKs repeat the bounds. The agent reads them with `messenger_history` and `messenger_draft_write` enforces them in code (`@hub/agent`, `src/messenger/rules.ts`): `reply_off`, `no_inbound` (the hub never makes first contact), `not_requested` (an `on_request` chat without the owner's words), and `already_drafted` for a chat that already has an open draft.

## Pre-analysis (P71 M-P, decision 0039, research 23 sections 1 and 3)

A chat whose `prefilter` the owner turned on has each inbound text message labelled by a cheap model through `@hub/llm` (`llm.batch`, the `cheap` preset, task `messages.preanalysis`, about 20 messages per request): `needs_reply`, `unclear`, `fyi`, `closing`, `automated` or `personal`. Code: `apps/server/src/messengers/preanalysis.ts` (the pass), `@hub/db` `repos/messenger-triage.ts` (the rows), the vocabulary in `@hub/config/chat-rules` (`TRIAGE_LABELS`, `HIDDEN_LABELS`).

- **Linked chats only, the body only.** Only stored rows of linked chats with the switch on are read (0036 point 3; an unlinked chat's text never reaches a model). The model sees the message's text and the two messages before it marked `client` or `owner`; never a sender's name, the chat's title, its id, the account or the client record. Our own messages and media are never judged; only messages of the last 7 days (`PREANALYSIS_LOOKBACK_DAYS`), at most 100 per pass.
- **Hide, never delete; fail open.** `closing`, `automated` and `personal` are hidden from the agent: kept, counted by reason, and readable with `messenger_history`'s `include_hidden`. `unclear` and everything else reach it. An item the model answered unusably twice (`llm.batch`'s alone re-ask included) is stored `unjudged` and reaches the agent; it is never asked again. A request that fails as a whole (the cap, the key, the network) stores nothing, and a later pass asks again.
- **Results:** `messenger_triage` (migration 0029), one row per message (verdict, model, prompt version, no text), `ON DELETE CASCADE` from `messenger_messages`: the retention purge and unlinking a chat take it along. Live topic `messengers`.
- **When it runs:** after a poll that stored messages (the bot, Telegram and WhatsApp supervisors' `onStored`) and when the owner turns a chat's switch on; never on a timer (decision 0039 point 3). One pass per project at a time; a call during a pass runs one more after it. No key and not `HUB_LLM=fake`: nothing is asked, so no ledger row is written per poll, and the switch's note says "Needs an OpenRouter key". The monthly cap of P78 applies to every request.
- **What the owner sees:** Messengers ▸ Chats, a muted line per chat with the counts by reason ("Pre-analysis: hid 3 of 12 (2 closing, 1 automated)"), and a newest message that was hidden owes no reply (`owed` false, "Their last message was hidden by the pre-analysis"); Settings ▸ Messengers, the switch with what it does or why nothing runs, and the same counts.
- **What the agent sees:** `messenger_history` leaves hidden messages out and returns `prefilter` (`on`, `hidden` by reason, `unjudged`, `left_out_below`, `newest_in_hidden`: the client's newest message was hidden, so no reply is owed; `triage-messages` skips it); `include_hidden: true` returns them marked `hidden`. Errors and pass counts go to the ops log, source `preanalysis` (counts and error kinds, never a text).
- **Not built (research 23):** units of one sender's messages within 2 minutes (each message is its own item), a flush timer or a flush on `messenger_history` (no timer is allowed and `hub mcp` holds no LLM), shadow mode (the switch is per chat and off by default instead), "Show to the agent" per hidden message, a summary per message.

## The agent's tools (P71 M2)

The agent never imports this package's send path: `hub mcp` (`@hub/agent`) has `messenger_history` (a linked chat, or a client's linked chats, with the rules and the open draft) and `messenger_draft_write` (one row in `messenger_drafts`, status `draft`, on a short write connection), both through `@hub/db` only, so `hub mcp` loads no Telegram client (research 26 section 4). A chat that is not linked, or is another project's, is `not_linked` and named nowhere. The guard asks for a `messenger_history` read of that chat earlier in the session before a draft (`@hub/projects`, `chat-ledger.ts`). The skill is `skills/triage-messages/SKILL.md`. The admin's owner-gated `Prepare reply` route is a second typed draft-only entry point: the Hub LLM writes one unsent draft (`apps/server/src/messengers/reply.ts`). Send is the server's door (P71 M4), pressed by the owner; decision 0046: in an attended session `hub mcp`'s `messenger_send` asks the server's agent send route, which verifies the owner's word in the session log and calls the same door (`actor` `agent_on_owner_word`); the agent still imports nothing of this package.

## History

`clientHistory({ repos, mail }, project, clientId, { limit, cursor })` merges mail (any `MailHistory`-shaped reader, injected) with stored messenger rows, newest first. The cursor is a position in the merged order. Paging deep into old mail re-reads its newer pages; the reader is a local read, so that is cheap.

## CLI

`hub messengers -p <project> <command>`

| Command | Needs a person at a terminal | Does |
|---|---|---|
| `link <clientId> <kind> <value>` | yes | links an identity to a client; a chat is also made known |
| `unlink <kind> <value>` | yes | removes the link; the chat stays known, not linked |
| `know` / `forget <channel> <chatId>` | yes | makes a chat known without a client; `forget` deletes its row, cached messages and drafts |

| `status` | no | poll health (stale after 10 min), known chats, counts, drafts |
| `poll [--once]` | no | the worker loop with offset persistence and backoff; `--once` fetches one batch and prints ids of unlisted chats |
| `purge` | no | deletes rows past retention |

## The bot token

A **new** bot from @BotFather, token alone in `state/secrets/telegram-bot-token` (chmod 600). Never the token of a bot that already has a webhook, and a webhook and `getUpdates` exclude each other. `start()` calls `deleteWebhook` on the bot it owns. The value is never logged; errors are scrubbed of anything token-shaped.

## Tests

`pnpm --filter @hub/messengers test`: Vitest, the `FakeAdapter`, `FakeMtClient`, `FakeLoginClient` and `FakeWaSocket`, an in-memory database. No network, no real token, no Telegram login, no WhatsApp socket (one test loads the real Baileys for its auth state and message mapping and builds no socket).
